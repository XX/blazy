  Одно архитектурное решение по ходу                                                       
                                                                                           
  Канвас пришлось разделить на два виджета. Трансформ виджета маппит его собственный border-box в родительский, и paint-проход преобразует clip path тем же window_transform — то есть один виджет с клипом и вью
  зумировал бы собственный вьюпорт вместе с содержимым. Отсюда CanvasLayer (клип, ввод, владеет вью) → CanvasContent (несёт трансформ, владеет детьми).
                                                                                           
  LOD подключён через систему свойств Masonry (CanvasDetail + property_changed), а не через трейт — так канвас остаётся пригодным для разнородных детей.
                                                                                           
  Результаты замеров                                                                       
                                                                                           
  Три тезиса проверялись, два подтвердились:                                               
                                                                                           
  Пан и зум не перезапускают layout детей — 0.0 вызовов layout на кадр. Перетаскивание одной ноды не трогает соседей — тоже 0.0. Обычные слайдеры и чекбоксы Masonry работают внутри зумируемых нод без правок —
  канвас только смотрит ctx.is_handled().                                                  

  Culling — нет. Стоимость кадра линейна по общему числу нод и не зависит от видимых:      
                                                                                           
  ┌────────┬────────┬──────────┬──────────┐
  │ Всего  │ Видимо │   idle   │   пан    │                                                
  ├────────┼────────┼──────────┼──────────┤
  │    250 │     24 │  0.22 мс │  0.81 мс │                                                
  ├────────┼────────┼──────────┼──────────┤                                                
  │ 16 000 │     27 │ 21.11 мс │ 66.29 мс │                                                
  └────────┴────────┴──────────┴──────────┘                                                
                                                                                           
  64× нод → 81× времени при неизменной видимой части. Контрольная проверка с другой стороны: сценарий с 280 видимыми нодами стоит те же ~21 мс, что и с 27.
                                                                                           
  Причина в двух местах masonry_core. passes/paint.rs рекурсирует по всем детям, включая stashed, намеренно — «to avoid creating zombie flags». А passes/compose.rs хоть и имеет ранний выход, но set_transform
  ставит transform_changed, который передаётся вниз по всей рекурсии, так что пан композитит всё дерево.
                                                                                           
  Что это меняет в плане                                                                   
                                                                                           
  Masonry берём. Ни один провал не касается абстракции рендера, retained-дерева, трансформов, свойств или маршрутизации событий — то есть всего, ради чего он и выбирался. Проблема ровно одна и решается на нашей
  стороне.

  виртуализированные 5000 нод должны стоить как нынешние 250, то есть примерно в 26 раз дешевле.
