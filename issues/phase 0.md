  Что сделано

  CanvasContent переписан: вместо Vec<Child> со сташенными виджетами — Vec<Slot>, где геометрия есть всегда, а pod: Option<WidgetPod> только пока нода в кадре. Виджеты строит NodeSource по требованию.

  Три решения по ходу:

  Модель — источник истины. Виджет живёт только пока нода видна, значит состояние в нём хранить нельзя. GraphNode пишет слайдер и чекбокс обратно в GraphModel через on_action, а build читает актуальное. Это не
  костыль — граф и так должен переживать любое представление ради сохранения и undo.

  Материализация в mutate-проходе. Добавление детей требует WidgetMut, которого в layout нет. cull() считает набор в layout и ставит mutate_self_later; mutate идёт раньше layout в rewrite-цикле, так что нода
  входит в кадр за один кадр. virtual_scroll для этого гоняет запрос через драйвер — нам не нужно, канвас сам владеет фабрикой.
  
  Диффинг слиянием двух отсортированных списков индексов: без аллокаций и хеширования.

  Предложения, по убыванию отдачи

  1. Simplified: не строить контролы вообще (≈4.3×). Сейчас чекбокс сташится, а слайдер живёт. По §20.2 сташенный виджет всё равно обходится проходами — это ровно та полумера, которую мы уже один раз
  опровергли. На зуме 0.15 слайдер высотой 3 px всё равно не нажать. Рисовать значение полоской прямо в GraphNode::paint.

  Требует расширить API: NodeSource::build(&mut self, index, detail), плюс полная переборка живых нод при пересечении порога. Порог пересекается редко, так что это дёшево.

  2. Full: контролы только там, где с ними работают (≈6× в пределе). При 140 нодах в кадре пользователь взаимодействует с одной. Третья ось виртуализации — «презентационная нода» против «интерактивной»:
  контролы материализуются под курсором и у выделенных. Ровно это делает большие нод-редакторы отзывчивыми.

  Дешёвый частный случай: Checkbox::new(checked, "on") тащит Label. Чекбокс без текста убирает виджет на ноду — минус 25% бесплатно.

  3. HUD в примере: 0.08 мс на кадр, до 54% дешёвых кадров. format_hud аллоцирует строку каждый layout, а post_paint шейпит текст parley каждый кадр. Это ровно то immediate-mode расточительство, против которого
  вся архитектура. Кэшировать Layout, перестраивать только при смене строки. Влияет на замеры, а не только на демо: hover 0.155 → 0.072 мс.

  4. cull() — две аллокации на вызов. Vec::with_capacity плюс visible.clone(). Клон не нужен: вне far-field desired == visible, достаточно сравнить с live напрямую. Плюс переиспользовать буфер вместо аллокации.

  5. cull() работает на каждом layout, даже когда вид не менялся, и это O(всего графа) — 4.4 нс/нода, при 100k нод уже 0.44 мс. Пропускать, когда visible_rect не изменился и ни одна нода не двигалась; дальше —
  uniform grid или R-дерево.

  6. CanvasContent::children_ids() аллоцирует, когда живых нод больше 16 (ChildrenIds = SmallVec<[WidgetId; 16]>), а вызывается по разу на проход. При 741 ноде это heap-аллокация несколько раз за кадр.
  
  7. apply_pending всегда дёргает request_layout(), давая второй полный layout-проход в кадрах, где состав менялся (~20% при пане).
