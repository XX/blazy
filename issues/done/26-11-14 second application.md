# Второе приложение: проверка публичного API

Библиотека пока на `publish = false`, а пин стоит на нашем форке Masonry (§17). Опубликоваться
нельзя, пока апстрим не выйдет на crates.io с нужным API, но проверить уже можно, «стоит ли с
этим API жить» (§15.1). `hello` для этого мал: он писался вместе с фасадом и знает его изнутри.

## Вопрос

Что приходится делать приложению, которое не писалось вместе с библиотекой, — где оно лезет во
внутренности, копирует код из `blazy-app` или `hello`, обходит фасад, — и что из этого исправить
до публикации?

## Разведка

* **Чего у приложения сейчас нет**, по разделам «Чего это не делает»:
  * сериализация графа — приложения (§42.4), и примера, как её писать, нет;
  * сессия (вид, история) не сериализуется (§44.7);
  * воркспейс описывает один экран, многооконной обёртки нет (§44.7);
  * экранные действия — не операторы `blazy-ops` (§47.5, §49.5);
  * системного буфера для нод нет: копию надо сделать текстом, а формат — приложения (§57.6).
    Это тот же формат, что у сохранения графа, и задача — место для обоих: сохранение и
    `Ctrl+C` в другой процесс через `ShellCtx::clipboard` (§56);
  * правки содержимого ноды из её виджетов идут мимо истории (§56.6: переименование в `hello`
    не отменяется).
* **Что появилось и требует проверки «стоит ли с этим жить»:**
  * шов `NodeGraph` — двенадцать обязательных методов и тип `Content` (§57.7); сколько строк
    это стоит приложению, которое пишет его с нуля, — число в разделе;
  * свой драйвер клавиш обязан собирать события через `OpEvent::from_keyboard`, иначе `Shift+D`
    и другая раскладка не работают; видно ли это из документации, а не из чтения `editor.rs`.
* **Что считать находкой.** Каждое место, где пример (а) импортирует не из `blazy`, (б)
  повторяет больше десятка строк из `blazy-app`/`hello`, (в) держит своё состояние, которое
  библиотека уже держит, (г) не может сделать то, что Blender делает из коробки.

## Что сделать

1. Пример `examples/<имя>`, только через фасад, с другим графом, чем у `hello`: несколько типов
   нод с разными портами и содержимым, сохранение и загрузка графа и воркспейса в файл, хотя
   бы одно окно сверх первого. Буфер обмена (§56) и копирование нод (§57) готовы — использовать;
   боковой регион и панель свойств.
2. Список находок — в разделе архитектуры, с решением по каждой: исправлено, отложено с
   причиной или «так и задумано» с аргументом.
3. Проход по публичным типам фасада: что `#[non_exhaustive]`, что конфиг, что лишнее наружу.

## Чем проверяется

* Пример собирается и проходит `cargo make ci` (фича-матрица, документация).
* Ручной проход по сценарию: создать граф, связать, сохранить, перезапустить, загрузить —
  записать, что проверено.

## Чего эта задача не делает

* **Не публикует крейты** и не двигает пин Masonry.
* **Не пишет книгу.** Документация для пользователя — отдельная работа, когда API перестанет
  меняться от каждой находки.
