# Фаза 0.6 — регионы и `ui_scale`

Спайк, не функциональность: цель — числа и вердикт, как в Фазах 0 и 0.5.

## Что открыто

§21.4 закрыл Фазу 0.5 выводом «форма здорова» и назвал ближайшее неизвестное:
пункт 5 плана §16, `ui_scale` на регион. Сейчас регионов внутри области нет вообще —
`AreaScreen` кладёт в область один виджет и на этом заканчивается.

§9 описывает три независимых множителя и прямо предупреждает про самую дорогую
ошибку в этом месте:

| Множитель | Откуда | Куда идёт |
|---|---|---|
| `device_scale` | ОС, один на окно | размер целевой текстуры |
| `ui_scale` | пользователь, **свой у каждого региона** | **layout**: кегль, паддинги, размеры контролов |
| `view` | пан/зум содержимого | **только paint**, как трансформ при композиции |

Смешать (2) и (3) — значит перезапускать layout на каждом кадре зума. Фаза 0 уже
доказала, что канвас этого не делает; здесь проверяется вторая половина: что
`ui_scale` действительно идёт в layout, действительно ограничен поддеревом региона и
не задевает ни соседние регионы, ни соседние области.

## Почему это, а не функциональность областей

join / maximize / swap / detach / сериализация — операции над деревом сплитов,
которое уже есть и покрыто тестами (§21.4). Они объёмны, но не рискованны: ни одна
не может опровергнуть архитектуру. `ui_scale` может — и это единственный оставшийся
пункт критического пути, про который §9 говорит «в апстриме этого нет, протаскивать
надо самим».

## Шаг 0 — разведка, до любого кода

Выяснить и записать, насколько далеко система свойств Masonry пускает нас без патча
апстрима. Конкретно: как `Length` разрешается в пиксели, читает ли это разрешение
что-либо, кроме `global_state.scale_factor`, и можно ли повлиять на кегль текста
(`parley`) и на `Padding`/`BorderWidth` через наследуемое свойство поддерева.

Механизм-образец есть: `CanvasDetail` в `blazy-canvas` — свойство, которое канвас
ставит детям и которое инвалидирует layout через `property_changed`. §9 прямо
называет `PropertyArena` + `property_changed` подходящим механизмом. Вопрос не в
том, доедет ли значение вниз, а в том, кто его прочитает на стороне встроенных
виджетов Masonry.

**Это шаг с развилкой.** Возможных исходов три, и от них зависит объём остального:

1. Свойства хватает — регион ставит `UiScale`, виджеты читают, `Length` считается с
   учётом. Работаем целиком у себя.
2. Хватает для наших виджетов, но не для масонриевских (`Slider`, `Checkbox`,
   текст). Тогда спайк меряет то, что есть, а в §17 добавляется четвёртый пункт для
   контрибьюта.
3. Не хватает принципиально. Тогда результат Фазы 0.6 — описание того, что именно
   надо в апстрим, и это тоже результат.

Записать исход в `rnd/architecture.md` §22 до того, как писать замеры.

## Что делать

1. **Регионы в `blazy-areas`.** `Region { kind, root: WidgetId, view: Affine,
   ui_scale: f32 }` внутри `Area`, по образцу §8. Минимум для спайка — два вида:
   `Header` (фиксированной высоты, содержимое масштабируется) и `Main`. Остальные
   (`Toolbar`, `Sidebar`, `Footer`) — функциональность, не риск.
2. **`UiScale` как свойство**, наследуемое вниз по поддереву региона, с
   инвалидацией layout через `property_changed`. Слой: `layout_scale =
   device_scale * region.ui_scale` идёт в `Length`; `region.view` не идёт никуда,
   кроме трансформа.
3. **Пример.** Расширить `examples/area-screen`: у каждой области шапка и main,
   `ui_scale` меняется с клавиши, чтобы разницу было видно глазом, а не только в
   счётчиках.
4. **Замеры** в `benches/screen/` поверх `bench-utils`, критерии — счётчиками, по
   дисциплине §20.9.

## Критерии (предварительные, уточнить по замерам)

Гейты — счётчики, миллисекунды информационные.

| Критерий | Счётчик | Смысл |
|---|---|---|
| смена `ui_scale` перекладывает только свой регион | виджеты вне региона, переложенные за кадр | = 0 |
| смена `ui_scale` не трогает соседние области | ресайзов областей за кадр | = 0 |
| зум содержимого не запускает layout | layout-проходов региона за кадр | ≈ 0 |
| простой не растёт от числа регионов | простой при 2 регионах на область против 1 | развёртка, как в §21.2 |

Пятое — резкость текста и кривых при любом из трёх множителей — счётчиком не
выражается. Это довод в пользу `imaging` из §9, и проверять его надо
golden-image-тестом на CPU-бэкенде (пункт 1 Фазы 1 плана §16), которого пока нет.
Либо тянуть этот пункт сюда, либо честно записать как непроверенное.

## Что не входит

`PaintLayerMode::IsolatedScene` на регион (§7.3) — по §21.4 экономить пока нечего;
мульти-окно и detach; сериализация workspace; выравнивание границ несоседних
областей; разнородные редакторы.

исходом разведки и вердиктом по пункту 5 плана §16.

## Выполнено

`cargo make ci` зелёный: 44 теста, 16 критериев в двух гейтах.

### Исход шага 0 — второй из трёх

Механизма хватает для наших виджетов и не хватает для масонриевских. Три находки,
подробно в `rnd/architecture.md` §22.1:

* **Layout целиком в логических пикселях**, `scale_factor` в него не входит вовсе —
  готового места, где длины на что-то умножаются, не существует.
* **Наследования свойств нет.** §9 предполагал «свойство, наследуемое вниз по
  поддереву»; на `ce7b04d` это неверно. `PropertyStack` висит на самом виджете,
  `Selector` фильтрует по классам и флагам состояния, по предкам — ничего.
  Работает `WidgetMut::insert_prop` → `property_changed` → виджет сам просит layout,
  по одному виджету за раз. Так же устроен `CanvasDetail` из Фазы 0.
* **Размеры приходят из трёх мест:** свойства с умолчаниями **на тип виджета** в
  `DefaultProperties` (одни на приложение), кегль как `parley`-овский
  `StyleProperty::FontSize` на экземпляр, и внутренние константы виджетов.

Исход зафиксирован не рассуждением, а тестом `masonry_widgets_do_not_follow_ui_scale`:
`Button` в регионе, смена `UiScale`, паддинг не сдвинулся. Тест упадёт с внятным
сообщением в тот день, когда апстрим обзаведётся масштабом на поддерево.

### Сделано

`AreaContent` — стек регионов внутри области, у каждого свой `ui_scale`; смена идёт
через mutate-проход и приземляется в том же кадре. `ScaledHeader` в примере — виджет,
честно читающий `UiScale` в `measure`/`layout`. Окно открывается с разным масштабом у
каждой области.

Соглашение, вынужденное отсутствием наследования: **контейнер передаёт `UiScale` вниз
сам**; автоматики нет.

### Критерии

Все четыре запланированных плюс пятый по цене региона:

| Критерий | Замерено | Граница |
|---|---:|---:|
| смена `ui_scale` доезжает до layout региона | 0 | < 0.5 пропущенных |
| смена `ui_scale` не ресайзит области | 0.00 | < 0.05 /кадр |
| смена `ui_scale` не достаёт до соседних областей | 0.00 | < 0.05 /кадр |
| зум содержимого не ресайзит регион | 0.00 | < 0.05 /кадр |
| второй регион не удваивает простой | 0.73× | < 2× |

Первый критерий проверен на вакуумность: если заставить шапку не читать свойство в
layout, он даёт 30.00 и роняет прогон.

### Развилка по резкости текста

Пятый пункт из постановки — резкость при смене любого из трёх множителей — счётчиком
не выражается. Решение: **записан как непроверенный**, а не притянут сюда. Golden-image
тест на CPU-бэкенде — это пункт 1 Фазы 1 плана §16, у него своя инфраструктура, и
тащить её в спайк про `ui_scale` значило бы смешать два вопроса. Дыра названа в §22.5.

### Следствия для плана §16

* Пункт 5 разблокирован для наших виджетов, заблокирован для масонриевских.
* Пункт 11 (`blazy-widgets`) перестал быть косметикой: это условие работоспособности
  `ui_scale` в плотном UI.
* В §17 добавлен четвёртый пункт для контрибьюта: переопределение
  `DefaultProperties` на поддерево. Тот же класс изменения, что публичный API для
  `PaintLayerMode` — инфраструктура готова, не хватает шва.
