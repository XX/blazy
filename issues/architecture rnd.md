  Диагноз: что реально тормозит в egui
  
  Не «пересборка UI каждый кадр» — прогон пользовательского кода дёшев. Дорого повторять производную работу: CPU-тесселяцию всех шейпов, layout на всё дерево, отсутствие damage tracking, аллокации. Плюс нет
  стабильной идентичности → боль с анимациями, фокусом и AccessKit.
  
  Vello убирает главный пункт бесплатно: тесселяции на CPU нет, флэттеринг кривых происходит на GPU с учётом финального трансформа. Следствие, которое стоит эксплуатировать как основу архитектуры:
  закодированный фрагмент сцены разрешение-независим — пан, зум и смена UI-scale не требуют перекодирования вообще.
  
  Парадигма
  
  Retained-дерево элементов со стабильными ID + опциональный декларативный слой с мемоизацией поверх (модель Xilem: View→diff→Element). Мемоизация по версии данных — именно она снимает аргумент против
  пересборки: движение мыши затрагивает единицы узлов, а не всё дерево. Декларативный слой делать последним, иначе его абстракции протекут в ядро и заблокируют встраивание в движки со своей реактивностью.
  
  Сменный рендер
  
  Не trait Renderer { fill_rect(); draw_text(); } — это chatty-интерфейс, убивающий кэширование, многопоточность и сериализацию. Вместо этого — backend-agnostic display list в форме, близкой к vello::Scene, с
  плоскими SoA-буферами, Cmd::Fragment для кэша и Cmd::Hole для областей, которые рисует хост (3D-вьюпорт). Шейпинг текста остаётся в ядре, бэкенд получает уже позиционированные глифы — иначе Vello- и GL-версии
  будут переносить строки по-разному.
  
  Бонус: смена версии Vello затрагивает один крейт из двенадцати.

  Производительность — три уровня кэша
  
  | A | нет грязных элементов → кадр не рисуется вообще |                                  
  | B | per-Area render-to-texture: тащишь ноду — остальные пять редакторов не перерисовываются |
  | C | per-layer scene fragments внутри грязной Area |
  
  Vello не умеет partial redraw по damage-регионам — инкрементальность строится над ним. Плюс relayout boundaries (Flutter) для инкрементального layout.
  
  Произвольные фигуры и gpui                                                               
  
  Ты прав, но важно, что именно не подходит. Рендер gpui — нет: специализированные шейдеры под quad/тень/спрайт-глиф, «всё есть прямоугольник» протекает в шейдеры. Архитектура элементов — да, стоит брать.
  
  Решение — разделить три обычно склеенные геометрии: layout-геометрия всегда Rect (иначе flex/grid невозможен), визуальная — произвольный BezPath, hit-геометрия — двухфазный тест (bbox через spatial index →
  точный winding через kurbo::Shape::contains, для связей — расстояние до кривой). 
  
  Blender-специфика
  
  - Окна: отдельная подсистема Screen → Area → Region над деревом виджетов, не «ещё один виджет» — у неё другие инварианты (persistent, сериализуемая, свой hit-тест краёв). Начинать с бинарного дерева сплитов;
    граф вершин/рёбер (как в самом Blender, ради выравнивания границ несоседних областей) — только если реально понадобится.
  - Масштабирование: три независимых множителя, которые нельзя путать — device_scale (HiDPI), ui_scale (свой у каждого региона, идёт в layout), view (пан/зум, только в paint). Смешать их = перезапуск layout на
    каждый кадр зума.
  - Ноды: CanvasLayer с инверсией указателя через view.inverse() — за счёт этого обычные виджеты работают внутри нод без единой правки. Плюс R-tree culling и LOD (Full/Simplified/Box), где на дальнем зуме
    layout детей отключается целиком.
  - Операторы + keymap как данные — одна точка для undo/redo, меню, горячих клавиш, скриптинга и тестов; модальные операторы на стеке вместо is_dragging: bool по виджетам.
  
  Риски Vello
  
  Нужны compute shaders (нет WebGL — держать vello_cpu/vello_hybrid как fallback); дорогие PushLayer с clip-path; conflation artifacts на встык прилегающих фигурах; мягкий мелкий текст — векторный рендер без
  хинтинга, на 10–11px при низком DPI будет заметно мягче egui/gpui с их атласами. Последнее — единственный пункт, где решение стоит отложить до момента, когда будет что мерить глазами.
  
  В §16 — порядок реализации из 10 шагов; CPU-бэкенд там вторым пунктом, ради golden-image тестов: без него дальнейшая работа над кэшированием слепая.

  Что изменилось

  Masonry отвязан от Vello. В xilem#1696 (https://github.com/linebender/xilem/pull/1696) (мерж 24.03.2026) Widget::paint принимает imaging::Painter<'_> вместо vello::Scene. imaging
  (https://github.com/forest-rs/imaging) — это буквально «backend-agnostic imaging IR and recording»: PaintSink-трейт для бэкендов, retained record::Scene для реплея. Бэкенды уже есть: imaging_vello (+cpu,
  +hybrid), imaging_skia, imaging_tiny_skia, imaging_wgpu.

  masonry_core на main зависит от imaging, kurbo, peniko, parley, accesskit, tree_arena, ui-events — ни vello, ни wgpu, ни winit. Твоё требование «сменный рендер для интеграции в движки» решено апстримом лучше,
  чем ты сделал бы в одиночку. 
  
  Дальше, из masonry_core/src/passes/paint.rs и widget_state.rs:
  
  - scene_cache: HashMap<WidgetId, (Scene, Scene, Scene)>, перекодирование гейтится по request_paint — уровень C из §7 уже есть;

  - VisualLayerKind::External { bounds } — ровно мой Cmd::Hole для 3D-вьюпорта хоста;
  - WidgetState::transform: Affine + window_transform + отдельный compose-проход — база для нод-канваса есть.
  
  Чего нет (и всё это аддитивно, форк не нужен)

  2. Per-region UI scale нет — один scale factor на окно.
  3. Damage regions нет. В paint-проходе буквально // TODO - Handle damage regions → xilem#789 (https://github.com/linebender/xilem/issues/789). Это уровень B из §7 и самый болезненный пропуск: именно per-area
     render-to-texture даёт основной выигрыш, когда на экране шесть редакторов. Правильный ход — контрибьютить, а не обходить.
  4. Нод-канваса нет. Canvas в Masonry — painter-callback без детей. Контейнер с per-child Affine, culling, spatial index и LOD писать самому.
