# blazy — архитектура

> **Задача.** GUI-библиотека на Rust с возможностями уровня Blender: сплиты окон,
> произвольное масштабирование UI в разных фреймах, контролы на нодах. Со сменным
> рендером для интеграции в движки. Без недостатков immediate-mode (egui). Компонентом
> может быть произвольная фигура.
>
> **Ревизия 2, август 2026.** Первая редакция проектировала весь стек с нуля. Проверка
> `linebender/xilem@main` показала, что три из четырёх ключевых подсистем уже реализованы
> апстримом. Документ переписан под связку **`imaging` + `masonry_core`**.
> Предыдущая редакция — `rnd/architecture.v1.md`, читать только ради истории решений:
> в ней есть фактические ошибки (см. §2.3).

---

## 0. Резюме решений

| Вопрос | Решение |
|---|---|
| Основа | **`imaging` (IR рендера) + `masonry_core` (retained-дерево)** как git-зависимости. Не писать своё |
| View-слой | `xilem` **не брать** на первом этапе. `masonry_core` работает без него |
| Что такое blazy | Не «ещё один тулкит», а **Blender-слой поверх Masonry**: areas/regions, нод-канвас, операторы |
| Абстракция рендера | Дана: `imaging::PaintSink` / `Painter` / `record::Scene`; бэкенды vello / vello_cpu / vello_hybrid / skia / tiny_skia / wgpu |
| Layout | Дан, но **не box constraints**: осевой measure/layout в стиле CSS (`Axis`, `LenReq`, `Dim`, `Length`) с встроенным кэшем измерений |
| Произвольные фигуры | Layout-геометрия — прямоугольник; визуальная — произвольная через `Painter`; хит — переопределяемый `find_widget_under_pointer` |
| Производительность | Уровни A и C даны (skip-frame, per-widget scene cache). **Уровень B (per-area текстуры) и damage — писать/контрибьютить** |
| Окна Blender | `blazy-areas`: Screen → Area → Region над деревом виджетов. Апстримного аналога нет |
| Ноды | `blazy-canvas`: контейнер с per-child `Affine`, culling, spatial index, LOD. `masonry::Canvas` для этого не годится |
| Взаимодействие | `blazy-ops`: операторы + keymap как данные + модальные обработчики |
| Главный риск | Апстрим в движении: crates.io отстаёт от main на ~10 месяцев, `imaging` — 0.0.1 |

## 1. Что уже дано апстримом

Всё проверено по исходникам `linebender/xilem@main` и crates.io в августе 2026.
Ссылки на файлы даны, чтобы это можно было перепроверить, а не принимать на веру.

### 1.1 `imaging` — абстракция рендера

Крейт [`forest-rs/imaging`](https://github.com/forest-rs/imaging), самоописание:
«backend-agnostic imaging IR and recording». Ровно та архитектура, которую первая
редакция предлагала строить самим.

* **Два режима.** Стриминг: `Painter` пишет команды в любой `PaintSink`.
  Ретейн: `record::Scene` — владеющее хранилище команд с валидацией и реплеем.
* **Примитивы.** `FillRef`/`FillBuilder`, `StrokeRef`/`StrokeBuilder`, `GlyphRunRef`,
  `BlurredRoundedRect`, `ClipRef`, `GroupRef` с `Filter`, `MaskRef`/`MaskMode`.
* **Композиция.** `replay_transformed(&scene, sink, affine)`,
  `Scene::append_transformed(&scene, affine)` — вставка готового фрагмента с
  произвольным трансформом. Это и есть механизм кэширования из первой редакции.
* **Бэкенды.** `imaging_vello` (+ `_cpu`, `_hybrid`), `imaging_skia`,
  `imaging_tiny_skia`, `imaging_wgpu`.
* **Трейты рендера.** `render::{ImageRenderer, RenderSource}`, целевые типы и форматы.

### 1.2 Masonry отвязан от Vello

[xilem#1696](https://github.com/linebender/xilem/pull/1696), мерж **24.03.2026**:
`Widget::paint` принимает `imaging::Painter<'_>` вместо `vello::Scene`.
`masonry_core/Cargo.toml` на main: `imaging`, `kurbo`, `peniko`, `parley`,
`accesskit`, `tree_arena`, `ui-events`, `smallvec`, `tracing`.
**Ни `vello`, ни `wgpu`, ни `winit`.**

Мотивация апстрима — нерешённые проблемы Vello classic и переход на sparse-strips.
Для нас это означает, что требование «сменный рендер» выполнено чужими руками и
поддерживается людьми, которые пишут сам рендер.

### 1.3 Retained-дерево с точечной инвалидацией

`masonry_core/src/passes/paint.rs`:

```rust
scene_cache: &mut HashMap<WidgetId, (Scene, Scene, Scene)>   // pre / main / post
...
if ctx.widget_state.request_paint {
    scene.clear();
    let mut painter = Painter::new(scene as &mut dyn PaintSink);
    widget.paint(&mut ctx, &props, &mut painter);
}
```

`paint()` виджета вызывается **только** при взведённом `request_paint`. У виджета
три сцены: `pre_paint` (фон, бордер, тень — вне клипа), `paint` (содержимое, под
детьми), `post_paint` (поверх детей, вне клипа). Плюс — отдельный кэш измерений
(`layout/measurement_cache.rs`) с ключом `(axis, len_req, cross_length)`.

### 1.4 Слои и дыры для хоста

`masonry_core/src/app/visual_layers.rs` (Copyright 2026 — совсем свежий код):

```rust
pub struct VisualLayerPlan { pub layers: Vec<VisualLayer> }

pub struct VisualLayer {
    pub kind: VisualLayerKind,
    pub transform: Affine,      // из layer-local в window space
    pub widget_id: WidgetId,
}

pub enum VisualLayerKind {
    Scene(Scene),               // ретейненная сцена в локальных координатах
    External { bounds: Rect },  // плейсхолдер: содержимое рисует хост
}
```

`RenderRoot::redraw() -> (VisualLayerPlan, Option<TreeUpdate>)` — на выходе **план
слоёв**, а не одна сцена. `VisualLayerKind::External` — это ровно `Cmd::Hole` из
первой редакции: дыра под 3D-вьюпорт хоста.

Документация типа прямо говорит: *«This is the semantic paint output of Masonry.
Current hosts still consume it through compatibility helpers that flatten or
reinterpret it, but the plan is the source of truth.»* То есть хост **вправе
реализовать слои иначе** — например, каждый в свою текстуру. Это наш штатный
крючок для уровня B (§7.3).

### 1.5 Трансформы и compose-проход

`WidgetState`: `transform: Affine`, `scroll_translation`, `window_transform`,
`transform_changed`, `compose_local_transform()`. Отдельный дешёвый проход
`Widget::compose(&mut ComposeCtx)` — «cheaper alternative than doing a full layout».

Это фундамент для нод-канваса: подвинуть ноду = обновить `transform` и запросить
compose, без перелейаута и без перекодирования сцен детей.

### 1.6 Остальное из коробки

* **Текст** — `parley` (shaping, перенос строк, bidi, курсор, выделение), виджеты
  `prose`, `text_area`, `text_input`, `variable_label`.
* **Доступность** — `accesskit`, отдельный проход, `TreeUpdate` из `redraw()`.
* **Развязка с winit** — `ui-events`; апстрим обсуждает `baseview` для VST-плагинов,
  то есть встраиваемость для них не абстрактное требование.
* **Свойства** — CSS-подобная система: `PropertiesRef/Mut`, `PropertyArena`,
  `DefaultProperties`, `property_stack_id`, `class_set`, колбэк `property_changed`.
  Готовая база для тем и стилей.
* **Мульти-окно** — в `masonry_winit` окна по `HandleId`, у каждого свой `RenderRoot`.
* **Слои виджетов** — `get_layer_root(idx)`, `edit_base_layer(..)` для попапов/оверлеев.
* **Виджеты** — 38 штук, включая `split`, `virtual_scroll`, `portal`, `zstack`,
  `indexed_stack`, `grid`, `flex`, `svg`, `resize_observer`.

## 2. Что это меняет для blazy

### 2.1 Позиционирование

Писать свой IR, своё retained-дерево, свою обвязку parley/AccessKit — значит потратить
человеко-годы на догон того, что уже работает, и получить на выходе четвёртый
Rust-тулкит общего назначения.

**blazy = Blender-слой поверх Masonry.** В экосистеме этого действительно нет, и
это защитимая позиция: система областей, нод-канвас с виджетами внутри нод, операторы
и keymap. Всё это аддитивно, **форк Masonry не требуется**.

### 2.2 Что остаётся написать

| Подсистема | Апстрим | Наше |
|---|---|---|
| IR рендера, бэкенды | ✅ `imaging` | — |
| Retained-дерево, проходы, кэш сцен | ✅ `masonry_core` | — |
| Layout | ✅ осевой measure/layout | адаптеры для areas и канваса |
| Текст, a11y, свойства | ✅ | — |
| Трансформы виджетов | ✅ `WidgetState::transform` | — |
| Дыры под 3D хоста | ✅ `VisualLayerKind::External` | реализация в хосте |
| **Screen/Area/Region** | ❌ | `blazy-areas` (§8) |
| **Per-region UI scale** | ❌ | `blazy-areas` (§9) |
| **Нод-канвас** | ❌ | `blazy-canvas` (§10) |
| **Операторы, keymap, модальность** | ❌ | `blazy-ops` (§11) |
| **Damage regions** | ❌ TODO #789 | контрибьютить (§7.3) |
| **Per-area render-to-texture** | ⚠️ скелет | контрибьютить + хост (§7.3) |
| **Точный хит-тест по фигуре** | ⚠️ крючок есть | `blazy-shape` (§6.2) |

### 2.3 Ошибки первой редакции — исправить

1. **«Layout — box constraints (Flutter/Druid)».** Неверно для текущего Masonry.
   Там осевая CSS-подобная модель `measure`/`layout` с `LenReq` и `Dim` (§5).
   Проектировать areas и канвас надо под неё.
2. **«Xilem — заимствовать идеи, не зависеть».** Написано по данным, устаревшим на
   год: тогда Masonry был жёстко прибит к Vello. После #1696 это не так.
3. **«Написать свой display list в форме `vello::Scene`».** Не нужно, есть `imaging`.
4. **«Relayout boundaries по tight constraints».** Понятия tight constraints в
   текущей модели нет; инкрементальность обеспечивается кэшем измерений и флагами
   `request_layout`.

## 3. Структура крейтов

```
        imaging            IR: Painter, PaintSink, record::Scene
        imaging_vello      + _cpu, _hybrid, _skia, _tiny_skia, _wgpu
        masonry_core       Widget, RenderRoot, проходы, scene cache, parley, accesskit
── граница blazy ──────────────────────────────────────────────────────
blazy-areas     Screen/Area/Region: сплиты, join, workspaces, per-region scale   §8 §9
blazy-canvas    CanvasLayer: per-child Affine, culling, spatial index, LOD       §10
blazy-ops       операторы, keymap, модальность, undo/redo                        §11
blazy-shape     произвольные хит-формы, кэш flatten, хит по кривой               §6
blazy-widgets   контролы, рассчитанные на нод-канвас и плотный UI редактора
blazy-compose   per-area render-to-texture поверх VisualLayerPlan                §7.3
blazy-shell     хост: окна, ввод, композиция (winit / встраивание)               §14
```

`xilem` в списке нет намеренно (§15.3).

**Правило зависимостей:** `blazy-areas`, `blazy-canvas`, `blazy-ops`, `blazy-shape`
зависят от `masonry_core` и `imaging`, но **не** от `masonry_winit`, `wgpu` и `winit`.
Всё, что знает про конкретный GPU-бэкенд и оконную систему, живёт в `blazy-shell`
и `blazy-compose`. Это то же правило, что и в первой редакции, просто граница
абстракции теперь проходит по чужому коду, а не по нашему.

## 4. Рендер и интеграция

### 4.1 Как рисует виджет

```rust
fn paint(&mut self, ctx: &mut PaintCtx<'_>, props: &PropertiesRef<'_>,
         painter: &mut Painter<'_>) {
    painter.fill(&self.body_path, brush).draw();
    painter.stroke(&self.outline, &stroke_style, color).draw();
}
```

Никакого `vello::Scene`. `Painter` пишет в `dyn PaintSink`, за которым может стоять
`record::Scene` (Masonry так и делает — ретейн) или напрямую бэкенд (стриминг).

### 4.2 Как хост получает картинку

```rust
let (plan, tree_update) = render_root.redraw();
// вариант 1 — совместимость: сплющить всё в одну сцену
plan.replay_into(&mut sink);
// вариант 2 — наш: реализовать слои по-своему (§7.3)
for layer in &plan.layers { /* своя текстура на слой */ }
```

`masonry_winit` идёт по варианту 1: берёт `root_layer()` и `overlay_layers()`,
собирает `PreparedFrame` и зовёт
`ImagingRenderer::render_to_texture(ImagingRenderTarget { adapter, device, queue, texture, view }, frame)`.

Это же — готовая форма guest mode: **хост отдаёт свои `Device`/`Queue`/текстуру**,
`imaging` не создаёт ни окна, ни девайса. Требование «встраивание в чужой движок»
удовлетворяется без единой строки нашего кода на уровне рендера.

### 4.3 3D-вьюпорт внутри UI

`VisualLayerKind::External { bounds }` — виджет объявляет, что его содержимое
рисует хост. Masonry записывает плейсхолдер в план, композитор хоста заполняет
прямоугольник своим пассом.

Оговорка из исходников: *«Current hosts do not realize these placeholders yet;
compatibility consumers simply skip them while flattening scene content.»*
Модель ядра готова, реализация в хосте — за нами (`blazy-shell`, §14). Для
Blender-подобного приложения это обязательный пункт, а не опция.

## 5. Layout: осевая модель Masonry

Это самое серьёзное отличие от первой редакции. Проектировать `blazy-areas` и
`blazy-canvas` надо под реальную модель.

### 5.1 Модель

```rust
fn measure(&mut self, ctx: &mut MeasureCtx<'_>, props: &PropertiesRef<'_>,
           axis: Axis, len_req: LenReq, cross_length: Option<Length>) -> Length;

fn layout(&mut self, ctx: &mut LayoutCtx<'_>, props: &PropertiesRef<'_>, size: Size);
```

* `measure` — «сколько ты хочешь по этой оси», вызывается **только** когда длина по
  оси не задана явно. Может вызываться много раз за проход, может не вызываться вовсе.
* `LenReq::{MinContent, MaxContent, FitContent(Length)}` — прямая калька с CSS
  intrinsic sizing.
* `Dim::{Auto, Fixed(Length), Ratio(f64), ...}` — как длина задаётся снаружи.
  `Ratio(0.5)` = 50% контекстной длины, с откатом в `Auto`, если контекста ещё нет.
* `layout` — родитель решил размер, контейнер обязан для каждого ребёнка вызвать
  `compute_size`/`compute_length` → `run_layout` → `place_child`.
* `LayoutCtx::set_clip_path` — клип, влияющий на paint (но не на `pre_paint`/`post_paint`).

### 5.2 Инкрементальность

Кэш измерений встроен: ключ `(axis, len_req, cross_length)`, инвалидация через
`request_layout`. Документация трезво предупреждает: кэш маленький, несколько записей
на виджет; если измерение дорогое — виджет обязан иметь свой внутренний кэш.

**Что это значит для нас.** Тело ноды в графе — виджет с дорогим измерением
(много детей). Значит `blazy-canvas` обязан:
* задавать нодам явные `Dim::Fixed` там, где размер известен (позиция и ширина ноды
  хранятся в модели графа) — тогда `measure` не вызывается вообще;
* иметь собственный кэш измерений на ноду поверх масонриевского;
* при LOD-переходе в `Detail::Box` (§10.3) не измерять содержимое вовсе.

### 5.3 Ловушка

`measure` **не должен** коммитить состояние: «don't commit any layout choices».
Соблазн посчитать в `measure` раскладку сокетов ноды и сохранить — прямой путь к
трудноуловимым багам, потому что за одним `measure` не гарантирован `layout`,
а `measure` может быть вызван несколько раз с разными гипотезами.

## 6. Произвольные фигуры

### 6.1 Три геометрии — тезис остаётся в силе

| Геометрия | Форма | Где живёт |
|---|---|---|
| Layout | всегда прямоугольник | `measure`/`layout`, `Size` |
| Визуальная | произвольная | `Painter::fill/stroke` по `kurbo` |
| Хит | произвольная | `find_widget_under_pointer` |

Layout обязан быть прямоугольным — любой flow/grid работает с bounding box; это не
ограничение, а условие существования компоновки. Нарисовано и кликабельно внутри
бокса — что угодно.

### 6.2 Хит-тест по фигуре

Апстрим даёт два крючка:

```rust
fn accepts_pointer_interaction(&self) -> bool { true }        // грубый флаг
fn find_widget_under_pointer<'c>(&'c self, ctx: QueryCtx<'c>, pos: Point)
    -> Option<WidgetRef<'c, dyn Widget>>;                     // переопределяемый
```

Второй — то, что нужно. `blazy-shape`:

```rust
pub struct ShapeHit {
    path: BezPath,
    flat: RefCell<Option<Flattened>>,   // кэш, версионируется с геометрией
    mode: HitMode,
}

pub enum HitMode {
    Fill { rule: FillRule },      // winding number: kurbo::Shape::contains
    Stroke { width: f64, slop: f64 },  // расстояние до кривой: ParamCurveNearest
}
```

Две фазы: грубая по bbox (её делает Masonry, спуская по дереву), точная — наша,
в переопределённом `find_widget_under_pointer`. Для связей между нодами — режим
`Stroke`: расстояние до кубической безье ≤ `width/2 + slop`.

### 6.3 Почему gpui не подходит — и что в нём всё-таки верно

**Рендер gpui не подходит.** Он построен на специализированных шейдерах под узкий
набор примитивов: quad со скруглением и бордером, тень, спрайт глифа из атласа,
подчёркивание. Произвольные пути — отдельный, менее оптимизированный путь. Модель
«всё есть прямоугольник» протекает в шейдеры. Для нод с круглыми сокетами, безье-связями
и радиальными меню это постоянная борьба с фреймворком. Плюс атласный рендер плохо
переносит произвольный зум: смена масштаба = ресемплинг или ретесселяция.

**Архитектура элементов gpui верна** — retained-дерево, taffy, типизированные хендлы
состояния. Но брать её теперь неоткуда и незачем: `masonry_core` даёт то же самое,
только с векторным рендером и без привязки к бэкенду.

Vello/`imaging` подходят именно потому, что произвольная кривая для них **нативный
примитив, а не спецслучай**, а закодированная сцена хранит кривые, а не треугольники,
и потому разрешение-независима.

## 7. Производительность

### 7.1 Диагноз IM — что именно дорого

Повторный прогон пользовательского кода каждый кадр дёшев. Дорого повторять
**производную работу**: CPU-тесселяцию, layout всего дерева, shaping, аллокации.
Плюс отсутствие стабильной идентичности бьёт по анимациям, фокусу, drag-state и
доступности.

Masonry снимает это конструктивно: стабильные `WidgetId`, `paint()` только по
`request_paint`, кэш измерений, `imaging` без тесселяции на CPU, `compose` вместо
полного layout для чистых сдвигов.

### 7.2 Что реально даёт кэш сцен — и где предел

> **ИЗМЕРЕНО (Фаза 0, август 2026).** Этот раздел был написан по чтению исходников
> и оказался прав в диагнозе, но **неполон в выводе**. Замеры `examples/node-canvas`
> показали, что дело не только в пересборке сцены слоя: проходы Masonry рекурсируют
> по **всему дереву виджетов**, а не по видимой части. Culling через `set_stashed`
> обязателен, но **недостаточен** — нужна виртуализация. Она реализована и
> перемерена: стоимость кадра стала независимой от размера графа. Числа — в §20.


Уровень A (кадр не рисуется, если ничего не изменилось) и уровень C (per-widget
кэш сцен) — есть.

**Но есть нюанс, который надо понимать до того, как строить на нём планы.**
В `paint.rs` после проверки `request_paint` идёт безусловное:

```rust
layer_collector.scene_mut().append_transformed(pre_scene,  content_box_to_layer_transform);
// ... clip ...
layer_collector.scene_mut().append_transformed(scene,      content_box_to_layer_transform);
// ... рекурсия по детям ...
layer_collector.scene_mut().append_transformed(post_scene, content_box_to_layer_transform);
```

Кэш экономит **вызов `paint()`**, но сцена слоя пересобирается каждый кадр: команды
всех видимых виджетов копируются в неё заново. Стоимость кадра — `O(суммарного объёма
команд видимых виджетов)`, а не `O(изменившихся)`.

Для обычного приложения это несущественно. Для Blender-подобного (шесть редакторов,
тысячи элементов) — это и есть потолок. Отсюда два вывода:

1. **Culling в нод-канвасе обязателен**, а не «оптимизация на потом» (§10.2).
   Невидимая нода не должна попадать в `append_transformed`.
2. **Уровень B критичен.** Без него перетаскивание одной ноды пересобирает сцену
   всего окна.

В исходниках это признано:
* `passes/paint.rs`: `// TODO - Handle damage regions` → [xilem#789](https://github.com/linebender/xilem/issues/789)
* `passes/paint.rs`: `// TODO - Reserve scene` → [xilem#524](https://github.com/linebender/xilem/issues/524)
* `render_root.rs::redraw`: `// TODO - Handle invalidation regions`
* комментарий в рекурсии: *«Once we implement compositor layers…»*

### 7.3 Уровень B: per-area render-to-texture

Каркас в апстриме уже есть:

```rust
pub enum PaintLayerMode { Inline, IsolatedScene, External }
```

`IsolatedScene` заставляет paint-проход завершить текущий слой и начать новый —
поддерево получает собственный `VisualLayer` со своим `transform`.

**Состояние: скелет.** Поле `WidgetState::paint_layer_mode` — `pub(crate)`, публичного
сеттера для виджета нет; в паспорте типа написано: *«Current hosts still flatten these
scene layers back together, so changing this does not yet change runtime presentation
behavior.»*

Наш план, по возрастанию инвазивности:

1. **Контрибьютить публичный API** для объявления виджета границей слоя
   (`PaintCtx::set_paint_layer_mode` или свойство). Изменение маленькое, ложится
   в направление, которое апстрим уже выбрал.
2. **`blazy-compose`: реализовать слои по-настоящему.** `VisualLayerPlan` для этого
   и задуман («the plan is the source of truth»). Каждый `VisualLayer` — своя
   текстура; чистый слой переиспользуется, композит экрана = blit нескольких квадов.
   LRU-пул текстур, для мелких областей отдельная текстура не выделяется.
3. **Damage regions** — самое инвазивное, делать только через апстрим (#789).

Практический эффект уровня B: тащим ноду в нод-редакторе — таймлайн, аутлайнер,
свойства и шейдер-редактор не перерисовываются вообще. Ровно так работает браузерный
композитор и, по сути, сам Blender со своими region redraw flags.

Смежные заготовки в forest-rs, стоит посмотреть перед тем, как писать своё:
`cachet` (atlas allocation, tiled-surface caching), `invalidation` (dirty tracking,
топологически упорядоченная инвалидация), `understory` (пространственные и scene-структуры
для UI и графических редакторов), `layerstack`.

### 7.4 Что мерить

Бенчмарк, который надо завести первым и держать в CI:

* 5000 нод в канвасе, видимо ~40 → время кадра при движении одной ноды;
* то же при пане канваса (меняется один `Affine`, layout не трогается);
* шесть областей на экране, активна одна → доля кадра, потраченная на неактивные;
* 10k элементов в списке, меняется один.

Без этих цифр рассуждения об уровнях кэша — гадание.

## 8. `blazy-areas`: Screen → Area → Region

Апстримного аналога нет. `masonry::widgets::split` — сплиттер на две панели, а не
модель экрана: нет join, maximize/restore, типов редакторов, сериализуемых
workspace-лейаутов, отсоединения области в отдельное ОС-окно.

Это **отдельная подсистема над деревом виджетов**, а не «ещё один виджет»: у неё
другие инварианты — персистентность, сериализуемость, собственный хит-тест краёв
и drag-логика.

```rust
pub struct Screen { root: NodeId, nodes: Slab<SplitNode> }

pub enum SplitNode {
    Split { dir: Axis, ratio: f32, a: NodeId, b: NodeId },
    Area(AreaId),
}

pub struct Area {
    editor:  Box<dyn Editor>,     // 3D view, node editor, timeline, outliner...
    regions: Vec<Region>,         // header, toolbar, sidebar, main, footer
    rect:    Rect,
}

pub struct Region {
    kind:      RegionKind,
    root:      WidgetId,          // корень поддерева Masonry
    view:      Affine,            // пан/зум содержимого
    ui_scale:  f32,               // ЛОКАЛЬНЫЙ масштаб интерфейса
}
```

**Стыковка с Masonry.** Дерево сплитов — наша структура; каждая `Area` держит
`WidgetId` корня своего поддерева в общем `RenderRoot`. Layout области выполняется
через `Dim::Fixed` по посчитанным нами прямоугольникам — то есть Masonry не
пересчитывает раскладку сплитов, он получает готовые размеры. Каждый корень области
помечается `PaintLayerMode::IsolatedScene` (§7.3), чтобы получить свой `VisualLayer`.

**Бинарное дерево против графа вершин и рёбер.** Blender использует граф, чтобы при
ресайзе выравнивались границы областей, не находящихся в отношении родитель/потомок.
Бинарное дерево этого не умеет, но проще на порядок. Рекомендация: начать с дерева,
спрятав операции за интерфейсом менеджера; если выравнивание понадобится — заменить
реализацию, не трогая остальной код.

Операции: `split`, `join` (только совместимые соседи), `swap`, `maximize/restore`,
drag границы, drag угла, detach в отдельное ОС-окно (в `masonry_winit` мульти-окно
уже есть). Дерево сериализуемо → workspaces сохраняются в файл.

## 9. Масштабирование в разных фреймах

Три независимых множителя, которые нельзя смешивать:

1. **`device_scale`** — HiDPI окна, от ОС. Влияет на размер целевой текстуры.
   В Masonry — `global_state.scale_factor`, один на окно.
2. **`ui_scale`** — пользовательский размер интерфейса, **свой у каждого региона**.
   Влияет на **layout**: кегль, паддинги, размеры контролов.
3. **`view`** — пан/зум содержимого канваса. **Не влияет на layout вообще** —
   чистый трансформ при композиции.

```rust
let layout_scale = device_scale * region.ui_scale;   // → в Length/Dim и в текст
let paint_xform  = region.view;                      // → в VisualLayer::transform
```

Критично: (2) идёт в layout, (3) — только в paint. Смешать их — значит перезапускать
layout на каждый кадр зума. Это ровно та ошибка, которая убивает производительность
нод-редакторов.

**Чего нет в апстриме.** У Masonry один scale factor на окно. Визуальную часть
даёт `WidgetState::transform`, но выбор кегля и метрики паддингов надо протаскивать
самим. Механизм: `ui_scale` региона — свойство в масонриевской системе свойств,
наследуемое вниз по поддереву; `Length` вычисляется из логических единиц с его учётом.
Система `PropertyArena` + `property_changed` для этого и предназначена — при смене
`ui_scale` региона поддерево получает инвалидацию штатным путём.

Поскольку `imaging` растеризует из кривых с учётом финального трансформа, изменение
любого из трёх множителей корректно без перекодирования сцены и без потери резкости.
Этого нет ни у атласных рендеров (gpui), ни у CPU-тесселяторов (egui/lyon).

## 10. `blazy-canvas`: контролы на нодах

### 10.1 Почему не `masonry::widgets::Canvas`

`Canvas` в Masonry — painter-callback: он держит `imaging::record::Scene`, которую
приложение перерисовывает через `update_scene`, и **не имеет детей**. Для графа нод,
внутри которых живут слайдеры и чекбоксы, он не годится принципиально.

### 10.2 Контейнер

```rust
pub struct CanvasLayer {
    view:     Affine,                 // пан/зум
    index:    RTree<WidgetId>,        // spatial index в координатах канваса
    children: Vec<CanvasChild>,       // { pod, canvas_pos, bbox }
    visible:  Vec<WidgetId>,          // результат culling за прошлый кадр
}
```

**Layout.** Не осевая раскладка, а свободное размещение: позиция ребёнка берётся из
модели графа, размер — `Dim::Fixed` там, где он известен, `Auto` только для нод с
динамическим содержимым. `place_child` в координатах канваса.

**Culling.** `index.query(view.inverse() * viewport_rect)` перед layout и paint.

> **ИСПРАВЛЕНО и РЕАЛИЗОВАНО по результатам Фазы 0.** Здесь было написано:
> «невидимые дети помечаются `is_stashed` — Masonry их не красит и не добавляет в
> сцену слоя». Это верно, но недостаточно: `set_stashed` **не убирает ноду из
> рекурсии проходов**, и стоимость кадра оставалась линейной по общему числу нод.
> Работает **виртуализация**: нода вне вида удаляется из дерева, а её состояние
> живёт в модели графа. Реализовано в `blazy-canvas` (§20.3), тезис «10k нод при
> 40 видимых должны стоить как 40» подтверждён замерами (§20.6).

**Пан и зум.** Меняется только `view` → `WidgetState::transform` корня слоя →
`request_compose`. Ни layout, ни перекодирование сцен детей не запускаются. Это
главный выигрыш от связки retained-дерево + векторный IR.

**События.** Точка указателя переводится `view.inverse() * p` перед спуском в детей.
Masonry уже делает это для своих трансформов (`window_transform`), так что обычные
виджеты работают внутри нод **без единой правки** — слайдеры, чекбоксы, комбо-боксы,
поля ввода. Именно этого не хватает большинству нод-редакторов.

### 10.3 LOD

```rust
pub enum Detail { Full, Simplified, Box }

fn detail(scale: f32) -> Detail {
    if scale > 0.6  { Detail::Full }        // все контролы
    else if scale > 0.25 { Detail::Simplified } // заголовок и сокеты
    else { Detail::Box }                     // цветной прямоугольник
}
```

Двойной выигрыш: меньше команд в сцене и — важнее — в режиме `Box` содержимое ноды
не измеряется и не раскладывается вовсе (§5.2).

### 10.4 Связи

Не виджеты, а отдельный слой кривых: кубические безье, батчатся в один
`Painter::stroke`-стрим, отдельная `record::Scene`, инвалидируемая только при
изменении топологии или движении концевых нод. Хит-тест — по расстоянию до кривой
(`blazy-shape`, `HitMode::Stroke`).

## 11. `blazy-ops`: операторы, keymap, модальность

Самое ценное, что есть у Blender архитектурно, и чего нет ни в одном Rust-тулките.

```rust
pub trait Operator {
    fn poll(&self, cx: &Context) -> bool;                 // доступен ли сейчас
    fn invoke(&mut self, cx: &mut Context) -> OpResult;   // запуск из UI
    fn exec(&mut self, cx: &mut Context) -> OpResult;     // запуск из скрипта / redo
    fn modal(&mut self, ev: &Event, cx: &mut Context) -> OpResult { OpResult::Finished }
}

pub enum OpResult { Running, Finished, Cancelled, PassThrough }
```

Одна точка для undo/redo, меню, горячих клавиш, скриптинга, тестов и записи макросов.
Меню и keymap ссылаются на операторы по имени, а не хранят замыкания.

**Keymap — данные, а не код:** `(context, event_pattern) -> (operator, props)`.
Контексты вложены: Window → Screen → Area → Region → активный модальный оператор.
Пользовательские переопределения — ещё один слой поверх. Сериализуемо.

**Модальность.** Стек модальных обработчиков на регион. Оператор трансформации
(перетаскивание ноды, ресайз сплита, box-select) захватывает ввод и получает все
события до `Finished`/`Cancelled`, с возможностью `PassThrough`. Это чище, чем
разбрасывать `is_dragging: bool` по виджетам.

**Стыковка с Masonry.** Обычная маршрутизация (`on_pointer_event`, `on_text_event`,
bubbling, focus) остаётся масонриевской. Действия виджетов (`Widget::Action`,
`on_action`) транслируются в вызовы операторов — так кнопка в тулбаре и горячая
клавиша идут одним путём и одинаково попадают в undo.

> **Поправка по §38.** Здесь стояло, что `blazy-ops` сидит **выше** маршрутизации и
> перехватывает событие до спуска в дерево. Замерено — мест три, и ни одно не делает всю
> работу: `Layer::capture_pointer_event` видит каждое событие раньше дерева и не умеет его
> удержать, захват указателя удерживает и выдаётся только на нажатие, а хост (цикл окна —
> наш с §26) может не пропустить ничего, но не знает, что под курсором, без
> `RenderRoot::edit_widget`. Поэтому состояние слоя живёт в обычном объекте `OpRuntime<W>`,
> а место — это то, чем драйвер его кормит (`Seat`). Числа и следствия — §38.

## 13. Многопоточность

`imaging::record::Scene` — владеющее значение с реплеем, а не граф объектов с `&mut`.
Значит `VisualLayerPlan` можно передать в рендер-поток и там реплеить в бэкенд, пока
UI-поток считает следующий кадр.

```
UI thread    : события → операторы → layout → compose → paint (Painter → record::Scene)
                  │ VisualLayerPlan (значение), double buffer
Render thread: replay_into(backend) → GPU submit → present
Workers      : shaping, декодирование картинок, вычисления редакторов
```

Оговорка: в текущем `masonry_winit` рендер синхронный, в том же потоке. Разнос по
потокам — наша работа в `blazy-shell`, и делать её надо после уровня B, не раньше:
без разбиения на слои переносить в другой поток нечего.

## 14. Встраивание в движки

Требования к guest mode и их текущий статус:

| Требование | Статус |
|---|---|
| Не владеть Device/Queue/Surface/окном | ✅ `ImagingRenderTarget` принимает чужие |
| Не создавать свой event loop | ✅ `RenderRoot` — просто объект, ввод подаётся снаружи |
| Нормализованные события, не типы winit | ✅ `ui-events` |
| Рендер в переданную текстуру | ✅ `render_to_texture` |
| Дыры под содержимое хоста | ⚠️ модель есть (`External`), реализации в хосте нет |
| Бэкенд без wgpu | ✅ `imaging_skia`, `imaging_tiny_skia`, `vello_cpu` |
| Явный контракт по времени | ⚠️ `redraw()` есть, политика пробуждения — за хостом |

`blazy-shell` даёт два режима:
1. **Owner** — свои окна через `masonry_winit` (или свой аналог на `ui-events`).
2. **Guest** — движок отдаёт `Device`/`Queue`/`TextureView` и подаёт события;
   blazy кладёт команды в чужой командный буфер и возвращает список `External`-дыр,
   которые движок заполняет сам.

Для движка со своим GL/Vulkan и без wgpu путь — свой `PaintSink`/`ImageRenderer`
с тесселяцией в треугольники и атласом глифов. Медленнее, но `imaging` это допускает
by design, и писать придётся только бэкенд, а не тулкит.

Опубликованный `masonry_core` 0.4.0 старше миграции на `imaging` на пять месяцев.
Всё, на чём построен этот документ, живёт **только в git-main**.

**Следствие:** зависимость от `masonry_core` и `imaging` будет git-зависимостью с
пиннингом по коммиту, с ручными обновлениями и регулярными поломками API. Для
приложения это терпимо. Для публикуемой библиотеки — это транслируется пользователям.

Смягчение:
* пиннинг по коммиту, обновление осознанными подходами, не «раз в неделю»;
* тонкий фасадный слой в `blazy-core` над теми местами Masonry, которые мы дёргаем
  чаще всего, чтобы поломка API правилась в одном месте;
* golden-image тесты через `imaging_tiny_skia` / `vello_cpu` — детерминированный
  CPU-бэкенд позволяет ловить регрессии после каждого обновления апстрима;
* контрибьютить то, что нам нужно (§7.3), а не форкать.

### 15.2 Критический путь вне нашего контроля

Blender-подобный UI нагружает нетипичные места: тысячи виджетов под одним трансформом,
per-region scale, произвольные хит-формы, damage. Это ровно те места, где Masonry
менее всего обкатан. Значит — регулярные апстрим-issue на критическом пути и
готовность самим присылать патчи.

### 15.3 Почему не `xilem` (view-слой)

`masonry_core` работает и без него. Причины отложить:
* тяжёлые дженерики и время компиляции;
* динамический контент требует `AnyView` с боксингом; граф из тысяч разнородных
  нод упрётся в это повсеместно;
* для нод-редактора реактивность всё равно своя — она следует из модели графа,
  а не из дерева view.

Это не приговор: когда ядро blazy устоится, поверх можно сделать декларативный слой
(свой или xilem'овский) как **удобство, а не фундамент**. Если начать с него,
его абстракции протекут вниз и заблокируют встраивание в движки со своей реактивностью.

## 18. Итог

`imaging` + `masonry_core` закрывают три из четырёх ключевых требований: сменный
рендер с шестью бэкендами, retained-дерево со стабильными ID и точечной инвалидацией,
дыры под содержимое хоста. Плюс бесплатно — parley, AccessKit, система свойств,
развязка с winit, мульти-окно.

Остаётся то, ради чего blazy и затевается: **система областей Blender, нод-канвас с
обычными виджетами внутри нод, операторы с keymap** — и один инженерно тяжёлый
пункт, **per-area композиция**, потому что кэш сцен в Masonry экономит вызов `paint()`,
но не пересборку сцены слоя (§7.2). Последнее — правильное место для контрибьюта,
а не для обхода.

Цена решения — жизнь на git-main двух молодых крейтов и участие в чужом API-churn.
Альтернатива — написать всё это самим и потратить годы на догон. Для приложения
выбор очевиден; для публикуемой библиотеки его надо принимать сознательно, с
фасадным слоем и golden-тестами как страховкой.

Фаза 0 из §16 существует именно затем, чтобы этот выбор был основан на замерах,
а не на этом документе.

## 20. Результаты Фазы 0 (замерено)

Прототип из §16 собран и измерен: `examples/node-canvas`, поверх
`masonry_core` на коммите `ce7b04d`. Запуск:

```
cargo make run-node-canvas   # интерактивное окно
cargo make bench-canvas      # замеры headless
```

Замеряется работа самого Masonry — маршрутизация событий, rewrite-проходы и
кодирование `VisualLayerPlan` через `TestHarness::redraw()`. Отправка на GPU
намеренно вне измерения: никакой выбор бэкенда не спасёт архитектуру, которая
перекладывает 5000 нод на каждый пан.

### 20.1 Что подтвердилось

5000 нод, вьюпорт 1100×750, 120 кадров на сценарий, 27 нод в кадре:

| Сценарий | мс/кадр | худший | layout детей/кадр |
|---|---:|---:|---:|
| idle | 6.79 | 8.72 | 0.0 |
| пан | 21.05 | 30.08 | 0.0 |
| зум | 21.47 | 35.43 | 3.5 |
| перетаскивание одной ноды | 13.68 | 17.23 | 0.0 |
| наведение мыши | 7.48 | 11.76 | 0.0 |

Три исходных тезиса held:

1. **Пан и зум не перезапускают layout детей.** `0.0` вызовов `layout` на кадр при
   пане: `run_layout_on` рано выходит для каждого чистого ребёнка неизменного
   размера. Разделение «`ui_scale` → в layout, `view` → только в paint» (§9)
   работает ровно так, как задумано.
2. **Перетаскивание одной ноды не трогает остальные.** Тоже `0.0`: меняется только
   позиция, `place_child` не требует перелейаута. Сцены соседей не перекодируются.
3. **Обычные виджеты работают внутри нод.** Слайдеры и чекбоксы Masonry живут внутри
   зумируемых нод без единой правки — Masonry инвертирует `window_transform` сам.
   `CanvasLayer` даже не знает об их существовании: он смотрит `ctx.is_handled()`
   и не мешает.

Culling работает: 27 из 5000 нод в кадре.

### 20.2 Что опровергнуто — главный результат

**Стоимость кадра линейна по общему числу нод и не зависит от числа видимых.**

Развёртка при фиксированном видимом наборе (~27 нод):

| Всего нод | Видимо | idle | пан | мкс/нода/кадр |
|---:|---:|---:|---:|---:|
| 250 | 24 | 0.22 | 0.81 | 3.25 |
| 1 000 | 27 | 0.73 | 2.89 | 2.89 |
| 4 000 | 27 | 5.05 | 16.21 | 4.05 |
| 16 000 | 27 | 21.11 | 66.29 | 4.14 |

64× нод → 81× времени при неизменной видимой части. Подтверждение с другой стороны:
сценарий «пан на Box-LOD» с **280** видимыми нодами стоит те же 20.9 мс, что и пан
с 27 видимыми. Видимый набор на стоимость кадра не влияет вообще.

**Причина — в двух местах `masonry_core`:**

1. `passes/paint.rs` рекурсирует по **всем** детям, включая stashed, и это сделано
   намеренно:
   > *«Note: At this point we could short-circuit if is_stashed is true, but we
   > deliberately avoid doing that to avoid creating zombie flags.»*

2. `passes/compose.rs` рано выходит по `if !transformed && !state.needs_compose`,
   но `set_transform` на `CanvasContent` ставит `transform_changed`, а флаг
   `transformed` передаётся вниз по рекурсии. То есть **пан композитит всё дерево**.
   Отсюда пан ≈ 3× idle.

При 3 виджетах на ноду (тело + слайдер + чекбокс) 5000 нод — это 15 000 виджетов,
обходимых каждый кадр. ~1.3 мкс на виджет — это не «медленный код», это стоимость
обхода дерева как такового.

### 20.3 Следствие: виртуализация вместо culling — реализовано

`set_stashed` убирает ноду из отрисовки, хит-теста и дерева доступности — но **не из
рекурсии проходов**. Чтобы нода перестала стоить, она должна исчезнуть **из дерева**.

Именно так работает `masonry::widgets::virtual_scroll`. `blazy-canvas` переписан по
той же модели:

```rust
struct Slot {
    pos: Point,          // геометрия есть всегда
    size: Size,
    pod: Option<WidgetPod<dyn Widget>>,   // виджет — только пока нода в кадре
}

pub trait NodeSource: 'static {
    fn build(&mut self, index: usize) -> NewWidget<dyn Widget>;
}
```

Ключевые решения:

* **Модель — источник истины.** Виджет ноды существует только пока нода видна, значит
  состояние в нём жить не может. `GraphNode` пишет изменения слайдера и чекбокса
  обратно в модель через `on_action`, а `build` читает из модели актуальное состояние.
  Это не обходной путь, а правильная схема для редактора: граф переживает любое
  представление и должен сохраняться, откатываться и скриптоваться независимо.
* **Материализация в mutate-проходе.** Добавление и удаление детей требует
  `WidgetMut`, которого нет в layout. `cull()` считает нужный набор в layout и ставит
  `mutate_self_later`; mutate-проход идёт раньше layout внутри rewrite-цикла, поэтому
  вошедшая в кадр нода строится, раскладывается и рисуется в том же кадре.
* **Диффинг слиянием.** Оба списка индексов отсортированы, так что разница находится
  одним проходом без аллокаций и хеширования.
* **Геометрия отдельно от виджетов.** Граф на миллион нод стоит миллион пар
  `(Point, Size)`, а не миллион виджетов. `cull()` — линейный скан по этому массиву:
  32 байта на ноду, никакого состояния виджетов. Место для R-дерева, когда сам скан
  начнёт мешать.

### 20.4 Два бага, которые вскрылись только на тестах

Оба были в коде до виртуализации и оба тихо портили прежние замеры.

**1. Culling не перезапускался при пане.** `raw.set_transform(view)` ставит
`needs_compose`, но **не** `needs_layout`. Culling живёт в layout, поэтому
`CanvasContent::layout` рано выходил и видимый набор считался один раз при старте.
В таблицах §20.1 колонка «видимо» была статичной. На главный вывод это не влияло
(стоимость всё равно шла по общему числу нод), но culling был ещё бесполезнее, чем
показано. Лечится явным `raw.request_layout()` рядом с `set_transform`.

**2. Канвас крал pointer capture у контролов внутри нод.** `Checkbox` и `Slider` на
`Down` вызывают `ctx.capture_pointer()`, но **не** `ctx.set_handled()`. Канвас видел
«необработанное» событие и начинал перетаскивание ноды, перехватывая capture. То есть
тезис 3 из §20.1 держался только потому, что тест на него отсутствовал.

Правильный сигнал — не `is_handled()`, а цель захвата:

```rust
if ctx.pointer_capture_target_id().is_some_and(|id| id != ctx.widget_id()) {
    return;
}
```

Это стоит запомнить как общее правило для контейнеров с drag-логикой: **`is_handled`
не является признаком того, что ребёнок занят вводом.**

Тесты на это есть: `examples/node-canvas/src/tests.rs`, пять штук — материализация
ограничена вьюпортом и не зависит от размера графа, нода уходит из дерева при пане,
состояние переживает круг «ушла — вернулась», контролы пишут в модель.

| зум | 21.47 мс | **0.623 мс** | 34× |
| перетаскивание ноды | 13.68 мс | **0.251 мс** | 54× |
| наведение мыши | 7.48 мс | **0.196 мс** | 38× |

Развёртка по размеру графа — то, ради чего всё делалось:

| Всего нод | Живых виджетов | idle | пан |
|---:|---:|---:|---:|
| 250 | 28 | 0.086 мс | 0.507 мс |
| 1 000 | 35 | 0.089 мс | 0.496 мс |
| 4 000 | 35 | 0.100 мс | 0.507 мс |
| 16 000 | 35 | 0.079 мс | 0.577 мс |

**64× нод → 1.1× времени.** Стоимость кадра определяется вьюпортом, а не графом.
Проверено и на 20 000 нод: idle 0.086 мс, пан 0.627 мс. Прежняя оценка потолка
(«как нынешние 250 нод») подтвердилась и оказалась даже консервативной.

Все критерии Фазы 0 пройдены:

```
[pass] панорамирование не перекладывает видимый набор   (0.2 layout/кадр против 34 видимых)
[pass] перетаскивание одной ноды перекладывает ~одну    (0.0 layout/кадр)
[pass] culling держит видимый набор малым               (34 из 5000)
[pass] стоимость кадра не зависит от размера графа      (64× нод → 1.1× времени)
```

### 20.6 Дальнее поле: когда виден весь граф

Виртуализация ограничивает стоимость кадра **видимым** набором. Если отдалить вид так,
что виден весь граф, ограничение исчезает по определению — видимый набор и есть граф.
Замер это подтвердил: пан при полностью отдалённом виде стоил **43.2 мс** при 4160
материализованных нодах.

Разложение по вкладам (пан на 0.02 px, чтобы ничего не входило и не выходило из кадра):
при `builds/frame = 0.0` и `child-layouts/frame = 0.0` кадр всё равно стоил 28.8 мс на
2970 нодах. То есть пересборка виджетов давала ~7%, а остальное — **тот же обход
дерева**, что и в §20.2: 2970 нод × 3 виджета (тело плюс сташенные слайдер и чекбокс)
≈ 8900 виджетов по ~3.2 мкс каждый.

**Решение — не материализовать вовсе.** Нода в несколько пикселей не нуждается ни в
layout, ни в хит-тесте, ни в маршруте событий, ни в узле доступности. Ей нужен
закрашенный прямоугольник. Ниже порога `Detail::Box` канвас перестаёт строить виджеты
и рисует ноды сам, одним проходом, в собственную сцену:

```rust
pub trait NodeSource: 'static {
    fn build(&mut self, index: usize) -> NewWidget<dyn Widget>;

    /// Рисует ноду, которая слишком мала, чтобы заслуживать виджет.
    fn paint_far(&mut self, index: usize, rect: Rect, painter: &mut Painter<'_>) {}
}
```

Сцена дальнего поля кодируется в **координатах канваса**, поэтому пан и зум
переиспользуют её через трансформ слоя без перекодирования — тот самый выигрыш от
векторного IR, о котором §1. Перерисовка нужна только когда меняется состав видимого
набора. Хит-тест переведён с `live` на `visible`, так что ноды остаются
перетаскиваемыми и без виджетов.

| Сценарий (5000 нод) | было | стало |
|---|---:|---:|
| пан на Box-LOD | 4.70 мс | **0.220 мс** |
| пан, виден весь граф | 43.23 мс | **1.615 мс** |

На 20 000 нод: 0.350 мс и 1.951 мс. Дальнее поле — единственное место, где стоимость
всё ещё растёт с размером графа, и растёт правильно: это O(видимых прямоугольников),
а прямоугольник стоит наносекунды против микросекунд у виджета.

**Тест, без которого этого раздела бы не было.** Первая версия дала 0.141 мс — и была
сломана: `paint` не вызывался вообще, потому что правка молча не применилась. Ничего не
рисовать очень быстро. Поэтому в наборе есть `far_field_is_actually_painted`: он
рендерит кадр в изображение и считает пиксели ярче фона. Это единственная проверка,
которую нельзя удовлетворить бездействием.

### 20.6a Дальнее поле не перерисовывается при пане

Первая версия дальнего поля перекодировала сцену **каждый кадр** панорамирования, и
это съедало большую часть выигрыша. Два независимых виновника.

**1. Сцена рисовалась ровно по вьюпорту.** Стоило одной ноде войти в кадр — и
перекодировались все несколько тысяч. Теперь сцена записывается для области с запасом
(`OVERSCAN = 0.5`, то есть полвьюпорта в каждую сторону) и переиспользуется, пока
вьюпорт из неё не вышел. Сцена лежит в **координатах канваса**, поэтому пан и зум
внутри области — это одна `Affine` и ничего больше. Ровно то свойство векторного
display list, ради которого §1 и выбирался Vello.

**2. Masonry помечает на перерисовку всё, у чего выполнился `layout`.** В
`passes/layout.rs` стоит безусловное `state.request_paint = true` с честным
комментарием апстрима:

> *«TODO - Not everything that has been re-laid out needs to be repainted.»*

А `CanvasContent` перелейаутился на каждый пан — потому что culling жил в его `layout`
и зависел от вида. То есть даже с валидной областью сцена всё равно перезаписывалась.

Лечение — перенести culling в `CanvasLayer`, где и живут вид с вьюпортом. Содержимое
теперь **не перелейаутится при смене вида вообще**: позиции детей заданы в координатах
канваса, вид на них не влияет, всю работу делает трансформ. `CanvasLayer` пишет
результаты culling в содержимое через `get_raw_mut` и запрашивает у него layout только
когда реально меняется состав виджетов.

Побочный эффект: это ускорило и ближние режимы, где на каждый пан впустую
переставлялись все живые ноды.

| Панорамирование (5000 нод) | до §20.6a | после |
|---|---:|---:|
| виден весь граф (Box) | 1.388 мс | **0.563 мс** |
| зум 0.11 (792 ноды) | 1.784 мс | **1.612 мс** |
| зум 0.15 (741 нода) | 1.461 мс | **1.447 мс** |
| зум 1.0 (34 ноды, Full) | 0.136 мс | **0.133 мс** |

Перерисовок дальнего поля при пане: **0.00 на кадр** (было 1.00). Есть счётчик
`CanvasStats::far_repaints` и тест `far_field_does_not_repaint_while_panning`.

**Что осталось нерешаемым на нашей стороне.** Сцена всё равно вклеивается в сцену слоя
каждый кадр — это §7.2, `append_transformed` в paint-проходе. Поэтому стоимость кадра
в дальнем поле остаётся O(нарисованных команд), и запас области её увеличивает. Отсюда
и предел: убрать перекодирование мы можем, убрать вклейку — нет. Это второй аргумент за
пропуск неизменившихся поддеревьев в paint-проходе (§17).

### 20.7 LOD: не «рисовать проще», а «не строить виджеты»

До виртуализации LOD давал 21.05 против 20.90 мс — шум, потому что экономил команды
отрисовки, а обход дерева от него не зависел.

Теперь оба уровня определены структурно, а не косметически:

* **`Box`** — виджетов нет вовсе, канвас рисует ноды сам (§20.6).
* **`Simplified`** — нода есть, но **без контролов**. Это оказалось необходимым, а не
  желательным: на зуме 0.11 нода шириной ~50 px несла `GraphNode` + `Slider` +
  `Checkbox` + вложенный в чекбокс `Label`, то есть **4 виджета**, из которых три
  нельзя нажать. 792 ноды × 4 = 3168 виджетов, 6.8 мс на кадр, худший 9.9 мс —
  видимые рывки при панорамировании.

Сташить их было недостаточно ровно по §20.2. Поэтому уровень детализации теперь
передаётся в момент постройки:

```rust
fn build(&mut self, index: usize, detail: Detail) -> NewWidget<dyn Widget>;
```

Пересечение порога Full/Simplified — это **пересборка** живых нод, а не перерисовка;
`CanvasContent` отслеживает `built_detail` и выставляет `rebuild`. Пороги пересекаются
редко, так что O(видимых) пересборка здесь — правильный размен. Значения слайдера и
чекбокса при этом рисуются двумя прямоугольниками: две команды отрисовки вместо трёх
виджетов.

| Панорамирование (5000 нод) | было | стало |
|---|---:|---:|
| зум 0.11 (792 ноды, Simplified) | 6.82 мс / худший 9.94 | **2.05 мс** / худший 3.5 |
| зум 0.15 (741 нода, Simplified) | 4.56 мс / худший 8.05 | **1.71 мс** / худший 3.9 |

**Осторожно с порогами.** `Detail::for_scale` сейчас переключается на 0.3 и 0.1.
Полоса 0.1–0.3 — самый невыгодный участок кривой: виджеты ещё строятся, а видна уже
большая часть графа. Если поднять порог дальнего поля, эта полоса сузится. Числа выше
получены при 0.3/0.1.

### 20.7a Full: контролы только у ноды под курсором — измерено и отключено

Идея: пользователь в любой момент работает с одной нодой, а платит за все. При 140
нодах в кадре это 560 виджетов, из которых 557 никто не трогает. Уровень детализации
делается свойством **ноды**, а не канваса:

```rust
fn effective_detail(&self, index: usize) -> Detail {
    let global = self.detail.unwrap_or(Detail::Full);
    if !self.controls_on_hover || global == Detail::Box { return global; }
    if self.active == Some(index) { Detail::Full } else { Detail::Simplified }
}
```

Выигрыш реальный и крупный: панорамирование на зуме 0.40 (140 нод) — **1.40 мс против
0.35 мс**, вчетверо.

**Но по умолчанию выключено.** На практике оказалось, что нарисованная заглушка
недостаточно похожа на темизированные `Slider` и `Checkbox` из Masonry: подмена в
момент наведения читается как изменение интерфейса под курсором. Дорисовать сходство
вручную можно, но это хрупко — смена темы молча ломает совпадение, а тема живёт в
апстриме.

Приём остался как `CanvasLayer::with_controls_on_hover(true)` и как отдельный сценарий
бенчмарка, чтобы цена решения оставалась числом, а не воспоминанием. Он уместен там,
где тело ноды рисует само приложение (тогда заглушка и «настоящий» вид — один и тот же
код), или где ноды достаточно мелкие, чтобы разница не читалась.

**Что осталось от этой работы полезного независимо от флага:**

* `Slot` помнит, на каком уровне собран виджет — своём и глобальном. Устаревание при
  смене уровня ловится общим механизмом, отдельный проход `set_detail` не нужен.
* Проверка устаревания идёт только когда детализация действительно менялась; при
  обычном панорамировании она пропускается целиком.
* `CanvasDetail` несёт **глобальный** уровень, а аргумент `build` — уровень самой
  ноды. Это разделение нужно, чтобы заглушка могла масштабировать свою детальность:
  при `Simplified` нод сотни, и каждая лишняя команда отрисовки умножается на их
  число. Скруглённые прямоугольники и окружность в заглушке стоили +0.4 мс при 741
  ноде — больше, чем экономил весь приём на этом масштабе.

Последний пункт стоит запомнить отдельно: **в канвасе стоимость команды отрисовки
всегда умножается на число видимых нод**, потому что сцена каждой ноды вклеивается в
сцену слоя каждый кадр (§7.2).

### 20.7b Ревью и чистка

После серии оптимизаций код прошёл ревью на читаемость. Главное, что нашлось, —
**четыре пары почти-одинаковых методов**: у каждой операции канваса была версия для
`WidgetMut` (публичный API) и версия для `EventCtx` (обработчик указателя). Они
отличались только тем, кому сообщать об инвалидации, — и уже успели разойтись:
`move_child` не сбрасывала регион дальнего поля, а `move_child_at` сбрасывала.
Математика зума была скопирована дословно.

Лечение — маленький тип `Invalidate` и трейт `Invalidator` над `MutateCtx`/`RawCtx`:
операция пишется один раз против `&mut self` и возвращает, что нужно перезапросить.
Чистый `zoomed_view` убрал дублирование арифметики.

Прочее из того же захода:

* Слияние двух отсортированных списков вынесено в `diff_sorted` — теперь оно
  покрыто юнит-тестами, чего через `TestHarness` сделать было нельзя. Буферы
  переиспользуются, так что пан не аллоцирует.
* Пять `Cell<u64>` убраны: все счётчики меняются из `&mut self`.
* `CanvasStats::visible` переименовано в `materialised` — оно и означало «сколько
  виджетов в дереве», а в дальнем поле показывало ноль при полном экране нод.
  Счётчики выделены в `CanvasCounters` с явной оговоркой, что `far_repaints` отстаёт
  на кадр (он инкрементится в paint, а снимок берётся в layout).
* Состояние дальнего поля собрано в `FarField` — инварианты вида «`nodes` осмысленны
  только когда `region` есть» стали видны в типах.
* Удалён мёртвый публичный API: `CanvasItem`, `view()`, `to_canvas`, `child_at`.
  Последний заодно был ловушкой — сканировал все слоты, тогда как `hit_child` только
  видимые.

**Пороги детализации и пределы зума переехали в настройки канваса**
(`DetailThresholds`, `with_zoom_limits`, `with_overscan`). Это не косметика: чтобы
поменять пороги, приходилось править исходник библиотеки — верный признак, что
политика оказалась не на своём уровне.

**Одна находка была настоящим багом.** `cull_margin` задавался в **канвасных**
единицах (128), то есть при зуме 8 давал 1024 экранных пикселя запаса, а при 0.02 —
два с половиной. Размерность перепутана: запас — понятие экранное. Перевод в долю
вьюпорта это исправил, но сначала стоил 40% на малых зумах: доля 0.15 материализовала
1058 нод вместо 741. Пришлось подбирать по замерам — 0.02 даёт тот же охват, что
прежние 128 единиц на рабочих зумах, и ведёт себя правильно на краях. Запас можно
делать малым потому, что вошедшая в кадр нода собирается в mutate-проходе и
раскладывается в том же кадре: он покупает плавность при быстром перетаскивании, а не
корректность.

Производительность после всей чистки — на уровне базы или лучше:

| Сценарий | до ревью | после |
|---|---:|---:|
| пан (34 ноды) | 0.441 мс | **0.324 мс** |
| зум (жест) | 0.550 мс | **0.490 мс** |
| зум 0.11 | 1.867 мс | **1.697 мс** |
| зум 0.40 | 1.536 мс | **1.446 мс** |
| перетаскивание | 0.141 мс | **0.127 мс** |

Тестов стало 20: 13 интеграционных в примере и 7 юнит-тестов в `blazy-canvas`.

### 20.8 Вердикт по Фазе 0

**Masonry берём.** Единственная серьёзная проблема — обход дерева — решена целиком на
нашей стороне: без форка, без патчей в апстрим и без единого `unsafe`. Всё остальное,
ради чего Masonry выбирался (абстракция рендера, retained-дерево, трансформы, система
свойств, маршрутизация событий), отработало как заявлено.

Что меняется в плане §16:

* **`blazy-canvas` уже виртуализирован** — пункт 10 плана закрыт в части архитектуры,
  осталась предметная часть (spatial index, слой связей, выделение, сериализация).
* **Виртуализация нужна не только канвасу.** Обход дерева — стоимость *на окно*, и
  любой редактор с длинным списком (аутлайнер, таймлайн, кривые) упрётся в то же самое.
  `masonry::widgets::virtual_scroll` покрывает списки; для нерегулярных раскладок
  образцом теперь служит `blazy-canvas`.
* **Уровень B (§7.3) стал менее срочным, но не отменился.** Он экономит перекодирование
  сцены между областями, а не обход дерева; после виртуализации это уже оптимизация,
  а не спасение.
* **Бенчмарк — в CI.** Развёртка по числу нод ловит регрессию всей архитектуры одним
  числом. Сделано — §20.9.
* **Дальнее поле — обязательная часть канваса, а не оптимизация** (§20.6). Любой
  редактор с обзорным масштабом (таймлайн, кривые, аутлайнер свёрнутый) нуждается в
  том же: ниже порога читаемости рисовать данные, а не строить виджеты.
* **Промежуточный LOD переделан на удаление контролов, а не сташивание** (§20.7).
  Общее правило, которое стоит вынести за пределы канваса: уровень детализации — это
  решение о том, *какие виджеты строить*, а не о том, как их рисовать.

Что стоит попробовать протолкнуть в апстрим (в дополнение к §17): пропуск stashed-
поддеревьев в paint-проходе. Комментарий про «zombie flags» описывает решаемую
проблему, а не фундаментальное ограничение — при unstash флаги и так сбрасываются
(`state.set_needs_layout(true)` и компания в `update_stashed`). Это сделало бы
`set_stashed` пригодным там, где виртуализация избыточна.

### 20.9 Критерии Фазы 0 как гейт CI

Вердикт §20.8 держится на числах, которые до сих пор надо было получать вручную и
читать глазами. Это ровно та форма знания, которая тихо протухает: код меняется,
никто не перезапускает замеры, и через полгода «критерии Фазы 0 пройдены» означает
«были пройдены когда-то». Поэтому критерии переписаны как проверяемые утверждения
(`crates/bench-utils/src/criteria.rs`), прогон возвращает ненулевой код при
провале, а `cargo make ci` (lint + тесты + критерии) гоняется на каждый push.

**Гейтятся счётчики, не миллисекунды.** Это главное решение, и оно не про удобство.
Счётчик (`child_layouts/frame`, число материализованных виджетов, число перезаписей
дальнего поля) детерминирован: на ноутбуке и на shared-раннере GitHub он один и тот
же, поэтому порог на нём либо держится, либо сообщает о настоящей регрессии.
Стенные миллисекунды на общем раннере гуляют в разы — любой честный порог на них
пришлось бы задрать так широко, что он перестанет что-либо ловить, а любой узкий
начнёт падать случайно и через месяц будет отключён. Времена печатаются и
складываются в JSON-отчёт (тренд важен), но границей не служат никогда.

Исключение одно: «стоимость кадра не следует за размером графа» — утверждение про
время, счётчиком его не переформулировать. Оно остаётся гейтом, потому что сравнивает
два времени, измеренных в одном процессе, и потому что запас огромен: измеренные 1.1×
против границы в половину отношения числа нод, то есть 32× на полной развёртке. Шум
раннера такой разрыв не покрывает. Рядом с ним стоит счётчиковый двойник —
«материализованный набор не растёт с графом» — с жёстким порогом; он поймал бы ту же
регрессию на кадр раньше.

Список гейтов:

| Критерий | Замерено | Граница |
|---|---:|---:|
| пан не перекладывает видимый набор | 0.15 | < 12 layout/кадр |
| перетаскивание одной ноды перекладывает ~одну | 0.0 | < 4 layout/кадр |
| culling держит живой набор малым | 24 | < 1250 виджетов |
| дальнее поле не перезаписывается при пане (§20.6a) | 0.03 | < 0.2 записей/кадр |
| материализованный набор не растёт с графом | 24 | < 44 виджетов |
| стоимость кадра не следует за числом нод | 1.1× | < 32× |

Две детали, которые легко упустить и обе разобраны тестами в `criteria.rs`:

* **Пустой список критериев — провал, а не успех.** Иначе самый вероятный способ
  сделать CI зелёным — переименовать сценарий так, что `evaluate` перестанет его
  находить, — сработает молча.
* **Отчёт остаётся валидным JSON при делении на ноль кадров.** Голый `NaN` в файле
  стоил бы не одного числа, а всего архива за прогон.

**Что не подтвердилось при реализации.** §20.8 предполагал, что для CI придётся брать
сокращённый набор сценариев, потому что полный прогон «занимает минуты». Замер: полный
прогон — 0.87 с, сокращённый — 0.11 с. Экономить нечего, поэтому CI гоняет полный набор
и складывает более богатый отчёт; флаг `--quick` остался как быстрый цикл разработчика.

**Почему не `criterion` и не встроенный `#[bench]`.** Встроенный отпадает механически:
он требует `#![feature(test)]`, то есть nightly, который здесь нужен только для
`cargo fmt`. С `criterion` четыре причины, и первые две решают:

1. **Пять гейтов из шести — не время, а счётчики.** `criterion` меряет длительность
   замыкания; понятия «сколько раз пересчитался layout» у него нет. Вернуть счётчик,
   притворяющийся наносекундами, значит натравить бутстрап и отсев выбросов на целое
   число, которое либо 0, либо 34.
2. **`criterion` не роняет сборку.** При регрессии против baseline он печатает
   предупреждение и возвращает 0 ([issue #824](https://github.com/bheisler/criterion.rs/issues/824)).
   Гейт всё равно пришлось бы писать самим, поверх лишней зависимости.
3. **Его собственный FAQ не рекомендует CI**: виртуализация раннеров вносит слишком
   много шума, вместо этого предлагается Iai со счётчиком инструкций Cachegrind. Это
   ровно аргумент «гейтить счётчики, а не миллисекунды», только на уровне инструкций
   CPU вместо доменных счётчиков.
4. **Сценарии stateful.** `criterion` сам подбирает число итераций, целясь примерно в
   5 с измерения; при 0.5 мс на кадр это ~10 000 итераций. Пан идёт на −6 единиц по x
   за кадр, граф — 80 × 220 = 17 600 единиц в ширину, то есть после ~2900 итераций
   вьюпорт уходит с графа и меряется пан по пустоте. `iter_batched` с пересозданием
   харнесса это лечит, но построение графа на 16 000 нод дороже замеряемого кадра.

Если гейт по времени когда-нибудь понадобится, правильный инструмент — не `criterion`,
а `iai-callgrind`: счётчик инструкций детерминирован и на виртуализированном раннере,
то есть попадает в ту же категорию, что нынешние счётчики.

**Раскладка целей.** Замеры живут в `examples/node-canvas/benches/phase0/` с
`harness = false`, а пакет разделён на библиотеку и тонкий бинарь. Причина
принудительная: bench-цели — отдельные крейты и видят только библиотеку пакета, так
что при раскладке «один бинарь» генератор графа пришлось бы дублировать — ровно то
единственное, что у всех замеров обязано быть общим. Побочные выгоды: профиль `bench`
наследует `release`, поэтому оптимизацию не нужно помнить флагом; бенч-код не попадает
в бинарь окна; и вывод замеров больше не глушится `windows_subsystem = "windows"`,
который стоит только на окне.

## 21. Результаты Фазы 0.5 — области (замерено)

§20.8 закрыл Фазу 0 выводом «Masonry берём», но оставил открытым второй вопрос,
который тот же вывод и породил: раз стоимость кадра — это стоимость обхода дерева,
а дерево одно **на окно**, то что происходит, когда в одном окне живут шесть-восемь
редакторов сразу? Нод-канвас ушёл от линейности виртуализацией; экран Blender может
вернуть её обратно другим путём — через число областей.

Спайк: `crates/blazy-areas` плюс `examples/area-screen`, каждая область держит
нод-канвас над одним общим графом. Запуск:

```bash
cargo make run-area-screen
cargo make bench-areas
```

### 21.1 Устройство

Ровно тот шов, который просит §8: `SplitTree` — чистая геометрия, ничего не знающая
о виджетах, и `AreaScreen` — виджет Masonry, который кладёт по одному ребёнку на
область в тот прямоугольник, который посчитало дерево. Область получает
прямоугольник, а не размер, который она сама бы выбрала: «layout области выполняется
по посчитанным нами прямоугольникам, то есть Masonry не пересчитывает раскладку
сплитов». Дерево бинарное, а не граф вершин и рёбер — по рекомендации §8, с
операциями, спрятанными за типом, чтобы замена представления не задела остальное.

Ключевой счётчик — не «сколько детей Masonry считал грязными», а **сколько областей
получили размер, отличный от прошлого**. Причина в `passes/layout.rs`: `run_layout_on`
делает ранний выход при `!needs_layout() && layout_border_box_size == border_box_size`,
то есть ресайз — это ровно та половина условия, которой управляет экран. Вторая
половина, флаг грязноты, в отладочной сборке принудительно ставится всем детям (чтобы
проверить, что родитель их обошёл), поэтому гейтить по ней нельзя, а по ресайзам —
можно.

### 21.2 Что подтвердилось

**Области не складываются.** Развёртка при неизменном окне 1400×900 и одном графе:

| Областей | Живых виджетов | простой | пан в одной области |
|---:|---:|---:|---:|
| 1 | 35 | 0.104 мс | 0.450 мс |
| 2 | 40 | 0.116 мс | 0.427 мс |
| 4 | 45 | 0.161 мс | 0.320 мс |
| 8 | 48 | 0.170 мс | 0.293 мс |
| 16 | 49 | 0.163 мс | 0.254 мс |

Развёртка гоняется **без регионов**, по одному канвасу на область, и это осознанно:
с шапками больше областей означает больше полосок шапок, то есть меньше канваса, и
число живых виджетов падало бы по причине, не имеющей отношения к проверяемому
утверждению. Цена региона меряется отдельно (§22.3).

16× областей → 1.4× живых виджетов и 1.6× времени простоя. Разбиение окна не
добавляет содержимого, оно делит тот же вьюпорт; рост, который всё-таки есть, — это
ноды на границах, материализуемые по обе стороны, и запас у каждой области свой.
Пан внутри одной области с ростом числа областей **дешевеет**: область меньше, нод в
ней меньше.

Числа сценариев ниже сняты до появления регионов (§22), когда область держала один
канвас и ничего больше. В текущей сборке у каждой области есть ещё шапка, поэтому те
же сценарии дают другие миллисекунды и другое число живых виджетов — свежая таблица
в §22.3. Счётчики, на которых стоят критерии, не изменились: это и есть довод в
пользу того, чтобы гейтить их, а не время.

**Перетаскивание листового сплиттера меняет размер ровно двум областям** — 2.00
ресайза на кадр при 4, 8 и 16 областях. Это и критерий, и отдельный тест
(`dragging_a_leaf_splitter_resizes_two_areas`), сравнивающий счётчик экрана с
фактическими размерами детей: счётчик, которому нечем возразить, — плохой счётчик.

**Пан и простой не трогают раскладку областей вовсе** — 0.00 ресайзов на кадр.

### 21.3 Что оказалось интереснее ожидаемого

Корневой сплиттер — заведомо худший случай: он двигает границу между половинами
экрана, и наивно все области в обеих половинах должны пережить ресайз. Замерено:

| Областей | Ресайзов на кадр при корневом сплиттере |
|---:|---:|
| 4 | 4.00 |
| 8 | 4.10 |
| 16 | 8.20 |

С 8 областей — половина от наивного числа, и это не погрешность. Причина —
округление доли до целого пикселя в `split_rect`. Изменение ширины на 1 пиксель
доходит вниз по дереву до первого вложенного сплита **по той же оси**, где
`round(usable * ratio)` для первой колонки даёт то же целое, что и раньше, и вся
дельта достаётся второй. Осей две и они чередуются по глубине, поэтому начиная с
восьми областей ровно половина листьев остаётся нетронутой. Проверено на трёх точках
развёртки.

Важная оговорка: это свойство **плавного** перетаскивания по пикселю за кадр, а не
гарантия. Скачок на десятки пикселей изменит обе стороны. Округление здесь не
косметика — без него каждый кадр перетаскивания сдвигал бы все прямоугольники на
доли пикселя, все области считались бы изменившимися, и вместе с осмысленностью
замера пропала бы и экономия, ради которой он делается.

Ресайз окна пиксель за кадром стоит те же ~2 ресайза областей на кадр по той же
причине. Мгновенный ресайз на произвольную величину — нет; сценарий меряет
медленное перетаскивание рамки, то есть реалистичный случай.

### 21.4 Вердикт по Фазе 0.5

**Форма здорова.** Дерево сплитов над одним деревом виджетов не воспроизводит
проблему §20.2: стоимость по-прежнему определяется окном, а не числом сущностей в
нём. Отдельная подсистема с собственной структурой данных (§8) оправдала себя сразу:
счётчик ресайзов, на котором держатся три критерия из пяти, существует только потому,
что прямоугольники считаем мы, а не Masonry.

Что меняется в плане §16:

* **Пункт 4 (`blazy-areas`) разблокирован по архитектуре.** Осталась
  функциональность: join, maximize/restore, swap, отсоединение в отдельное окно,
  сериализация workspace. Ни одна из них не является риском — все они операции над
  деревом, которое уже есть и покрыто тестами.
* **Пункт 5 (`ui_scale` на регион) не начат и остаётся ближайшим неизвестным.**
  Регионов внутри области пока нет вообще. Механизм — свойство, наследуемое вниз по
  поддереву, — уже обкатан на `CanvasDetail` в Фазе 0, но на поддереве области не
  проверялся, и §9 предупреждает про самую дорогую ошибку в этом месте: смешать
  `ui_scale` (идёт в layout) с `view` (только в paint).
* **Уровень B (§7.3) по-прежнему не нужен.** Простой с шестнадцатью областями стоит
  0.14 мс. Per-area render-to-texture экономит перекодирование сцены между
  областями — на этих числах экономить нечего. Он вернётся в повестку, когда области
  начнут держать содержимое, которое дорого рисовать, а не дорого обходить.
* **Округление в раскладке — предметное решение, а не деталь.** Любая будущая
  раскладка областей должна давать целочисленные прямоугольники по той же причине.

### 21.5 Чего спайк не проверял

Регионы внутри области, `ui_scale`, `PaintLayerMode::IsolatedScene` на область
(§7.3), мульти-окно и отсоединение, сериализацию, выравнивание границ несоседних
областей (то, ради чего Blender использует граф, а не дерево). Разнородные редакторы
тоже: все области здесь держат один и тот же канвас, поэтому «стоимость области» —
это стоимость канваса, а не среднее по редакторам разной природы.

## 22. Результаты Фазы 0.6 — регионы и `ui_scale` (замерено)

§21.4 назвал `ui_scale` на регион ближайшим неизвестным и единственным оставшимся
пунктом критического пути, про который §9 говорит «в апстриме этого нет».

### 22.1 Разведка: что на самом деле даёт Masonry

Задача начиналась не с кода, а с вопроса «кто прочитает свойство на стороне
встроенных виджетов». Три находки, и вторая меняет формулировку §9.

**Layout целиком в логических пикселях; `scale_factor` в него не входит.** `Length` —
голый `f64`. `global_state.scale_factor` встречается ровно в трёх местах: перевод
позиции указателя physical → logical, перевод размера корня logical → physical в
конце layout-прохода, и трансформ в проходе доступности. Это хорошая новость для
модели §9 — `device_scale` действительно не трогает layout, — и плохая для
реализации: готового места, где логические длины умножаются на что-либо, не
существует.

**Наследования свойств нет.** §9 писал: «`ui_scale` региона — свойство в
масонриевской системе свойств, **наследуемое вниз по поддереву**». На коммите
`ce7b04d` это неверно. `PropertyStack` висит на самом виджете
(`state.property_stack_id`), а `Selector` умеет фильтровать по классам и по флагам
состояния виджета (`is_hovered`, `is_active`, `is_disabled`, `has_focus_target`) — по
предкам он не умеет ничего. Работает другой механизм: `WidgetMut::insert_prop`
вызывает `core_property_changed` и `Widget::property_changed`, и виджет уже сам
просит layout. По одному виджету за раз. Ровно так и устроен `CanvasDetail` из Фазы 0
— канвас вешает его на каждую ноду, которую строит; автоматики там не было никогда,
просто раньше это не бросалось в глаза.

**Размеры приходят из трёх разных мест, и «умножить всё» упирается в каждое
по-своему.** `Padding`, `BorderWidth`, `CornerRadius` — свойства, но их значения по
умолчанию заданы **на тип виджета** в `DefaultProperties`, а это одна штука на
приложение, не на регион. Кегль — вообще не свойство: это `parley`-овский
`StyleProperty::FontSize` внутри `Label`/`TextArea`, задаваемый на экземпляр. Плюс у
каждого виджета свои внутренние константы.

**Исход развилки — второй из трёх, названных в задаче:** механизма хватает для наших
виджетов и не хватает для масонриевских. Это не вывод из чтения исходников, а
измерение: тест `masonry_widgets_do_not_follow_ui_scale` кладёт `Button` в регион,
меняет `UiScale` и проверяет, что паддинг кнопки не сдвинулся. Он сформулирован так,
чтобы упасть в тот день, когда апстрим обзаведётся масштабом на поддерево, — и
сказать, что костыль можно убирать.

### 22.2 Что построено

`AreaContent` — стек регионов внутри области: заголовок фиксированной логической
высоты сверху, main под ним. У каждого региона свой `ui_scale`. Смена масштаба идёт в
два шага: `set_ui_scale` помечает регион, mutate-проход вешает `UiScale` на его
корень, `property_changed` корня просит layout. Mutate-проход идёт перед layout в том
же цикле перезаписи, поэтому смена приземляется в том же кадре.

Соглашение, которое приходится ввести из-за отсутствия наследования: **контейнер,
который хочет масштабировать своих детей, обязан передать значение вниз сам.** Ничего
не делает этого автоматически.

`ScaledHeader` в примере — виджет, который честно читает `UiScale` в `measure` и
`layout` и запоминает масштаб, при котором раскладывался. Последнее не для красоты:
спросить из mutate-прохода, «взял ли корень свойство», нечем — `needs_layout()` есть
только у `LayoutCtx`, — и вместо того чтобы угадывать, счётчик поставлен туда, где
знание есть, а бенчмарк читает его обратно.

### 22.3 Замерено

8 областей по шапке и канвасу в каждой, 5000 нод, вьюпорт 1400×900. Миллисекунды —
один прогон и гуляют между прогонами процентов на двадцать; счётчики справа
воспроизводятся до второго знака, и критерии стоят на них.

| Сценарий | мс/кадр | ресайзов областей | ресайзов регионов |
|---|---:|---:|---:|
| простой | 0.182 | 0.00 | 0.00 |
| смена `ui_scale` одного региона | 0.220 | **0.00** | 1.98 |
| зум содержимого одного региона | 0.251 | 0.00 | **0.00** |
| пан в одной области | 0.248 | 0.00 | 0.00 |
| перетаскивание листового сплиттера | 0.253 | 2.00 | 4.00 |
| перетаскивание корневого сплиттера | 0.486 | 4.10 | 8.20 |
| ресайз окна | 0.317 | 1.95 | 3.90 |

Обе половины §9 держатся, и обе измерены с двух сторон.

**`ui_scale` идёт в layout.** За прогон не потеряно ни одной смены масштаба: заголовок
раскладывался ровно на том значении, которое ему выставили (критерий сформулирован от
обратного — «сколько смен регион не увидел», — чтобы его, как и все остальные, можно
было ограничить сверху). Смена стоит 1.98 ресайза региона на кадр: сам заголовок и
main, у которого меняется остаток высоты. Областей она не задевает вовсе, соседних
областей — тоже.

**`view` в layout не идёт.** Зум содержимого — 0.00 ресайзов региона. Фаза 0 доказала
это внутри канваса; здесь проверено на уровень выше, что стек регионов не соблазнился
считать зум ресайзом.

**Цена второго региона.** Простой при 8 областях: 0.145 мс с одним регионом на
область, 0.102 мс с двумя. Второй регион вышел *дешевле*, и объяснение не в том, что
регионы бесплатны, а в том, что заголовок отъедает 24 пикселя у канваса, и тот
материализует меньше нод — 48 живых виджетов против 32. Критерий сформулирован как
«не удваивает», а не «не стоит ничего», именно поэтому, и по той же причине развёртка
§21.2 гоняется без шапок.

### 22.4 Вердикт по Фазе 0.6

**Разделение §9 выдержало.** Самая дорогая ошибка этого места — смешать `ui_scale` с
`view` — теперь не «мы про неё помним», а четыре счётчиковых критерия в CI и семь
тестов.

Что меняется в плане §16:

* **Пункт 5 разблокирован для наших виджетов и заблокирован для масонриевских.**
  Механизм работает; читать `UiScale` умеет только тот, кого мы написали. Для
  прикладного приложения это терпимо ровно до того момента, когда в плотном UI
  появятся масонриевские слайдеры и чекбоксы, — то есть до пункта 11
  (`blazy-widgets`), который с этого момента становится не «контролы покрасивее», а
  условие работоспособности `ui_scale`.
* **В §17 добавляется четвёртый пункт для контрибьюта:** масштаб интерфейса,
  наследуемый вниз по поддереву. Формулировать его надо не как «добавьте нам
  свойство» — свойства есть, — а как «`DefaultProperties` привязаны к приложению, а
  должны допускать переопределение на поддерево». Это тот же класс изменения, что
  публичный API для `PaintLayerMode`: инфраструктура готова, не хватает шва.
* **Округление снова оказалось обязательным.** Высота заголовка округляется до целого
  пикселя по той же причине, что и границы сплитов (§21.3).

### 22.5 Чего Фаза 0.6 не проверяла

Передачу `UiScale` глубже одного уровня: в спайке корень региона — один виджет, и
соглашение «контейнер передаёт вниз» описано, но не нагружено. Регионы кроме шапки и
main. Резкость текста и кривых при смене любого из трёх множителей — довод §9 в пользу
`imaging`, который счётчиком не выражается и требует golden-image-теста на
CPU-бэкенде (пункт 1 Фазы 1); он **не проверен**, и это самая заметная дыра, оставшаяся
после трёх спайков. `PaintLayerMode::IsolatedScene` на регион по-прежнему не нужен по
числам §21.4.

## 23. Результаты Фазы 1.1 — рендер и резкость (замерено)

§22.5 назвал оставшуюся дыру: ни один тест в проекте не проверял, что хоть
что-нибудь нарисовано правильно. Все проверки были про счётчики. Для библиотеки,
которая продаёт рендер, это была самая большая непокрытая поверхность, и внутри неё
лежало непроверенное утверждение §9 — то самое, ради которого `imaging` частично и
выбран: смена любого из трёх множителей корректна **без потери резкости**, чего не
могут ни атласные рендеры, ни тесселяторы.

### 23.1 Разведка: что уже даёт апстрим

`masonry_testing` умеет больше, чем предполагал §16 пункт 1:

* `TestHarness::render()` растеризует на CPU через `VelloCpuRenderer` — без GPU,
  композитора и оконного менеджера.
* Есть `assert_render_snapshot!`, эталоны в `<crate>/screenshots/`, обновление через
  `MASONRY_TEST_BLESS=1`, допуск по каналу, картинка разницы при провале.
* **Шрифт запиннен:** харнесс ставит `use_system_fonts: false` и подкладывает
  встроенный Roboto. Это снимает главный источник дрейфа golden images.

То есть инфраструктуру снапшотов писать не надо — надо решить, где она применима.

### 23.2 Воспроизводимость снапшотов — замерено

Три прогона подряд дают побайтово идентичную картинку, и **debug и release тоже дают
идентичную** (`opt-level=1` против `3`). Последнее — не формальность: разный уровень
оптимизации допускает разное округление в плавающей точке, и совпадение говорит, что
растеризатор к этому нечувствителен.

Вместе с запинненным шрифтом, CPU-растеризацией и пином апстрима по коммиту это
делает снапшоты здесь гораздо надёжнее, чем golden images бывают вообще. Поэтому они
включены в гейт, а не спрятаны за `SKIP_RENDER_TESTS`.

**Что осталось непроверенным: другая архитектура процессора.** Локальная машина и
раннер CI — обе x86-64 Linux, так что первый прогон в CI ничего нового не покажет;
ARM-раннер или другая платформа — открытый риск. Если снапшоты там разойдутся,
правило §20.9 требует перестать их гейтить и сказать об этом, а не приглушить
переменной окружения.

### 23.3 Метрика резкости вместо картинки

Побайтовое сравнение отвечает «изменилось или нет», а §9 спрашивает другое —
«не размылось ли». Это выражается числом, и число надёжнее картинки.

**Первая попытка была неверной, и ошибка поучительная.** Средний модуль градиента
яркости даёт для перерисованного и для размытого изображения **одно и то же**:
7189 против 7189 при заметно разных картинках. Причина в том, что сумма модулей вдоль
ступеньки сохраняется — одна ступенька в 40 и четыре по 10 дают одинаковый вклад.
Метрика была слепа к размытию по построению.

Работает **средний квадрат градиента**: 1600 против 4×100. Замерено на реальном
содержимом, увеличение в 4 раза:

| Множитель §9 | Как передаётся | Выигрыш в резкости |
|---|---|---:|
| `ui_scale` | через layout | 4.64× |
| `view` (зум канваса) | трансформ при композиции | 4.87× |
| `device_scale` | трансформ при композиции | 4.64× |

Порог гейта — 2.0×. Проверено на вакуумность: если подсунуть вместо перерисовки
билинейно увеличенную картинку, тест даёт ровно 1.00× и падает.

**Признанное слепое пятно метрики.** Она меряет ширину края, поэтому увеличение
методом «ближайшего соседа» набирает столько же, сколько честная перерисовка — края и
там и там в один пиксель. Реальный рендер так не увеличивает, но это способ пройти
проверку, ничего не сделав, поэтому рядом стоит вторая: доля пикселей, отличающихся
от блочного увеличения. Настоящая перерисовка пересемплирует каждый край, блочное
повторение — нет. Слепое пятно зафиксировано отдельным тестом в `bench-utils`, чтобы
его не открыли заново как сюрприз.

### 23.4 `device_scale` не проверяется через харнесс апстрима

Попытка задать `TestHarnessParams::with_scale(4.0)` дала выигрыш 1.17× и 95%
пикселей, отличных от ожидаемых. Причина не в рендере: `VisualLayerPlan` выдаётся в
логических координатах, а применение оконного масштаба — работа хоста (§4.2), и
`TestHarness::render()` её не делает, применяя только `padding * layer.transform`.

Поэтому третий множитель проверяется **собственным хостом**: план забирается через
`redraw()`, слои переигрываются через `replay_transformed` с `Affine::scale(k)`, и
результат растеризуется `VelloCpuRenderer`-ом. Сорок строк в тестах — и это первый
кусок того, что §16 называет `blazy-shell`.

### 23.5 Выбор бэкенда: пункт 1 §16 выполним, но это работа, а не флаг

`masonry_imaging::image_render` выбирает `Renderer` **каскадом `cfg(feature)`** с
жёстким приоритетом (`vello` → `skia` → `vello_hybrid` → `vello_cpu` → заглушка), то
есть на этапе компиляции. `masonry_winit` делает то же самое, пробрасывая фичи вниз.
Выбора в рантайме апстрим не предоставляет.

Но и не мешает: модули бэкендов гейтятся каждый своей фичей независимо, поэтому
включить несколько сразу можно, а трейт `imaging::render::ImageRenderer`
объектно-безопасен — `Box<dyn ImageRenderer>`, выбираемый при старте, собирается у
нас. Для окна к этому нужен свой хост, то есть `blazy-shell`.

**Вердикт по пункту 1 §16:** формулировка «выбор бэкенда в рантайме» выполнима и не
требует изменений в апстриме, но требует собственного оконного слоя. Патч наверх не
нужен, в §17 ничего не добавляется. Минимальный кусок хоста уже написан (§23.4) и
показывает, что путь короткий.

### 23.6 Что закрыто и что осталось

Закрыто главное: §9 больше не вера. Три множителя проверены по отдельности, каждый
своим маршрутом, и разница между «идёт через layout» и «трансформ при композиции»
видна в том, как тесты их приводят в действие.

Не сделано и осознанно: `blazy-shell` целиком (окно, owner mode, выбор бэкенда в
рантайме) — по §23.5 это работа без неизвестных; `blazy-shape` (§16 пункт 2). Не
проверено: снапшоты на другой архитектуре (§23.2).

## 24. Результаты: слой связей и пространственный индекс (замерено)

§16 пункт 10 состоял из трёх вещей. LOD был сделан в §20.7; здесь закрыты остальные
две, и они оказались одной задачей: индекс отвечает на вопрос «что сейчас в кадре»,
а связям этот же ответ нужен, чтобы знать, какие кривые записывать.

### 24.1 Разведка поправила постановку

Задача исходила из того, что линейный проход `cull` — уже большая часть простоя.
**Это оказалось неверно.** Простой при 256 000 нод стоит те же 0.085 мс, что при
16 000: когда дерево чистое, layout не бежит, а `cull` вызывается из него — то есть
на простое проход не выполняется вовсе.

Линейность видна на пане, и развёртка никогда не поднималась достаточно высоко,
чтобы её показать:

| Всего нод | Пан до индекса | Пан после |
|---:|---:|---:|
| 4 000 | 0.592 мс | 0.351 мс |
| 16 000 | 0.477 мс | 0.342 мс |
| 64 000 | 0.669 мс | 0.424 мс |
| 256 000 | 2.332 мс | 0.327 мс |
| 1 000 000 | 6.839 мс | **0.334 мс** |

До 64 000 проход теряется в фиксированной стоимости кадра; выше — доминирует.
На миллионе нод индекс дал **20×**, и кривая стала плоской.

Отсюда следствие про сами критерии: развёртка §20.5 заканчивается на 16 000, и
критерий «стоимость кадра не следует за числом нод» на ней проходил всё это время,
хотя линейная стоимость никуда не девалась. **Границы развёртки — часть критерия**, и
слишком короткая прячет ровно то, что критерий должен ловить.

### 24.2 Индекс: равномерная сетка

Сетка, а не R-tree. Причина не в простоте самой по себе, а в том, что ноды двигаются:
перетаскивание должно обновлять индекс, не трогая остального, и у сетки это
перекладывание из ячейки в ячейку без перебалансировки. Кластеризацию — случай, на
котором сетка должна проигрывать, — она переживает, потому что запрос посещает только
ячейки, пересекающие вьюпорт: плотный кластер стоит своего размера лишь когда он на
экране, а тогда его ноды всё равно надо обработать.

Две вещи, которые пришлось сделать явно, а не «по умолчанию»:

* **Запас запроса выводится из размера ноды, а не берётся равным одной ячейке.** Нода
  приписана к ячейке по левому верхнему углу, поэтому нода левее запроса всё ещё может
  в него дотягиваться. Одна ячейка запаса ломается в тот момент, когда нода шире
  ячейки, и ломается молча — нода просто перестаёт рисоваться у левого края. Запас
  считается по самой широкой ноде и покрыт тестом.
* **Запрос обрезается по сетке.** Иначе нода, утащенная за исходные границы графа,
  становится ненаходимой.

Замерено на пане при 5000 нод: **52.65 геометрии за кадр** против 5000 у линейного
прохода. Критерий стоит на счётчике, а не на микросекундах, — счётчик точен и не
зависит от машины, а микросекунды прохода до 64 000 нод в шуме и не видны.

### 24.3 Связи не вернули линейность

Это был единственный настоящий риск в задаче. Виртуализация (§20.3) сняла линейность,
убрав ноды из дерева; связи так убрать нельзя — их столько же, сколько нод, и связь с
одним концом в кадре всё равно должна быть нарисована.

Развёртка по числу рёбер при 5000 нод и неизменном вьюпорте:

| Рёбер | Пан | Пересборов набора связей за кадр |
|---:|---:|---:|
| 0 | 0.340 мс | 0.00 |
| 2 464 | 0.381 мс | 0.00 |
| 4 928 | 0.371 мс | 0.00 |
| 9 857 | 0.354 мс | 0.00 |

**1.04× при бесконечном росте рёбер.** Приём тот же, что вытащил дальнее поле (§20.6):
сцена кривых в канвасных координатах, пан и зум переиспользуют её трансформом.

**Разделение «перерисовать» и «пересобрать» — то, что делает перетаскивание дешёвым.**
Первая версия слоя держала один флаг `dirty`, и тест это поймал: при таком устройстве
каждый кадр перетаскивания заново выбирал бы, какие кривые на экране, то есть обходил
бы регион шестьдесят раз в секунду. У перетаскиваемой ноды двигаются концы её
собственных кривых — сцену надо перерисовать, но набор не меняется. Сейчас это два
флага, и замер показывает 0.97 перерисовки и **0.00 пересбора** на кадр.

### 24.4 Признанное ограничение выбора связей

Связи выбираются через список смежности, а не через индекс их собственных
ограничивающих прямоугольников: связь записывается, если **любой её конец** попал в
регион. Это точно для графа, у которого рёбра короче запаса региона — полэкрана, — то
есть для нод-редактора, и это же делает перетаскивание дешёвым, потому что кривые
двигаемой ноды — ровно её собственные.

В общем случае неточно: связь, у которой оба конца вне региона, а кривая пересекает
экран, не рисуется. Починка — второй индекс по прямоугольникам связей, у которого
ячейки вырождаются, как только появляется одно длинное ребро. Ограничение закреплено
тестом, а не оставлено на переоткрытие.

### 24.5 Что это меняет в плане §16

* **Пункт 10 закрыт.** Осталась предметная работа поверх готового индекса — выделение,
  box-select, сериализация графа — и хит-тест по кривым, который по §10.4 принадлежит
  `blazy-shape` (пункт 2).
* **Последняя стоимость, линейная по графу, снята.** В канвасе больше не осталось
  места, где кадр зависит от размера графа, а не от вьюпорта.
* **Снапшот поймал, что связи не видны там, где на них смотрели.** Существующий
  снапшот экрана продолжал проходить после появления связей, потому что при его
  разбиении одна нода занимает всю область. Добавлен отдельный снапшот графа с
  рёбрами; урок общий — снапшот проверяет ровно то, что попало в кадр.

## 25. Результаты: точный хит-тест по фигуре (замерено)

§16 пункт 2. Три геометрии из §6.1 существовали в проекте в количестве двух:
раскладочная и визуальная. Хитовая была прямоугольником везде — и у виджета, где её
считает апстрим по bbox, и в канвасе, где `CanvasLayer::hit_child` проверял
`Rect::contains` по слоту. Связи не были достижимы вообще: сущность, которой нет в
дереве виджетов, невидима для `find_widget_under_pointer`.

### 25.1 Разведка: что даёт апстрим и сколько стоит точная фаза

Точка входа `masonry_core::core::widget::find_widget_under_pointer` устроена так:
`bounding_box().contains(pos)` → `is_stashed` → `clip_path().contains(to_local(pos))`
→ дети в обратном порядке `children_ids` → сам виджет. Отсюда два факта, которые
определили постановку:

* **Грубая фаза уже есть и она бесплатна для нас.** Переопределять
  `find_widget_under_pointer` нужно ради точности, а не ради скорости: обход детей
  линеен по числу детей, а у канваса их столько, сколько материализовано.
* **`pos` приходит в координатах окна, а `window_transform` виджета несёт зум
  канваса.** Замерено: у виджета внутри канваса на зуме 0.5 масштаб
  `window_transform` равен 0.5. Значит виджет сам может пересчитать допуск из
  экранных пикселей в свои единицы, не спрашивая канвас.

Стоимость точной фазы (release, 200 000 итераций на замер):

| Операция | Наносекунд |
|---|---:|
| `Rect::contains` | 17.5 |
| `RoundedRect::contains` | 26.2 |
| `BezPath::contains` (тот же скруглённый прямоугольник, 8 сегментов) | **576.0** |
| та же фигура, кэш флаттенинга (16 точек, winding по полилинии) | **37.5** |
| `CubicBez::nearest`, точность 0.1 | 122.7 |
| отсев по bbox контрольного полигона кубики | 17.3 |

Два вывода, и оба меняли бы дизайн, если бы числа вышли другими:

1. **Кэш флаттенинга из §6.2 оправдан замером, а не вкусом: 15×.** `BezPath::contains`
   заново разбирает элементы пути на каждый вызов. При 32 кандидатах на один запрос
   это 18 мкс против 1.2 мкс — на кадре в 0.3 мс разница между «незаметно» и «6%
   кадра на движение мыши».
2. **Кривые проверяются без кэша, но с отсевом.** `nearest` в семь раз дороже отсева
   по контрольному полигону, а кривая связи не переживает кадр — она выводится из
   прямоугольников концевых нод. Поэтому связи: дешёвый отсев по bbox, точный
   `nearest` только для выживших.

**Число кандидатов на точечный запрос выводится из устройства сетки, а не измеряется
отдельно:** ячейка держит в среднем 8 нод (`TARGET_PER_CELL`), запас запроса — одна
ячейка по каждой оси, потому что нода уже́ ячейки. Значит 2×2 ячейки ≈ 32 геометрии на
запрос, и это число не зависит от размера графа: при 250, 5000, 64 000 и 1 000 000 нод
сторона ячейки выходит 745, 630, 625 и 625 канвасных единиц соответственно.

### 25.2 Допуск — в экранных пикселях, и это не деталь

Тот же вопрос §9 о трёх множителях, но со стороны ввода. Точная фаза считается в
локальных (канвасных) координатах, а попадание пользователь ощущает в пикселях экрана.
Допуск в 4 канвасные единицы по диапазону зума канваса (0.02…8):

| Зум | Допуск на экране |
|---:|---:|
| 0.02× | 0.08 px |
| 0.10× | 0.40 px |
| 1.00× | 4.00 px |
| 8.00× | 32.00 px |

400-кратный разброс: на обзорном масштабе по связи невозможно попасть, на приближении
она ловит курсор за полсантиметра. Поэтому допуск задаётся в экранных пикселях и
делится на масштаб в момент проверки.

### 25.3 Что построено

**`blazy-shape` — точная фаза, и только она.** Грубую делает апстрим, спускаясь по
дереву; `ShapeHit::find_widget` встаёт перед ней одной проверкой и годится телом для
`Widget::find_widget_under_pointer`. Два режима, как в §6.2: `Fill { rule }` — winding
по флаттенингу, `Stroke { width, slop }` — расстояние до сегментов. Фигура закрывает
всё поддерево, ровно как клип: ребёнок, торчащий за фигуру, через неё недостижим — что
и требуется телу ноды, у которой срезанный угол должен принадлежать тому, что за ним.

**Кривые, которые не виджеты, обслуживаются отдельной функцией.** `near_segment` не
хранит ничего: связь выводится из прямоугольников концевых нод и не переживает кадр,
кэшировать нечего. Отсев — bbox контрольного полигона, он всегда содержит кривую.

**Канвас отвечает за то, чего нет в дереве.** `CanvasLayer::hit_test` спрашивает
модель, а не дерево, и потому работает там, где дерево пусто: под порогом дальнего поля
ни у одной ноды нет виджета (§20.6), а у связи его нет никогда. Ноды — кандидаты из
сетки, затем точная проверка; связи — записанный набор, затем `near_segment`.

**Кандидаты по связям — это записанный набор, а не второй индекс.** Кликается ровно то,
что нарисовано: правило выбора §24.4 унаследовано вместе с его ограничением, а не
изобретено заново. Второй способ выбирать кандидатов означал бы указатель, который
попадает по кривой, которой не видно, или промахивается по той, которую видят все.

**Шов к приложению — `NodeSource::hit`.** Канвас знает, где нода и какого она размера;
как она выглядит, знает только приложение. Канвас сужает кандидатов сеткой и спрашивает
про каждого выжившего — вызовов на запрос единицы, поэтому реализация может позволить
себе быть точной и держать свой `ShapeHit` с кэшем между запросами.

### 25.4 Замерено

| Счётчик | Замерено | Граница |
|---|---:|---:|
| геометрий нод на запрос (1000 → 16 000 нод) | 18.9 → 18.9 | 36.3 |
| кривых на запрос (4000 → 16 000 нод) | 79.7 → 79.7 | 127.6 |
| раскладок на кадр при движении мыши | 0.00 | 0.5 |
| углов, ошибочно попавших в ноду (240 проб) | 0 | 1 |
| исходов, изменившихся по развёртке зума (12 проб) | 0 | 1 |

Все пять проверены на вакуумность — каждая ломается тем, что она запрещает:

| Что сломано | Счётчик становится |
|---|---:|
| перебор всех слотов вместо сетки | 4800 геометрий на запрос |
| перебор всех рёбер вместо записанного набора | 5065 кривых на запрос |
| прямоугольник вместо фигуры | 160 углов из 240 «попали» в ноду |
| допуск в канвасных единицах | 2 исхода из 12 изменились |
| hover просит раскладку | 1.00 раскладки на кадр |

**Развёртка снова оказалась частью критерия — с другого конца.** Первая версия
начиналась с 250 нод и падала: 46 кривых на запрос против 80 при 4000 и 16 000. Причина
не в индексе, а в том, что граф из 250 нод (три ряда) **меньше региона**, для которого
канвас записывает связи, — кривые заканчиваются раньше, чем регион. Нижняя точка
развёртки мерила протяжённость графа, а не его плотность. Урок §24.1 был про слишком
короткую развёртку; этот — про слишком раннее начало.

**Счётчик, который не ловил то, ради чего написан.** Критерий «попадание не запускает
раскладку» сначала считал *детские* раскладки — и не сработал, когда hover заставили
просить `request_layout`: проход по чистым детям ничего не дёргает, счётчик остаётся
нулём. Считать надо проходы раскладки, а не детей в них. Поймано вакуумной проверкой,
которая для этого и делается.

**Счётчики попаданий не могут ехать на раскладке.** Остальная статистика канваса
обновляется в конце layout — самое дешёвое честное место. Для попаданий оно не годится
именно потому, что попадание обязано раскладку не запускать: счётчик, ждущий её,
показал бы ноль ровно в том сценарии, ради которого заведён. Поэтому пик публикует свои
три числа сам.

**Точность `ParamCurveNearest::nearest` — не то, что написано в аргументе.** Параметр
`accuracy` ведёт себя как допуск подразбиения, а не как граница ошибки расстояния: при
0.1 ответ на одной кривой связи уходил на **1.66 единицы** от истинного расстояния —
половина трёхпиксельного допуска. При 0.01 худшая ошибка 0.003, при 0.001 — ноль в
пределах double. Стоимость при этом почти не меняется (123 нс против 162 нс), потому
что дорого само обращение, а не его точность. Взято 0.001.

### 25.5 Чего это не делает

* **Выделение, box-select, перетаскивание конца связи** — ответ «что под курсором» есть,
  а что с ним делать, решают операторы (§11, `blazy-ops`). Наведённая связь
  подсвечивается, и это перерисовка, а не модель выделения.
* **Связь, у которой оба конца вне записанного региона, не выбирается указателем** —
  потому что она и не рисуется (§24.4). Ограничение унаследовано осознанно и закреплено
  тестом; исправляется тем же вторым индексом, что и в §24.4, и с той же ценой.
* **Неравномерный масштаб.** `scale_of` берёт длину преобразованного единичного вектора
  по x. Для переносов, поворотов и равномерных масштабов это и есть масштаб; для
  анизотропного допуск указателя двусмыслен по существу.

### 25.6 Что это меняет в плане §16

* **Пункт 2 закрыт.** `blazy-shape` есть, он в фасаде, и обе стороны хит-теста —
  виджетная и модельная — работают через одну фигуру.
* **Из Фазы 1 остался только пункт 1** (`blazy-shell`), про который §23.5 уже сказал:
  работа без неизвестных.
* **Предметная работа по канвасу разблокирована полностью.** Выделение и box-select
  теперь стоят поверх готового ответа, а не поверх прямоугольников.

## 26. Результаты: `blazy-shell`, owner mode (замерено)

§16 пункт 1. §23.5 обещал работу без неизвестных. Неизвестных действительно не нашлось,
но разведка поправила две вещи, записанные в этом документе, и одна из них — про
апстрим, который ушёл вперёд.

### 26.1 Разведка: апстрим сдвинулся, и §7.3 с §17 устарели

**`PaintCtx::set_paint_layer_mode` уже публичный.** §7.3 описывает `PaintLayerMode` как
скелет с `pub(crate)`-полем и без сеттера, а §17 ставит «публичный API для
`PaintLayerMode`» первым пунктом того, что мы собирались контрибьютить. На закреплённой
ревизии сеттер есть (`masonry_core/src/core/contexts.rs`), и виджет может объявить себя
внешним слоем сегодня. Пункт 1 §17 закрыт апстримом без нас; **`blazy-compose` (§7.3)
больше не ждёт патча наверх** — только нашей работы.

**Дыра живёт один кадр.** Проверено виджетом, который в `paint` объявляет себя
`External`: в кадре, где он перерисовывался, план содержит `VisualLayerKind::External`;
в кадре, где он **не** перерисовывался, — обычный слой сцены с его прошлым содержимым.
Причина в устройстве прохода: `state.paint_layer_mode` сбрасывается в `Inline` в начале
прохода **для каждого виджета**, а вернуть его может только сам виджет, и только если
`request_paint` был выставлен. Ретейн-дерево устроено так, что чистый виджет не красят —
и объявление теряется молча.

Для хоста это значит, что «дыр в кадре нет» и «виджет не перерисовывался» — неразличимы
на стороне плана, поэтому виджет-дыра обязан краситься каждый кадр. Он ничего не рисует,
так что это вызов функции, а не работа; но это соглашение, а не свойство, и потому
оформлено виджетом в `blazy-shell`, а не оставлено на прочтение документации. Настоящая
починка — сделать режим свойством виджета, а не флагом прохода; это второй кандидат в
§17 взамен закрытого первого.

### 26.2 Разведка: объектно-безопасен именно *image*-шов

§23.5 верен, но недоговаривает. Объектно безопасен `imaging::render::ImageRenderer`, и
он рендерит **в буфер пикселей, которым владеет вызывающий**. Текстурный шов —
`imaging_wgpu::TextureRenderer` — имеет ассоциированные типы (`TextureTarget`,
`Texture`), то есть `Box<dyn TextureRenderer>` невозможен в принципе, а
`masonry_imaging::texture_render::Renderer` сам выбран каскадом `cfg`.

Отсюда честная формулировка пункта 1 §16: **выбор бэкенда в рантайме — это выбор
растеризатора, а не пути на экран**. Растеризатор отдаёт картинку, показать её — работа
хоста, и она пишется один раз для всех бэкендов. Путь «прямо в текстуру свопчейна»
остаётся выбором на этапе компиляции, пока у него ассоциированные типы; он относится к
уровню B (§7.3), а не к owner mode.

### 26.3 Разведка: от `masonry_winit` переиспользовать нечего

Конвертация событий — `pub(crate)` (`masonry_winit/src/convert_winit_event.rs`),
`MasonryState` держит и конкретный `ImagingRenderer`, и пул поверхностей. Нужный кусок
лежит внутри ненужного, и снаружи не достаётся.

Зато `RenderRoot` публичен целиком: `handle_pointer_event`, `handle_text_event`,
`handle_window_event`, `redraw`, `cursor_icon`, `needs_anim`, сигналы. Своё окно — это
цикл winit поверх публичного `RenderRoot`, а не форк чужого рантайма. Что мы при этом
не получаем даром и что осознанно не сделано — в §26.5.

### 26.4 Что построено и замерено

**`blazy-shell`**: реестр бэкендов (`Backend`, `COMPILED`, `open`), композиция плана с
масштабом устройства и сбором дыр (`Composition`, `Hole`), хост (`Host`: план внутрь,
кадр наружу), виджет-дыра (`ExternalContent`) и owner mode (`window`) — окно, цикл
событий, ввод через `ui_events_winit::WindowEventReducer` и показ кадра через
`softbuffer` (второй путь показа появился в §27). Оба примера переведены на него, `masonry_winit` из зависимостей рабочего
пространства **убран**: он больше нигде не используется.

Сорок строк хоста из §23.4 переехали в крейт, и тесты резкости теперь зовут его.

**Выбор бэкенда — не формальность.** По умолчанию собран один растеризатор
(`vello_cpu`), с фичей `vello` — два, и реестр открывает оба: на этой машине
`cargo bench -p blazy-shell --features vello` печатает `vello_cpu opens`,
`vello opens`, и приложение выбирает флагом `--backend`. Фича выключена по умолчанию
потому, что GPU-бэкенду нужен девайс, которого у сборочной машины может не быть, — и
это отдельный вид отказа: `BackendError::Unavailable` про машину, `NotCompiled` про
сборку, и критерий считает только второе.

| Критерий | Замерено | Граница |
|---|---:|---:|
| бэкендов, недостижимых по имени | 0 | 1 |
| раскладок при композиции на четырёх масштабах | 0 | 0.5 |
| отклонение размера кадра от масштаба | 0 px | 1 px |
| кадров без дыры там, где дыра объявлена | 0 из 40 | 1 |
| непрозрачных пикселей в кадре к показу | 0 | 1 |

Все пять проверены на вакуумность: реестр с невыведенным бэкендом даёт 1;
`device_scale`, проведённый через изменение размера дерева, — 3 раскладки; игнорирование
масштаба при вычислении размера кадра — 3300 пикселей; виджет, объявляющий дыру один
раз, — 40 кадров без дыры; кадр без базового цвета — 629 824 полупрозрачных пикселя.
Пятый критерий появился здесь позже остальных, и почему — в конце раздела.

**Кадр обязан быть непрозрачным до показа — найдено глазами уже после сдачи.** Показ
выбрасывает альфу, поэтому всё, что осталось полупрозрачным, теряет сглаживание, которое
растеризатор только что посчитал: кривая превращается в лесенку, а пиксели с малой
альфой, у которых непремультиплицированный цвет разогнан округлением, становятся белыми
точками и мерцают при движении. В node-canvas этого не видно, потому что его корень
заливает окно непрозрачным фоном; в area-screen `AreaScreen::paint` рисует только
полоски сплиттеров, а `AreaContent::paint` — ничего. Замерено на кадре 800×600: у
area-screen 261 652 полностью прозрачных пикселя и 11 260 полупрозрачных, из них 220
почти белых; у node-canvas — ноль и ноль.

Дерево виджетов не обязано закрывать окно, поэтому базовый цвет — свойство окна, а не
приложения (у `masonry_winit` это поле `base_color` на окне). Заливка идёт в сцену до
плана, то есть смешивание делает растеризатор, а показ остаётся перестановкой каналов;
альтернатива — смешивать при блите — стоила бы трёх умножений на пиксель каждый кадр.
Закреплено тестом и критерием: с базовым цветом 0 непрозрачных пикселей, без него —
629 824.

**Четвёртый критерий задачи оказался не критерием, а фактом о графе зависимостей.**
«Крейты ядра не знают про окно» бенчмарк проверить не может: к моменту запуска дерево
уже слинковано. Это отдельная задача `cargo make deps-rule` в `ci`, и она тоже проверена
на вакуумность — `winit` в зависимостях `blazy-canvas` роняет её.

**Счётчик, который считал не то — второй раз за две задачи.** Первая версия критерия про
дыры считала «объявлено минус доставлено». Разница равна нулю и когда всё доходит, и
когда виджет **перестал объявлять** — то есть ровно в том отказе, ради которого критерий
написан. Вакуумная проверка это показала: сломанный виджет прошёл. Считать надо кадры
без дыры. Урок тот же, что в §25.4, и повторяемость намекает, что проверять критерий на
вакуумность стоит не «когда есть сомнения», а всегда.

### 26.5 Чего owner mode не делает

Названо, а не забыто:

* **IME, буфер обмена, доступность, оконные жесты** (перетаскивание за собственный
  заголовок, ручки ресайза, системное меню). Masonry шлёт сигналы на всё это, а цикл их
  игнорирует. Каждое — отдельная платформенная интеграция, и ни одна не лежит на
  критическом пути вопроса, ради которого крейт написан.
* **Показ кадра идёт через CPU.** Кадр приходит пикселями (§26.2), и `softbuffer`
  кладёт их в окно; это один проход по кадру на перестановку каналов. **Снято в §27**:
  прямой путь в свопчейн написан, и он оказался не задачей `blazy-compose`, а
  собственным швом презентации после композиции. Ниже примерно мегапикселя блит,
  впрочем, остаётся быстрее (§27.4), поэтому он никуда не делся.
* **Guest mode** (§14) — почти готов у апстрима, но проверять его нечем без движка;
  ждёт `blazy-embed-*` (§16 пункт 13).
* **Мульти-окно** (§16 пункт 6). Цикл держит одно окно; `RenderRoot` per window, так
  что дорога открыта, но не пройдена.

### 26.6 Что это меняет в плане §16 и §17

* **Пункт 1 Фазы 1 закрыт**, и вместе с ним закрыта вся Фаза 1: §23 сделал рендер и
  резкость, §25 — `blazy-shape`, здесь — оконный слой.
* **Пункт 1 §17 закрыт апстримом** (§26.1): публичный API для `PaintLayerMode` уже
  есть. Взамен появляется новый кандидат в контрибуцию — сделать режим свойством
  виджета, а не флагом прохода, чтобы дыра не терялась в кадре без перерисовки.
* **Пункт 9 Фазы 3** (`VisualLayerKind::External` в хосте) сделан: дыры доходят до
  владельца окна. Что осталось от пункта 9 — заполнить их чужим пассом, то есть уже
  guest mode и движок.
* **Зависимость от `masonry_winit` снята.** Главный риск §15.1 — жизнь на двух молодых
  крейтах — уменьшился на один крейт: осталась поверхность `masonry` и `imaging`.

## 27. Результаты: прямой путь кадра в свопчейн (замерено)

Продолжение §26. Owner mode показывал кадр через оперативную память: растеризатор
отдавал пиксели, `softbuffer` клал их в окно. Уровень A из §7.3 — окно целиком одной
текстурой — закрывается здесь; уровень B, текстура на область, остаётся за
`blazy-compose`.

### 27.1 Разведка: рецепт есть, и он чужой

**Наша сцена годится напрямую.** `TextureRenderer::render_source_into_texture` принимает
`&mut dyn RenderSource`, а `record::Scene` его реализует. Значит композиция §26 —
масштаб устройства, базовый цвет, сбор дыр — остаётся нетронутой: в текстуру уходит
ровно та сцена, которую мы уже собираем, и `PreparedFrame` апстрима нам не нужен.

**Но vello рисует только в `Rgba8Unorm`.** `supported_texture_formats()` у
`imaging_vello` возвращает ровно один формат, а поверхности окна обычно
`Bgra8Unorm`. Поэтому прямой путь — не «рисовать в текстуру свопчейна», а
**промежуточная текстура плюс блит**: сцена рендерится в свою `Rgba8Unorm`-текстуру
размером с окно, а `wgpu::util::TextureBlitter` копирует её в текстуру свопчейна. Копия
остаётся на видеокарте, через процессор кадр не проходит.

Ровно так устроен и апстрим — `masonry_winit` держит `target_texture`, `target_view` и
`blitter` в своей `RenderSurface`. То есть «свой оконный слой» здесь означает повторить
известный рецепт, а не изобрести.

**Что в этом рецепте не выводится из документации** (и стоило бы дня на своих граблях):
выбор формата поверхности только среди `Rgba8Unorm`/`Bgra8Unorm`; три ветки по
`alpha_modes` с разными состояниями смешивания у блиттера; премультиплицированный блит
на AMD под Windows даже для непрозрачной поверхности; повторный `get_current_texture`
после `Outdated` — «частое явление на X11 и Xwayland с драйверами NVIDIA». Всё это
видно в их коде, и всё это мы забираем как знание, а не как зависимость.

### 27.2 Что это меняет в постановке

Задача просила «свой шов презентации, объектно безопасный у нас». Разведка это
подтверждает и уточняет форму: шов проходит **после композиции**, а не вокруг
растеризатора. Композиция общая для обоих путей, а дальше либо пиксели в окно
(`softbuffer`), либо сцена в текстуру и блит в свопчейн. Дыры §26 не меняются вовсе —
они и там и там прямоугольники в координатах кадра.

Отсюда же следует, чего нельзя проверить в CI: путь свопчейна требует окна, а окна на
раннере нет. Поэтому гейт меряет **ту же самую отрисовку в собственную текстуру**, без
поверхности: это весь путь кадра, кроме `get_current_texture` и `present`. Что именно
остаётся непроверенным, сказано в §27.5.

### 27.3 Что построено

**Шов презентации у нас, объектно безопасный.** `Presenter` — трейт с двумя
реализациями, выбираемыми при старте: `BlitPresenter` (растеризация в буфер и копия в
окно через `softbuffer`) и `SwapchainPresenter` (сцена в текстуру, текстура блитом в
свопчейн). Всё, что выше шва — композиция, масштаб устройства, базовый цвет, дыры, —
общее.

**GPU-путь разделён на две половины.** `GpuFrames` рисует в свою текстуру и не знает
про окно; `SwapchainPresenter` добавляет поверхность, блиттер и `present`. Разделение не
косметическое: половина без окна — это то, что можно измерить и загейтить на машине с
видеокартой, но без дисплея (§27.5).

**Отказ читаемый.** Запрошенный GPU-путь на машине без подходящего девайса даёт
`BackendError::Unavailable`, предупреждение в лог и рабочее окно на блит-пути — окно
обязано открыться. Заодно shell теперь поднимает подписчика `tracing`, если приложение
этого не сделало: иначе такое предупреждение никто не увидит.

**`masonry_imaging` больше не нужен.** Он был нужен ради `new_headless_renderer`, чей
`headless_wgpu` приватен; двадцать строк своего запроса девайса и `block_on` на парковке
потока (тем же способом, что у апстрима) убирают ещё одну git-зависимость на пине.

**Что не выводится из документации и стоило бы дня:** vello рисует через compute-шейдер,
поэтому промежуточной текстуре нужен `STORAGE_BINDING` — без него первый же кадр падает
валидацией wgpu, а не выглядит неправильно.

### 27.4 Замерено: путь на GPU быстрее не всегда

Отрисовка и показ, замерены по отдельности, 10 кадров на точку (`draw` для блита —
растеризация в буфер, `show` — перестановка каналов; для свопчейна `draw` включает
ожидание GPU, а блит в свопчейн идёт в той же посылке и отдельной цены не имеет):

| Окно | Масштаб | blit: draw + show | swapchain | Через память |
|---|---:|---:|---:|---:|
| 800×600 | 1 | 0.61 + 0.33 = **0.94 мс** | 1.81 мс | 1.9 МБ |
| 800×600 | 2 | 2.71 + 2.10 = 4.80 мс | **3.76 мс** | 7.7 МБ |
| 1400×900 | 1 | 1.60 + 1.04 = 2.64 мс | **2.29 мс** | 5.0 МБ |
| 1400×900 | 2 | 10.50 + 9.51 = 20.01 мс | **6.92 мс** | 20.2 МБ |
| 1920×1200 | 1 | 3.47 + 2.87 = 6.34 мс | **3.42 мс** | 9.2 МБ |
| 1920×1200 | 2 | 19.66 + 17.45 = 37.11 мс | **11.76 мс** | 36.9 МБ |

Три вывода, и первый противоречит ожиданию, с которым задача заводилась:

1. **Ниже примерно мегапикселя блит выигрывает.** На 800×600 GPU-путь стоит 1.81 мс
   против 0.94 — накладные расходы на посылку кадра доминируют над экономией. «Прямой
   путь» не синоним «быстрее».
2. **Выше — выигрывает свопчейн, и разрыв растёт**: 1.9× на 1920×1200 и 3.2× на том же
   окне с масштабом 2. На окне настоящего приложения (1400×900 при HiDPI) это 20 мс
   против 6.9 — разница между «не попадает в кадр» и «попадает».
3. **Одна перестановка каналов на 3840×2400 стоит 17.4 мс** — сама по себе больше
   бюджета кадра при 60 Гц. Это и есть та цена, которая растёт с площадью и которую
   прямой путь убирает целиком.

| Критерий | Замерено | Граница |
|---|---:|---:|
| байт кадра через оперативную память (GPU-путь) | 0 | 1 |
| чтений кадра обратно (GPU-путь) | 0 | 1 |
| кадров без дыры на GPU-пути | 0 из 40 | 1 |

Проверены на вакуумность: GPU-путь, отдающий кадр через память, даёт 3 300 000 байт и
1 чтение на кадр; путь, теряющий дыры, — 40 кадров без дыры.

Оба примера переведены на GPU-путь по умолчанию; в окне это подтверждается строкой
`blazy shell presenter="swapchain"`. Флаг `--backend vello_cpu` оставляет блит-путь, то
есть сравнить их можно в живом окне, а не только в бенчмарке.

### 27.5 Чего эта работа не проверяет

* **Окна в CI нет.** Гейт меряет `GpuFrames` — композицию, отрисовку в текстуру, дыры,
  счётчики, — но `get_current_texture`, `present`, реконфигурацию поверхности и её
  потерю проверяет только запуск руками. Это первый гейт в проекте, у которого есть
  машинозависимая часть, и на машине без видеокарты его GPU-критерии просто
  отсутствуют, а не падают.
* **Текстура на область** (§7.3 уровень B) — по-прежнему `blazy-compose`. Основание под
  неё теперь есть: композиция ходит по слоям, а `GpuFrames` умеет отрисовать любую
  сцену в текстуру, так что per-area кэш — это то же самое, повторённое на слой.
* **Guest mode** (§14): `GpuFrames::new` уже принимает чужие `Device`/`Queue`, то есть
  движку останется отдать их и забрать текстуру. Не проверено, потому что движка нет.
* **Damage regions** (#789) — только через апстрим.

### 27.6 Что это меняет в плане §16

* **Уровень A из §7.3 закрыт**: окно целиком одной текстурой, кадр не проходит через
  процессор. Регрессия показа, которой §26 расплатился за выбор бэкенда, снята.
* **Зависимостей на пине снова меньше**: `masonry_imaging` убран, осталась одна
  `masonry`.
* **Пункт 8 Фазы 3 разблокирован по-настоящему**, а не на словах: механизм отрисовки
  сцены в текстуру и блита в цель написан и замерен.

### 27.7 Правки после ревью

Ревью кода нашло в этом же разделе четыре вещи; три из них — ошибки, и одна лежала бы
до первого неудачного кадра.

**Пересъём поверхности при `Suboptimal` роняет приложение.** `wgpu` различает шесть
исходов получения текстуры свопчейна, и `Suboptimal` **отдаёт готовую картинку**,
попутно советуя переконфигурировать поверхность. Первая версия обрабатывала его вместе с
`Outdated`: конфигурировала и просила текстуру заново — не забрав первую из
сопоставляемого значения, которое живёт до конца `match`. То есть повторный запрос шёл
при уже удерживаемой картинке, а это `AlreadyAcquired`, и по умолчанию невыловленная
ошибка валидации — паника. Случай не редкий: `Suboptimal` — обычное дело на X11 и
Xwayland с драйверами NVIDIA во время перетаскивания окна, ровно в том сценарии, на
который ссылался комментарий рядом.

Теперь каждый исход разобран по смыслу: `Suboptimal` показывается, а переконфигурация
откладывается до следующего кадра; `Outdated` — конфигурируем и просим снова; `Occluded`
и `Timeout` — обычная жизнь свёрнутого окна, кадр пропускается **без** записи в лог
уровня error; `Lost` — поверхность пересоздаётся из сохранённого `Instance`, иначе окно
остаётся чёрным до конца сеанса после перезапуска композитора.

**Откат на блит-путь просил девайс во второй раз.** Если запрошен `--backend vello`, а
девайса нет, откат брал тот же бэкенд и снова требовал устройство — то есть обещание
«стартует и без GPU» не выполнялось именно тогда, когда было нужно. Теперь откат всегда
берёт растеризатор, которому девайс не нужен.

**Критерий про байты через память сторожил не тот код.** Счётчик `cpu_bytes` на GPU-пути
равен нулю по построению — там нечему его увеличивать, — и такой критерий не может
упасть, что запрещено дисциплиной §20.9. Исправлено двумя ходами: учёт байт переехал
туда, где байты возникают (`Host` считает то, что растеризовал), а рядом появился парный
критерий «блит-путь сообщает байты, которые двигает», считаемый от отказной стороны.
Проверено: снятие инкремента в `Host` роняет парный критерий. Первая версия парного
критерия сторожила арифметику самого бенчмарка — вакуумная проверка это и показала.

**Фасад не давал дотянуться до GPU-пути.** `blazy` зависел от `blazy-shell` без фичи
`vello` и не пробрасывал её, то есть приложение, зависящее от фасада — а по §18 так и
задумано, — не могло включить прямой путь в свопчейн вообще. Оба примера обходили это,
завися от `blazy-shell` напрямую. Фича проброшена.

Заодно из публичной поверхности убран тип ошибки `softbuffer`: какой крейт кладёт
пиксели в окно — деталь реализации презентера, и библиотека, протаскивающая её в свой
`Error`, передаёт вниз каждое переименование в апстриме (§15.1). Размер кадра стал одним
числом: окно знает его в физических пикселях, и презентер получает именно его, а не
логический размер, из которого он же и восстанавливается — на дробном масштабе 1.1458
этот круг мог разойтись на пиксель.

## 28. Регион, который умел только расти (найдено в работе)

Симптом, замеченный в живом окне: на зуме 1–2 всё плавно; после того как отъехать к
0.05 и вернуться обратно — тот же вид тормозит, и дальше тормозит всегда.

### 28.1 Что происходило

Набор рисуемых связей выбирается не для вьюпорта, а для **региона** — вьюпорта плюс
половина на каждую сторону (§24.4), — и пересматривается, когда вьюпорт из этого
региона выходит. На отъезде регион становится размером с граф; при возврате новый,
маленький вьюпорт **лежит внутри** старого региона, условие «вышел за регион» не
срабатывает никогда, и канвас продолжает рисовать все рёбра графа.

Замерено на 5000 нодах, панорамирование по 200 кадров:

| Состояние | Записано кривых | мс/кадр |
|---|---:|---:|
| свежий канвас, зум 1 | 96 | 0.27 |
| зум 0.05 | 9857 | 3.68 |
| **возврат на зум 1** | **9857** | **2.46** |
| возврат на зум 2 | 9857 | 1.88 |

Девятикратная разница на одном и том же виде — вся разница в том, был ли до этого
взгляд на весь граф. Причём перерисовок сцены при этом почти нет (0.01 на кадр): платим
не за перезапись, а за то, что кэшированная сцена содержимого теперь содержит десять
тысяч кривых, и проход покраски приклеивает её в слой каждый кадр — ровно та стоимость,
о которой §20.2.

### 28.2 Почему это не поймали раньше

Три причины, и все три поучительны:

* **Критерии смотрели на скорость пересмотра, а не на размер набора.** «Пан не
  пересматривает связи» выполнялось идеально — набор не пересматривался вовсе, в том
  числе тогда, когда был обязан.
* **Развёртки ходили по зуму в одну сторону.** Сценарии меряют пан на фиксированном
  зуме и зум из исходного состояния; ни один не возвращался обратно. Дефект живёт
  ровно в переходе «туда и обратно».
* **Долгий прогон это тоже не показал.** 10 000 кадров непрерывного зума с
  панорамированием дают ровную линию — потому что колебание шло в полосе 0.21…1.0 и
  никогда не доходило до обзорного масштаба. Ровный график — не доказательство
  отсутствия утечки, а доказательство того, что сценарий её не задевает.

### 28.3 Починка

Регион обслуживает вьюпорт, пока он не только его содержит, но и **соразмерен** ему:

```rust
pub(crate) fn region_covers(region: Rect, visible: Rect) -> bool {
    contains_rect(region, visible) && region.area() <= visible.area() * REGION_SLACK
}
```

`REGION_SLACK = 16`: регион по построению вчетверо больше вьюпорта по площади, так что
запас в четыре раза — это «приблизился вдвое, ничего не переписываем; приблизился
вчетверо — пересобираем». Правило общее для связей и для дальнего поля: у второго та же
конструкция, и та же болезнь внутри обзорного режима.

После починки возврат на зум 1 даёт 96 кривых и 0.27 мс — столько же, сколько у свежего
канваса.

Закреплено с трёх сторон: unit-тест на само правило, тест канваса на путь «отъехал и
вернулся» и критерий в гейте (`an_overview_does_not_leave_the_graph_recorded`: 96 против
границы 320). Проверено на вакуумность — со старым правилом критерий даёт 9857, а тест
падает.

### 28.4 Что это добавляет к дисциплине §20.9

**Счётчик работы за кадр не заменяет счётчик состояния.** Все существующие критерии
считали действия — раскладки, пересборы, перерисовки. Этот дефект был в размере
удерживаемого набора, и ни одно число про действия его не видело. К «сколько работы
сделано» нужно «сколько всего удерживается».

**Развёртка обязана возвращаться.** Тестировать переход в состояние и не тестировать
выход из него — значит проверять половину переключателя.

зума, зависит от размера ноды и плотности графа, то есть от вещей, которых порог по

| 0.02 | Box | 0 | 3 | — | 4.999 | 5.491 | — |

**Кадр стоит виджетов, и цена виджета одна.** Панорамируемый кадр стоит 6.5–8.5 мкс на
виджет в дереве на всём диапазоне и не различает, каким уровнем эти виджеты получены:
1771 виджет на `Full` и 1662 на `Simplified` стоят 11.8 и 12.2 мс. Отношение цены ноды
между уровнями — ровно отношение числа виджетов: 4.01 против 1.01. Это и есть
обоснование формулировки «бюджет в виджетах»: единица, в которой цена аддитивна,
одна, и перевод нод в неё — константа уровня.

**Предположение задачи про размер графа не подтвердилось.** Постановка исходила из
того, что «на 20 000 тот же зум материализует вчетверо больше». Замер: нет. Видимый
набор ограничен вьюпортом, а плотность у генератора одна, поэтому на любом зуме, где
вьюпорт полон, число видимых от размера графа не зависит; размер графа решает лишь,
на каком зуме граф кончится. Умножает дерево **плотность и размер ноды**: те же 5000
нод с вдвое меньшим шагом сетки дают на зуме 0.30 не 216 видимых, а 867, и на 0.21 не
442, а 1538 — то есть 3471 и 6155 виджетов, 26.2 и 42.0 мс на кадр. Поэтому парный
критерий поставлен по плотности, а не по числу нод: на числе нод он был бы вакуумным
(§20.9), потому что не мог бы упасть.

**Разброс видимого набора за кадр** — то, из чего берётся ширина гистерезиса, а не
вкусовая константа. За 40 кадров панорамирования: ×1.04 на зуме 0.15, ×1.10 на 0.21,
×1.13 на 0.10, ×1.15 на 0.30, ×1.18 на 0.50, до ×1.27–1.33 на малых числах. То есть
до ~22% в диапазоне, где бюджет вообще может сработать. Отсюда 0.25.

**Где принимается решение.** `cull` уже считает видимый набор до того, как решает,
уходить ли в дальнее поле; уровень можно решать там же — это умножение над готовым
числом, без второго прохода и без лишней раскладки. Решение переехало туда целиком;
`CanvasLayer` спускает вниз только «читаемый» уровень и бюджет.

**Цена дальнего поля растёт с графом, и бюджет её не берёт.** 5000 нод — 5.0–5.5 мс
(5000 прямоугольников, 9857 кривых); 20 000 на зуме 0.04 — 7.3–7.9 мс (11 600 и
18 944); на 0.02 — 27.5–32.9 мс (20 000 и 39 670). Виджетов при этом ноль. Ниже `Box`
уровня нет, значит бюджет здесь ничего не может предложить (§29.4).

**Бюджет — величина окна, а не канваса.** Замерено на `area-screen`: область с мелким
зумом, которую **никто не трогает**, дорожает кадр соседней области с 0.29 до 4.94 мс
— в шестнадцать раз, — притом что все её счётчики за 120 кадров нулевые
(`content_layouts`, `child_layouts`, `composes`, `builds`, `link_repaints`,
`far_repaints`). Область в дальнем поле держит ноль виджетов и всё равно стоит 3.10 мс.
Причина в `masonry_core/src/passes/paint.rs`: проход отрисовки обходит дерево окна
безусловно и доклеивает `append_transformed`-ом закэшированную сцену каждого чистого
виджета в план слоёв. Чистый виджет не перерисовывается — но его сцена собирается
заново каждый кадр, и пропустить неизменившееся поддерево апстрим пока не умеет
(`TODO - Handle damage regions`, xilem#789). Значит восемь канвасов, каждый честно
внутри собственного потолка, дают окно, вышедшее за потолок восьмикратно, и ни один
канвас этого увидеть не может.

### 29.2 Что построено

**`DetailBudget` рядом с `DetailThresholds`** — политика приложения, не константа
крейта, по тем же соображениям, что и пороги (§20.7):

```rust
pub struct DetailBudget {
    pub widgets: usize,          // потолок в виджетах
    pub full_cost: usize,        // виджетов на ноду при Full      (у примера 4)
    pub simplified_cost: usize,  // виджетов на ноду при Simplified (у примера 1)
    pub hysteresis: f64,         // 0.25 — из замеренного разброса
}
```

Цена уровня задаётся, а не считается: канвас строит ноду через `NodeSource` и внутрь
результата не заглядывает — сколько виджетов стоит уровень, знает приложение.

`DEFAULT_WIDGET_BUDGET = 1200` — **выведен, а не назначен**: 7 мкс на виджет из
таблицы выше дают 8–9 мс, то есть половину кадра 60 Гц, остальное остаётся дальнему
полю, связям и всему прочему в окне. Нижний конец проверен там же: обычная работа на
зуме 1–2 держит 50–100 виджетов — на два порядка внутри потолка, политика её не
касается.

**Строгое из двух правил.** `Detail` упорядочен от подробного к грубому, поэтому
решение — это `readable.max(affordable)`: читаемость по зуму и стоимость по бюджету
охраняют разные отказы (слайдер в три пикселя бесполезен, сколько бы он ни стоил;
четыре тысячи виджетов неподъёмны, как бы хорошо они ни читались), и снять любое из
них нельзя.

**Гистерезис асимметричен.** Остаться на уровне — влезть в бюджет; подняться на более
подробный — влезть в бюджет с запасом `hysteresis`. Видимое следствие честное и его
надо знать: один и тот же зум несёт разный уровень в зависимости от того, с какой
стороны в него пришли (в развёртке 20 000 нод на 0.10 — `Simplified` на пути вниз и
`Box` на обратном пути).

**Бюджет делится сверху.** `DetailBudget::split(ways)` и `area_screen::window_budget`:
экран раздаёт областям доли одного оконного потолка. Поровну — то, что область держит,
не зависит от её размера: маленькая область на мелком зуме держит столько же, сколько
большая.

**Счётчики.** `CanvasStats::visible` (нод в кадре, с виджетами или без) — вход
политики, и без него её нечем проверить; `CanvasCounters::level_switches` — выход.
Плюс `with_thresholds` и `with_budget`, потому что политика, до которой нельзя
дотянуться из приложения, политикой не является.

### 29.3 Замерено

Та же развёртка, тот же вьюпорт, с бюджетом по умолчанию:

| Зум | Было | Стало |
|---:|---|---|
| 0.30 | Full, 867 виджетов, 5.5 мс | Full, 867, 6.0 мс |
| 0.21 | Full, **1771**, 11.8 мс | Simplified, **445**, 2.7 мс |
| 0.15 | Simplified, 867, 7.2 мс | Simplified, 867, 6.6 мс |
| 0.10 | Simplified, **1662**, 12.2 мс | Box, **3**, 2.6 мс |
| 0.06 | Simplified, **3808**, 30.7 мс | Box, 3, 3.5 мс |
| 0.0501 | Simplified, **4507**, 31.5 мс | Box, 3, 4.2 мс |

Максимум по всей развёртке (обе ветви): **867 виджетов против 4507**, худшая точка
6.6 мс против 31.5. На вчетверо более плотном графе — 870 против 6155.

Окно из восьми областей, в каждой обзорный зум, панорамирование в одной:
**2931 виджет и 11.8 мс на кадр против 33 виджетов и 6.1 мс** с разделённым бюджетом.
Остаток в 6.1 мс — восемь сцен дальнего поля, и это ровно то, чего бюджет не берёт
(§29.4).

Пять новых критериев, все счётчиковые (§20.9):

| Критерий | Замерено | Граница | Сломано нарочно — даёт |
|---|---:|---:|---:|
| ни один зум не выводит дерево за бюджет | 867 | < 1440 виджетов | 3808 |
| вчетверо более плотный граф не держит больше | 870 | < 1308 виджетов | 6155 |
| колебание зума у границы не переключает уровень | 0.03 | < 0.2 переключений/кадр | 1.00 |
| обычная работа политику не задевает | 0.00 | < 0.05 переключений/кадр | — |
| области делят один бюджет, а не берут по одному | 33 | < 1280 виджетов в окне | 2931 |

Гистерезис судится по **переключениям уровня**, а не по сборкам на кадр, как
предполагала постановка: сборки идут и при обычном пане — ноды входят в кадр, — так что
порог на них пришлось бы задрать выше нормального фона и он перестал бы ловить
дрожание. Переключение уровня — это само решение, и его нормальное значение ноль.

Последний столбец — проверка на вакуумность, и она обязательна: каждый критерий
сломан на живом коде (бюджет отключён; гистерезис в ноль; доля области заменена на
полный бюджет) и наблюдался падающим. Критерий про колебание зума калибруется по
графу — потолок ставится равным числу видимых нод на тестовом зуме, — иначе он
проходил бы, просто ни разу не оказавшись у границы.

Прогон `cargo make bench-canvas` — 9 с, `bench-areas` — 14 с; развёртка по зуму идёт в
обе стороны на двух графах и лежит в JSON-отчёте отдельным разделом `zoom_sweep`.

### 29.4 Чего бюджет не делает

**Дальнее поле стало потолком.** 20 000 нод на зуме 0.02 — 33 мс на кадр при нуле
виджетов: цена сцены, а не дерева. Бюджет выбирает уровень, а ниже `Box` уровня нет,
поэтому предложить он ничего не может. Устройство дальнего поля задача явно исключала
(§20.6), и вывод остаётся следующей работой: потолок для дальнего поля надо ставить в
**командах отрисовки**, а рычаги для него — запас области (`FAR_OVERSCAN`), огрубление
записи и отказ от кривых на обзорном зуме.

**Гистерезис не бесплатен для восприятия**: уровень зависит от направления подхода
(§29.2). Это сознательный размен на пересборку всех видимых нод при каждом дрожании.

**Доли окна раздаются поровну и не пересматриваются.** Область, показывающая три ноды,
держит свою долю впустую. Брокер, перераспределяющий неиспользованное, — очевидное
продолжение, но он требует общего состояния между областями, а сейчас его нет и
измеримой нужды в нём тоже нет.

**Не пересмотрено**: контролы только под курсором (§20.7a), устройство дальнего поля
(§20.6), путь кадра на экран (§27).

### 29.5 Что это меняет в плане §16

Пункт 10 («`blazy-canvas` в продовом виде: spatial index, LOD, слой связей») закрыт в
части LOD: уровень выбирается по стоимости, а не по одному лишь зуму, и стоимость
измерена. Пункт «участие в damage regions (#789)» из раздела «потом» получил цену:
пока апстрим доклеивает сцену чистого поддерева каждый кадр, любой бюджет обязан
ограничивать **сумму по окну**, а не выбирать уровень на канвас, и простаивающая
область остаётся статьёй расхода, которую нельзя обнулить у себя. Это второй
независимый аргумент за #789 после §20.6a.

## 30. Две области над одним графом расходились (найдено в работе)

### 30.1 Что происходило

Экран из областей держит **один** `GraphModel` на все области — §21 прямо называет
несколько видов одной модели нормальной раскладкой, и весь пример на этом построен.
Но перетаскивание ноды в одной области двигало её только там: в остальных нода
оставалась на прежнем месте навсегда. Нашёл это не тест и не замер, а взгляд на окно.

### 30.2 Почему

Канвас держит геометрию в своих `slots` (§20.3: геометрия у всех нод, виджет — только
у видимых), засеянных из модели при постройке. `store_child_pos` писал в слот и не
писал обратно в модель — а `GraphModel` и не мог принять запись: `set_value` и
`set_checked` у него были, `set_pos` не было вовсе. То есть для двух полей состояния
ноды источником истины была модель, а для третьего — вид, и нигде это не было записано.
§20.2 говорит «состояние живёт в модели, потому что виджета большую часть времени не
существует»; позиция под это правило не попала, потому что она нужна канвасу и без
виджета — и именно поэтому у канваса завелась своя копия.

Рядом вскрылся второй дефект, независимый. Масонри-шный `Checkbox` **сам себя не
переключает**: он отправляет `CheckboxToggled(!checked)` и оставляет состояние тому, кто
владеет истиной (так написано в его собственной документации). `GraphNode::on_action`
писал модель и свою копию, но `Checkbox::set_checked` не звал — значит клик по галочке
не переключал её визуально, а второй клик отправлял **то же самое** целевое состояние, и
модель залипала на `true`. Тест `controls_write_back_to_the_model` проверял один клик и
этого видеть не мог.

### 30.3 Починка

Три шва в `blazy-canvas`, все с пустыми реализациями по умолчанию:

* `NodeSource::attached(canvas)` — канвас сообщает источнику свой id при первой
  раскладке. Раньше id взять было неоткуда: `CanvasLayer` существует до того, как
  становится виджетом. Это же делает регистрацию вида автоматической — ни один
  конструктор в примере не поменялся.
* `NodeSource::moved(index, pos, peers)` — канвас сообщает о перетаскивании. Приложение
  пишет позицию в модель и называет остальные виды; фан-аут делает канвас, потому что
  контекст виджета есть только у него. `peers` — переиспользуемый буфер, как
  `candidates` у пространственного индекса.
* `CanvasLayer::update_child(index, f)` — дотянуться до виджета ноды, если он сейчас
  есть. Нод без виджета чинить не нужно: они читают модель при следующей постройке.

В примере: `GraphModel::set_pos`, реестр видов, `GraphSource::attached`/`moved`,
`GraphNode::broadcast` — сначала себя через `mutate_self_later`, потом остальные виды —
и `GraphNode::reload`, читающий состояние из модели обратно в виджет и в контролы.
Собственный reload здесь не роскошь: он и есть починка галочки.

Рассылка идёт через `mutate_later`: соседний канвас — не ребёнок этого виджета, а
mutate-проход единственное место, где чужой виджет можно менять законно. Он идёт до
следующей раскладки, поэтому другие области показывают изменение **в том же кадре**.

### 30.4 Цена

Перетаскивание ноды на экране из восьми областей над одним графом (5000 нод, 60 кадров,
release): **0.341 мс/кадр без рассылки против 0.882 мс/кадр с ней**. Втрое — и это
работа, которую нельзя не делать: семь соседних областей обязаны перерисовать сдвинутую
ноду. Раскладок нод при этом 0.00 на кадр: сосед переставляет ноду, но не перекладывает
её (§20.5), то есть цена — перерисовка, а не layout.

### 30.5 Что это добавляет к дисциплине §20.9 и §28.4

**Разделяемую модель проверяют двумя видами, а не одним.** Все тесты канваса до сих пор
смотрели на один вид, и ни один из них не мог увидеть расхождения в принципе: при одном
виде «истина в модели» и «истина в виде» неразличимы. Тест на два вида — это то же
самое, что развёртка, которая возвращается (§28.4): без второй стороны проверяется
половина утверждения.

**Обратный клик — часть теста переключателя.** Один клик проверяет, что что-то
произошло; второй — что произошло именно *переключение*, а не залипание.

**Виджет апстрима может не хранить своё состояние.** `Checkbox` — контролируемый
компонент: состояние принадлежит владельцу, и владелец обязан его вернуть. Проверять это
надо по документации виджета, а не по интуиции, и лучше — тестом, который отличает
переключение от залипания.

## 31. Кадр стоит команд отрисовки, а не геометрии (замерено)

§29 закрыл бюджет **виджетов** и в §29.4 назвал то, чего бюджет не берёт: на обзорном
зуме дерево пустое, а кадр всё равно дорогой. Задача — `issues/far field draw commands.md`.

### 31.1 Единица, в которой считается вторая половина кадра

Проход отрисовки собирает `VisualLayerPlan` заново на каждом кадре и доклеивает в него
закэшированную сцену каждого виджета (`masonry_core/src/passes/paint.rs`; §29.1). Значит
платится не за то, что изменилось, а за то, что **лежит в сцене**, и простаивающая
область платит столько же, сколько рабочая. Разведка задачи показала, за что именно:

| | своей командой | внутри общей |
|---|---:|---:|
| кривая связи | 0.428 мкс | 0.029 мкс (×15) |
| прямоугольник ноды | 0.211 мкс | 0.014 мкс (×15) |

**Платится счёт команд, а не их содержимое.** Замена кубиков прямыми не дала ничего
(6.43 мс против 5.27) — сложность геометрии ни при чём; сложение всех связей в один
`BezPath` дало 1.40 против 5.27.

Отсюда счётчик, на котором стоят новые критерии: **число команд в плане слоёв окна**,
`bench_utils::plan::commands`. Он читается из `VisualLayerPlan::layers` и
`Scene::commands()` — оба публичны, так что цена кадра видна без участия приложения,
которое рисует дальнее поле и могло бы о ней умолчать. И он **оконный**, а это та же
поправка, что и у бюджета виджетов: кадр принадлежит окну, и ни один канвас суммы не
видит.

### 31.2 Батч — это один путь из N подпутей

Все записанные кривые идут в **один путь на стиль** и обводятся одной командой. Разрыв
между связями — `move_to`: `kurbo::stroke` на нём вызывает `finish` и закрывает
предыдущий подпуть его капами (`stroke.rs:314`), поэтому соединительного отрезка между
концом одной связи и началом следующей не возникает, а точки подключения могут лежать
где угодно. То же для дальнего поля: `NodeSource::paint_far` теперь получает **весь
набор** `&[(usize, Rect)]`, а не ноду за нодой, — прежняя сигнатура физически навязывала
приложению самый дорогой способ рисовать. Пример группирует по шести тинтам.

**Цена — порядок отрисовки между связями стал неопределённым.** Кривые группируются по
стилю, а не по индексу, поэтому «последняя нарисованная — верхняя» больше не выводится из
`recorded()`. Хит-тест переписан под это: он возвращает *какую-то* из связей под
указателем, а не верхнюю. Альтернатива — команда на каждую смену стиля, то есть ровно та
цена, которую батч и убирает. Что сохранилось — свойство, которое важно: кандидаты для
указателя это в точности то, что нарисовано.

Ключ батча — не цвет, а весь стиль команды: кисть, `Stroke` и трансформ кисти. Связи
разной толщины или с пунктиром — разные команды; градиент на связь не батчится вовсе.

**Батч не пиксельно тождествен, и это надо знать.** Две кривые, выходящие из одной точки,
перекрываются, и их сглаженное покрытие композитится один раз внутри общей команды против
двух раз в отдельных. В снапшоте `canvas_with_links` это сдвинуло **50 пикселей из
46 800**, максимум на 25 из 255, все — на перекрытиях. Снапшот перевыпущен; тест
`overlapping_curves_composite_once_in_a_batch` держит это как известное свойство, а
`a_batched_stroke_draws_what_separate_strokes_draw` — что во всём остальном картинка та
же и никакой отрезок подпути не соединяет.

### 31.3 Ширина связи осталась в координатах канваса

Минимум ширины в экранных пикселях (как рисует связи Blender) рассмотрен и **отклонён**.
В закреплённом `imaging` нет non-scaling stroke: ширина живёт в пространстве геометрии, а
трансформ прикладывается целиком (`paint.rs:1106`, `draw.prepend_transform`). Постоянная
экранная ширина потребовала бы, чтобы **записанная** ширина зависела от масштаба, — а
сцена записывается в координатах канваса именно затем, чтобы пан и зум переиспользовали её
нетронутой (§20.6a). То есть у сцены появилась бы вторая ось инвалидации, механизм
квантования, счётчик и критерий — ради линии в две десятых пикселя. Рисовать связи в
`CanvasLayer`, где координаты экранные, не выход: тогда сцену перекодирует каждый пан.

### 31.4 Отказ от коротких дуг — правило рядом с двумя другими, а не внутри уровня

`LinkStyle::min_screen_length` (2 логических пикселя): связь, чей габарит на экране
короче, не рисуется. Три решения, каждое со своей причиной.

**Не привязано к уровню детализации.** §29 специально развёл читаемость и стоимость; если
повесить «нет связей» на `Detail::Box`, то бюджет виджетов начнёт решать, показывать ли
структуру графа. Правило ключёвано на собственной экранной геометрии связи и потому гаснет
в крупном масштабе само — оговорка «только в дальнем поле» ему не нужна.

**Считается при выборе набора, а не при отрисовке.** `refresh_links` перевыбирает набор
только когда вьюпорт покидает область, так что новой инвалидации правило не заводит.
Между перевыборами набор слегка устаревает — связь, укоротившаяся после выбора, ещё
какое-то время рисуется, — и это видно в развёртке: на зуме 0.10 на пути вниз спрятано 0,
на обратном пути 1015. Ошибки в другую сторону нет.

**Отрисовка и пикинг читают один набор**, поэтому спрятанная связь исчезает из картинки и
из-под указателя одним действием. Это то, ради чего `link_curve` сделана общей функцией.

Габарит меряется по bounding box кривой, а не по хорде: дуга с `reach = max(|dx|·0.5, 24)`
может уйти вбок и вернуться, и коробка — консервативная мера, никогда не меньше стороны.

**Прикидка задачи не подтвердилась, и развёртка её исправила.** Задача считала, что выше
зума 0.033 правило не сработает ни на чём: шаг сетки 220 минус ширина ноды 160 даёт зазор
60 канвасных единиц. Замер: на 0.10 прячется 927–1015 связей. Причина — джиттер генератора
(±30 по каждой оси), из-за которого зазор распределён по [0, 120], и у части соседей ноды
почти касаются. Эти связи действительно короче двух пикселей. Что подтвердилось: **пока
хоть одна нода на экране остаётся виджетом, правило не прячет ничего** — 0 на всех точках
развёртки, на обоих графах и обеих ветвях.

### 31.5 Замерено

Профиль `bench`, 5000 нод, вьюпорт 1100×750. «Было» — тот же код с разобранным батчем
(команда на ноду, команда на связь), то есть проверка на вакуумность и замер сразу:

| Сценарий | Команд было | Стало | мс было | Стало |
|---|---:|---:|---:|---:|
| пан, виден весь граф | 13 567 | **13** | 2.300 | **0.285** |
| зум 0.04, дальнее поле | 13 567 | **13** | 1.695 | 0.351 |
| зум 0.10, дальнее поле | 12 541 | **13** | 1.539 | 0.276 |
| зум 0.21, `Simplified` | 5 321 | 2 217 | 1.654 | 1.232 |
| зум 1.00, `Full` | 438 | 235 | 0.246 | 0.237 |

**13 команд** — на любом зуме в дальнем поле и на обоих графах: шесть тинтов, связи одной
обводкой и мебель редактора. При 5000 видимых нод и ~8500 записанных кривых. Даже на зуме
1, где связей всего 96, батч вдвое уменьшает план.

Окно из восьми областей над одним графом, каждая на зуме 0.06, панорамирование в одной:

| | Виджетов | Команд | мс/кадр | Худший |
|---|---:|---:|---:|---:|
| было | 33 | 23 575 | 3.049 | 6.517 |
| стало | 33 | **127** | **0.611** | 0.993 |

Виджетов поровну — цена целиком лежала вне бюджета §29, и счётчик виджетов её увидеть не
мог в принципе.

Три новых критерия, все счётчиковые, все сломаны на живом коде:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---:|
| кадр дальнего поля стоит числа стилей, а не нод | 13 | < 64 команд | 8538 |
| область на обзоре наполняет план цветами, а не нодами | 127 | < 512 команд в окне | 8495 |
| ни одна связь не спрятана, пока ноды ещё виджеты | 0 | < 1 | 1530 |

Побочно вскрылось, что при поломке третьего падает и `picking_means_the_same_at_every_zoom`:
спрятанная связь перестаёт выбираться указателем, и критерий пикинга это видит. Сцепка
«не нарисовано — не выбирается» проверена не только тестом.

Отдельного критерия «правило не завело новых перезаписей сцены» не понадобилось:
`pan_does_not_reselect_links` и `dragging_a_linked_node_does_not_reselect_links` меряют
ровно это и остались на нуле.

### 31.6 Чего это не делает

**Потолка в командах нет, и он не понадобился.** Задача допускала оба исхода. Замер выбрал
первый: после батча дальнее поле стоит числа стилей, и ограничивать нечего — счёт команд
стал **гейтом**, а не политикой. Потолок понадобится приложению, которое даёт стиль на
ноду или на связь: батч сжимается до числа различных стилей, а не до единицы.

**Мерялась CPU-половина кадра** — проходы и сборка плана (`TestHarness::redraw`).
Растеризация не мерялась; меньше команд должно означать меньше draw objects, но это
отдельный замер на `bench-shell`, и на обоих путях кадра (§27.4).

**Рычаги дальнего поля не тронуты**: `FAR_OVERSCAN` остался 0.5, огрубление записи не
делалось. После батча экономить нечего; оба остаются в запасе.

**Не пересмотрено**: устройство дальнего поля (§20.6), контролы только под курсором
(§20.7a), апстримный #789 — батч уменьшает то, что он сэкономил бы, и ждать его не надо.

### 31.7 Что это меняет в плане §16

Пункт 10 («`blazy-canvas` в продовом виде») закрыт ещё и в части слоя связей: он стоит
одной команды на стиль независимо от числа рёбер. Пункт 8 («`blazy-compose`: per-area
render-to-texture») подешевел в приоритете — после батча у простаивающей области в плане
десяток команд, кэшировать нечего; он остаётся уместным для области, держащей много
**виджетов**, а это ровно то, что запрещает бюджет §29.

## 32. Вторая половина кадра: растеризация (замерено)

§31 свёл дальнее поле к 13 командам и 0.285 мс на кадр — но мерялась **CPU-половина**:
проходы Masonry и сборка `VisualLayerPlan` (`TestHarness::redraw`). §31.6 честно назвал
вторую половину неизмеренной и отложил её. Задача — `issues/raster half of the frame.md`.

Замерено на сцене-заменителе дальнего поля: 8000 коротких кривых во вьюпорте 1100×750,
собранных в разное число команд обводки при **одной и той же геометрии** (16 004 сегмента
во всех строках, что и подтверждает: чернил поровну). Машина — Intel UHD (CML GT2),
профиль `bench`, 12 кадров на строку; разброс между прогонами ±20%, поэтому ниже важны
отношения, а не абсолютные миллисекунды.

### 32.1 Счётчик у растеризатора всё-таки есть, и устройство ему не нужно

Задача допускала, что счётчика не найдётся и придётся обойтись одним `Kind::Timing`.
Нашёлся, и лучше ожидаемого: `imaging_vello` реэкспортирует `vello`, а его
`VelloSceneSink` публичен, — значит сцену можно **закодировать без девайса** и прочитать
`Scene::encoding()`: `draw_tags.len()` это объекты отрисовки, `n_path_segments` —
сегменты. Оба числа точны и машинонезависимы, то есть годятся в критерий (§20.9), и в
отличие от всех остальных GPU-чисел здесь существуют на раннере без видеокарты.

Первое, что этот счётчик говорит: **команда плана — это ровно один объект отрисовки**.
Значит `bench_utils::plan::commands` §31 считает не свою внутреннюю величину, а вход
растеризатора. Второе: **масштаб устройства не меняет кодирование** — объекты и сегменты
на 1.0 и 2.0 совпадают до штуки, что и есть §9 и §23.4, проверенные со стороны
растеризатора, а не со стороны layout.

У CPU-растеризатора эквивалента нет: `imaging_vello_cpu` отдаёт рендерер и ничего о
работе внутри. Там отвечают только часы.

### 32.2 Растеризация не следует за числом команд

Одна и та же сцена, зум 1.0, ширина обводки 0.5 px:

| Команд в плане | Объектов | План, мс | Растеризация CPU, мс | GPU, мс |
|---:|---:|---:|---:|---:|
| 2 | 2 | 0.045 | 34.0 | 24.2 |
| 9 | 9 | 0.099 | 40.8 | 24.7 |
| 65 | 65 | 0.229 | 39.9 | 27.2 |
| 513 | 513 | 0.709 | 52.0 | 31.1 |
| 2049 | 2049 | 1.459 | 39.2 | *не нарисовано, §32.4* |
| 8001 | 8001 | 3.675 | 39.3 | 35.9 |

**Гипотеза §31.6 не подтвердилась.** Объекты отрисовки падают вместе с командами ровно
1:1 — и растеризация за ними не идёт. Сборка плана дешевеет в **80 раз**, CPU-растеризация
не меняется вовсе (разброс между строками не больше разброса между прогонами), GPU
дешевеет в **1.5 раза**. Батч §31 экономит счёт команд, а растеризатор платит за сегменты
и пиксели, которых батч не убавляет ни одного.

### 32.3 Кадр дальнего поля — это растеризация, и он не влезает в 60 Гц

Числа из той же таблицы: 0.045 мс на план против 34 мс на пиксели. **Половина кадра,
которую §31 уменьшил в восемь раз, составляет одну тысячную кадра.** На кривую это 4.2 мкс
(CPU) и 3.0 мкс (GPU) против 0.029 мкс на запись кривой внутри общей команды (§31.1) — то
есть нарисовать кривую в **сто с лишним раз** дороже, чем записать её.

Две оставшиеся оси слабее, чем ожидалось, и это тот же вывод с другой стороны:

* **Чернила.** Одна команда, те же кривые, ширина 0.1 → 8 px (покрытие 23% → 90%):
  CPU 46 → 53 мс, GPU 22 → 22 мс. Роста в разы нет.
* **Масштаб устройства.** ×2 это ×4 пикселей, а цена растёт в 1.7 (CPU) и 1.4 (GPU) раза:
  58.5 и 34.8 мс против 34.0 и 24.2.

Обе оси говорят одно: платится **за сегменты**, а не за площадь и не за команды. У
дальнего поля сегментов столько же, сколько кривых, и уменьшить их можно только тем, что
§31 оставил в запасе, — `FAR_OVERSCAN`, огрублением записи и правилом коротких связей.

И главное число: 8000 кривых стоят 34 мс на CPU-пути и 24 мс на GPU-пути при бюджете
16.7 мс на кадр при 60 Гц. **Дальнее поле не влезает в кадр ни на одном из путей** — на
этой машине, на графе того размера, на котором §31 объявил кадр стоящим 0.285 мс.

### 32.4 Кадр, которого не было (найдено в работе)

Первая версия замера показала, что на GPU-пути 513 команд рисуются **втрое быстрее**
одной. Разгадка нашлась, только когда после каждого кадра стали читать текстуру обратно:
таких кадров не было вовсе. `GpuFrames::draw` возвращает `Ok`, `wgpu` не сообщает ничего,
в текстуре остаётся **предыдущий** кадр — а «отрисовка» стоит втрое дешевле, потому что
её не было.

Проверка, которая это поймала, устроена так: сцена рисуется **двумя тинтами через кадр**, и
полоса в 32 строки сравнивается с обоими эталонами CPU-пути; кадр обязан быть ближе к
своему. Порога тут нет и быть не может — зазор между «две растеризации сглаживают
по-разному» и «в текстуре чужой тинт» на полупиксельной обводке слишком узок, чтобы в него
поместилось число (пробовали: пропустило три строки). Ровно половина кадров каждой битой
строки не проходит проверку — то есть не рисуется **ни один**, а совпадают те, у которых
тинт случайно тот же, что у последнего удавшегося.

Что известно про условия: 512–2048 команд обводки, каждая с габаритом во весь экран, при
цели 2200×1500; на 1100×750 те же сцены рисуются, на 8001 команде (габарит каждой — одна
кривая) рисуются, на 1–65 командах рисуются. Похоже на переполнение внутренних буферов
vello, которое коарс-стадия проглатывает молча. Что проверено и не помогло: пересоздание
`VelloRenderer` на ресайзе, ожидание GPU после каждого кадра, оба порядка обхода
масштабов. Что усугубляет: **чередование размера цели** — при нём пустые кадры появляются
и там, где при стабильном размере их нет. Поэтому таблица §32.2 обходит масштабы внешним
циклом: бенчмарк, провоцирующий дефект, которого он не измеряет, меряет шум.

Для хоста отсюда следует неприятное: **обнаружить это без обратного чтения нечем**, а
обратное чтение — ровно то, что §27.4 запрещает на пути кадра. Задача заведена отдельно:
`issues/frames the gpu never drew.md`.

`GpuFrames::read_pixels` и `read_rows` появились здесь же и считаются как `readbacks`,
поэтому ноль в `gpu_frames_are_not_read_back` теперь подпёрт парой — как и байты кадра в
§27.4: критерий `the_readback_counter_is_not_a_stub` падает, если счётчик перестанет
замечать чтение.

### 32.5 Замерено

Шесть новых критериев, все проверены поломкой живого кода:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---:|
| команда плана — один объект отрисовки | 0 | < 1 строки расхождения | 10 |
| дальнее поле — горстка объектов, а не по объекту на кривую | 2 | < 64 | 8001 |
| растеризатору дают ту же сцену на любом масштабе устройства | 0 | < 1 строки | 4 |
| в каждом замеренном кадре что-то есть | 0 | < 1 пустого кадра | 10 |
| чтение кадра обратно считается за readback | 0 | < 1 | 1 |
| сборка плана — доля от отрисовки (`Kind::Timing`) | 0.002 | < 0.5 | 1.44 |

Последний — единственный временной, и его запас 250-кратный: он держит утверждение §32.3
и упадёт, если цена кадра когда-нибудь вернётся в план. Ни одна точка развёртки к границе
не подходит.

### 32.6 Чего эта работа не делает

* **CPU-растеризатор остаётся без счётчика.** `imaging_vello_cpu` не отдаёт ничего о
  своей работе, поэтому про блит-путь здесь говорят только часы (и потому все шесть
  критериев выше — про кодирование и про кадр, а не про его время).
* **Сцена — заменитель, а не канвас.** Расположение крейтов запрещает `blazy-shell`
  зависеть от примера (CLAUDE.md, «где живёт бенчмарк»), поэтому дальнее поле собрано
  в самом бенче: 8000 коротких кривых того же порядка, что 8500 связей §31.5. Настоящая
  сцена сверх этого рисует ещё 5000 прямоугольников нод — то есть числа §32.3 скорее
  занижены.
* **Дальнее поле не переделано.** Задача мерила то, что построил §31; что делать с
  сегментами — следующая работа.
* **Половина показа не тронута**: перестановка каналов и блит в свопчейн те же, что в
  §27.4, и от числа команд не зависят.

### 32.7 Что это меняет в плане §16

**Пункт 8 (`blazy-compose`, текстура на область) возвращается вверх, и §31.7 в этой части
неверен.** Там сказано: после батча у простаивающей области в плане десяток команд,
кэшировать нечего. Кэшировать есть что — не команды, а **сегменты**: те же десять команд
несут восемь с половиной тысяч кривых, и растеризатор перерисовывает их в каждом кадре,
хотя в области ничего не изменилось. Именно это убирает текстура на область.

**Damage regions (#789) дорожают по той же причине.** §31.6 говорил, что батч уменьшает
то, что #789 сэкономил бы. Для плана — да; для растеризации — нет, и апстримный механизм
«не перерисовывать то, что не менялось» бьёт ровно в ту половину кадра, которая теперь
известна как дорогая.

**Рычаги дальнего поля перестают быть запасом.** `FAR_OVERSCAN`, огрубление записи и
порог коротких связей уменьшают число кривых, а цена кадра идёт за кривыми.

**Пункт 1 Фазы 1 (`blazy-shell`) получает новую незакрытую дыру** — §32.4, кадр, который
GPU молча не нарисовал.

## 33. Кадр, которого не было: причина и защита (замерено)

§32.4 нашёл дефект: GPU-путь отдаёт `Ok`, а кадра нет — в текстуре остаётся предыдущий.
Задача — `issues/frames the gpu never drew.md`. Здесь причина, отчёт наверх и то, что
хост делает до исправления.

### 33.1 Причина: буфер тайлов размером с константу

`vello_encoding::BufferSizes::new` раздаёт буферы bump-аллокатора числами, которые не
зависят ни от сцены, ни от размера цели, и говорит об этом прямо:

> The following buffer sizes have been hand picked to accommodate the vello test scenes
> as well as paris-30k. These should instead get derived from the scene layout using
> reasonable heuristics.

Тайлов там `1 << 21`. Сцена, которой нужно больше, переполняет коарс-стадию — и **никто
об этом не узнаёт**: обратное чтение флагов bump-аллокатора включено только с фичей
vello `debug_layers` (`let robust = cfg!(feature = "debug_layers");`), а синхронный
`render_to_texture` не отдаёт их вовсе.

Проверено **воспроизводителем без Masonry и без `imaging`** — vello 0.9 и wgpu 29, путь
= диагональ во весь кадр, так что габарит каждого равен цели:

| Цель | Тайлов на путь | Рисуется | Не рисуется |
|---|---:|---|---|
| 1100×750 | 3243 | 646 путей (2 094 978 тайлов) | 647 путей (2 098 221) |
| 2200×1500 | 12 972 | 161 путь (2 088 492) | 162 пути (2 101 464) |

Граница совпадает с `1 << 21 = 2 097 152` **с точностью до пути** и предсказывается
арифметикой: тайл 16×16, на путь — тайлы его габарита, **обрезанного кадром**. Обрезка
проверена, а не предположена: пути втрое больше кадра границу не сдвигают ни на путь.
Машина — Intel UHD (CML GT2), Mesa 25.2.8, Vulkan.

**Свежая версия ведёт себя так же.** vello 0.10 (актуальная на крейтс.ио) проверена тем
же воспроизводителем: те же 646/647 и 161/162, тот же `Ok` на кадре, которого нет. В
исходниках не изменилось ни одно из трёх мест — константа `1 << 21` с тем же
комментарием «hand picked», `robust = cfg!(feature = "debug_layers")`, `tile: 0` в
оценщике. То есть это не хвост, который вот-вот отвалится сам: отчёт наверх подаётся
против 0.10, а не против нашего пина.

Это объясняет и немонотонность §32.4, которая казалась бессмысленной: 513 команд на
2200×1500 — это 6.65 млн тайлов (мимо), те же 513 на 1100×750 — 1.66 млн (рисуется), а
8001 команда рисуется потому, что каждый её путь — одна кривая с крошечным габаритом.
Предиктор не «сколько команд», а **сколько путей × какой они величины**.

### 33.2 Читаемой диагностики нет ни одной

* `Scene::bump_estimate` существует и работает без устройства — но тайлы он не считает:
  `BumpEstimator` начинается с `// TODO: support binning / ptcl / tile`, а `tally`
  возвращает `tile: 0`. Именно тот буфер, который переполняется, не оценивается.
* Робастный путь спрятан за фичей `debug_layers`, и `imaging_vello` его не включает и
  наружу не отдаёт.

Отчёт для апстрима лежит в `rnd/upstream/vello-silent-tile-overflow.md` (рядом с ним
`vello-silent-tile-overflow.rs` — воспроизводитель целиком, одна зависимость
`vello = "0.10"`) — единственные файлы прозы и кода в репозитории, написанные для
апстрима, поэтому по-английски и против его свежей версии.

**У апстрима это известно, и исправление написано, но не влито.** Проверено 2026-08-25:

* **#366 «Strategy for robust dynamic memory, readback, and async»** — открыт с сентября
  2023, зонтичный. Первая же из перечисленных там стратегий — «заранее заданные размеры,
  молча падать при переполнении», то есть нынешнее поведение выбрано сознательно. Чего в
  обсуждении нет — как эта стратегия выглядит снаружи: окно перестаёт обновляться, и
  никто ничего не сообщает.
* **#606 «Robust memory allocation handling»** (DJMcNab, открыт с июня 2024, последняя
  правка март 2026, не черновик) делает ровно то, что нужно: отмена конвейера, чтение
  bump-буфера от позапрошлого кадра, перераспределение. Ждёт ревью около двух лет.
* **#788** — тот же подход, но в другом буфере: `bin_data` уходит в минус на очень
  большом числе картинок и в релизе заворачивается, давая доступ за границы.

На `main` не изменилось ничего из трёх мест, а `render_to_texture_async` — единственная
точка входа, способная вернуть `BumpAllocators`, — теперь **помечена устаревшей**. То
есть путь, по которому вызывающий мог бы узнать о переполнении, не расширяется, а
сужается. Наша защита §33.3 — не подпорка на неделю до чужого релиза. Три просьбы по
возрастанию цены: **сообщать** (флаг, ошибка), **оценивать** (научить `BumpEstimator`
тайлам), **растить** (то, что предлагает комментарий в самом vello). Стратегия §17 —
контрибьютить, а не форкать, — здесь и применяется: чинить у себя нечего, у нас есть
только защита.

### 33.3 Защита у нас: посчитать до отправки

`blazy_shell::tile_demand(scene, frame)` проходит составленную сцену и складывает тайлы
по габаритам, обрезанным кадром, — ту самую арифметику, что предсказала границу.
Заливки, обводки и клипы считаются по габаритам, глиф — по кегль-квадрату, группы и
картинки не считаются (тайлов на путь они не занимают). Все приближения **в сторону
завышения**: отказать зря — видно и сообщается, пропустить — снова тишина.

`GpuFrames::draw` отказывается рисовать сцену свыше `TILE_BUDGET`: `PresentError::
SceneTooLarge { tiles, budget }`, счётчик `frames_refused`, и на GPU не уходит ничего.
Окно (`window::redraw`) на такой отказ пишет предупреждение **на переходе** — не
шестьдесят раз в секунду — пропускает кадр и продолжает жить. Разница с тем, что было,
не в картинке: кадра нет в обоих случаях. Разница в том, что раньше об этом не знал
никто.

**Цена проверки замерена, а не объявлена малой, и после замера уменьшена.** Обход сцены
стоил 1.78 мс на батченном дальнем поле — 5% кадра, но в сорок раз больше сборки плана
(§32.3), то есть самая дорогая CPU-работа кадра после самой растеризации. Поэтому
`tiles_over_budget` сначала считает **потолок за две операции**: ни одна сцена не может
запросить больше, чем её число команд × тайлы кадра, потому что ни один путь не платит
больше, чем за весь кадр. Дальнее поле — дюжина команд, а дюжина кадров тайлов это 8%
бюджета, так что до обхода дело не доходит вовсе: **0.000 мс**. Обход остаётся для сцен,
которые в потолок не влезли, и стоит там 1.03 мс на 8001 команде против 48.7 мс её же
растеризации.

Дешёвый вариант габарита — коробка по контрольным точкам вместо точных экстремумов —
пробовался и дал 2% разницы: время уходило на обход сцены, а не на арифметику. Отсюда и
вывод, что резать надо не арифметику, а сам обход.

`GpuFrames::draw_unchecked` — дверь для бенчмарка, и она нужна: доказать, что проверка
не слепая **и** не параноидальная, можно только нарисовав то, что она отвергла, и
посмотрев на результат.

### 33.4 Замерено

В развёртке §32.2 из двадцати четырёх GPU-строк отказано шести: 2049 команд на масштабе
1 (обе ширины), 513 и 2049 на масштабе 2. Это **ровно те строки**, где §32.4 видел
неотрисованные кадры, и ни одной лишней. Строк с `!` — то есть кадров, выданных за
нарисованные, — не осталось.

Три новых критерия, все проверены поломкой:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---|
| ни одно время не снято с кадра, который растеризатор пропустил | 0 | < 1 строки | 1 (бюджет 1<<40) |
| каждая отвергнутая сцена действительно не рисуется | 0 | < 1 | 1 (бюджет 1<<19) |
| развёртка содержит сцену свыше бюджета | 0 | < 1 | 1 (бюджет 1<<40) |

Третий — не украшение: без него первые два проходят на развёртке, которая до бюджета не
доходит.

Плюс тесты, которым GPU не нужен: `the_boundary_is_where_vello_puts_it` держит нашу
арифметику на измеренных 646/647 и 161/162, `a_path_outside_the_frame_pays_for_what_is_
inside` — на том, что габарит режется кадром, `a_far_field_frame_is_far_from_the_budget`
— на том, что канвасу до этой границы двенадцать раз по столько (13 путей на HiDPI-окне
это 168 636 тайлов из 2 097 152, то есть 8%).

### 33.5 Чего это не делает

* **Апстрим не вылечен.** Кадр по-прежнему не показывается — просто теперь об этом
  говорят вслух. Настоящее исправление приходит сверху (§33.2).
* **Константа привязана к пину, и пин пока никуда не двинется.** `TILE_BUDGET` — это
  `1 << 21` из vello, а не часть публичного API. В 0.10 она та же, так что переход
  ничего здесь не менял бы, — но и перейти сейчас нельзя: `imaging_vello` 0.0.2 знает
  только vello 0.7/0.8/0.9, а `vello-0-10` у него нет (wgpu при этом остаётся 29 и в
  0.10, то есть §27.1 будущий переход не заденет). Если апстрим когда-нибудь изменит
  число, наши тесты по-прежнему пройдут — они держат нашу арифметику, а не чужой буфер, —
  и поймает это только развёртка на машине с видеокартой, где немедленно появятся либо
  тихие кадры, либо ложные отказы. Поэтому при смене пина `bench-shell` на машине с GPU
  обязателен.
* **Блит-путь не трогается**: у CPU-растеризатора такого потолка нет, и проверка на нём
  не выполняется.
* **Проверяется один буфер из шести.** Тайлы — не единственное, что vello раздаёт
  константой, и §33.7 показывает второй способ потерять кадр, которого эта проверка не
  видит.
* **Guest mode** (§14) получит ту же границу вместе с чужим устройством — она про
  vello, а не про то, чей `Device`.

### 33.6 Что это меняет в плане §16

Дыру, которую §32.7 записал за пунктом 1 (`blazy-shell`), закрывать нечем — она чужая, —
но она больше не тихая, и это меняет статус: не «хост может показать не тот кадр», а
«хост сообщает, что кадра нет».

И это первое **конкретное** подтверждение риска §15.1. Жить на молодом крейте — не
абстракция: `imaging_vello` 0.0.2 → vello 0.9 приносит потолок, о котором не написано
нигде, кроме комментария в исходнике, и обнаруживается он обратным чтением кадра в
бенчмарке. Страховка, которую §18 называет фасадом и критериями в CI, здесь сработала
ровно так, как задумывалась: дефект нашёлся замером, а не в чужом приложении.


### 33.7 Тем же способом ломается не только это (замерено)

Раз причина — фиксированные буферы, стоило спросить, что ещё они ломают. Замерено на той
же машине, vello 0.10.

**Стек блендинга — потолок ниже и достижимее.** `blend_spill` это `1 << 20` слов, а тайл,
уходящий глубже `BLEND_STACK_SPLIT` (4), тратит `(глубина − 4) × 256` слов. Отсюда: на
окне 1100×750 (3243 тайла) пять вложенных слоёв влезают (830 208), шесть — нет
(1 660 416). На 2200×1500 не влезают уже **пять**. Проверено: на шести (соответственно
пяти) кадр исчезает целиком, и так же молча.

| Окно | Глубина 4 | 5 | 6 |
|---|---|---|---|
| 1100×750 | рисуется | рисуется | **пусто** |
| 2200×1500 | рисуется | **пусто** | **пусто** |

Слои были зрительно нулевыми — `Mix::Normal`, alpha 1.0, — то есть дело не в содержимом,
а в самой вложенности. Для UI это куда ближе, чем 647 путей во весь экран: пара
анимаций прозрачности внутри модального слоя — и глубина шесть.

**Клипы ведут себя иначе, и вывод отсюда верный, а объяснение — нет.** Тот же опыт с
`push_clip_layer` вместо `push_layer`: до глубины 8 на обоих окнах картинка верная.
Отсюда было записано «клип не тратит стек блендинга»; §34.2 показал, что тратит — просто
не везде, а только на тайлах, которые пересекает его контур. Вывод «наша архитектура этот
потолок не задевает» устоял, но держится он не на том, что клип это клип, а на том, что
области и вьюпорт канваса режутся **прямоугольниками** (§20.3), у которых контур идёт по
краю. Клип с извилистым контуром теряет кадр там же, где группы.

**`ptcl` переполнить раньше тайлов не удалось.** В `coarse.wgsl` переполнение списков
команд обрабатывается иначе — не отказом, а записью всех по нулевому смещению с
комментарием «technical UB, as lots of threads will be writing to the same locations», —
то есть теоретически это не пустой кадр, а **неверный**. На практике ни одна сцена, где
это пробовалось (тысячи сплошных прямоугольников друг на друге, оракул — непрозрачный
прямоугольник известного цвета последним), не дошла до этого буфера: тайлы кончаются
раньше. Записано как непроверенная возможность, а не как найденный симптом.

**Что из этого следует для §33.3.** Проверка тайлов — не полная защита, а защита от
одного из шести буферов, и притом не от самого достижимого. Расширить её на стек
блендинга дёшево (глубина групп считается в том же обходе), и это следующая работа —
здесь она не сделана, потому что задача была про кадр, которого не было, а не про полный
предиктор чужих буферов.

## 34. Второй буфер: стек блендинга (замерено)

§33.7 назвал следующую работу: проверка тайлов защищает от одного буфера vello из шести,
и притом не от самого достижимого. Задача — `issues/blend stack budget.md`. Здесь
результат: механизм оказался не тем, что был записан, модель считает не пути, а тайлы, и
защита стоит нуля на настоящем кадре.

### 34.1 Что было записано неверно

§33.7 записал: «клип не тратит стек блендинга… наша собственная архитектура этот потолок
не задевает». Первая половина неверна. `push_clip_layer` и `push_layer` идут через один
`push_layer_inner` и различаются одним полем (`CLIP_BLEND_MODE = 0x8003` против пары
mix/compose, `vello-0.9.0/src/scene.rs:192`), а `coarse.wgsl` наращивает
`render_blend_depth` на `DRAWTAG_BEGIN_CLIP`, не глядя на режим. То есть по исходникам
клип обязан платить — а замер показывал, что восемь вложенных клипов рисуются.

Разошлись они потому, что оба смотрели на **экранный прямоугольник**. Решает не «клип
или группа», а сколько тайлов попадает в слой, и это следующий раздел. Вывод §33.7 —
«архитектура не задевает потолок» — устоял, но по другой причине, чем там написано.

### 34.2 Что заряжает тайл

Строка, которая всё решает (`coarse.wgsl`, обе версии):

```wgsl
let is_blend     = blend != BLEND_CLIP;
let include_tile = n_segs != 0u || (backdrop_clear == is_clip) || is_blend;
```

* **группа** — это blend-слой, `is_blend` истинно всегда, поэтому она включается в
  **каждый** тайл своего габарита и заряжает их все;
* **клип** включается только там, где у его пути есть сегменты, то есть на тайлах, которые
  пересекает его **контур**. Тайлы внутри клипа остаются на своей глубине; тайлы снаружи
  уходят в ветку `clip_zero`, которая подавляет всё вложенное и не заряжает ничего.

Замерено на том же Intel UHD (CML GT2), Mesa 25.2.8, vello 0.10; воспроизводитель —
`rnd/upstream/vello-silent-blend-overflow.rs`, слои зрительно нулевые:

| Вложенность | 1100×750 | 2200×1500 |
|---|---|---|
| группы (`push_layer`) | рисуется 5, пусто 6 | рисуется 4, пусто 5 |
| прямоугольный клип во весь экран | рисуется 30, пусто 40 | рисуется 21, пусто 22 |
| прямоугольный клип с отступом 32 | рисуется 40 | рисуется 22, пусто 23 |
| клип-зигзаг через все ряды тайлов | рисуется 5, пусто 6 | рисуется 4, пусто 5 |
| клип вокруг каждой группы | рисуется 5, пусто 6 | рисуется 4, пусто 5 |
| клипы внутри четырёх групп | рисуется 25 | рисуется 12, пусто 20 |

Три вещи, которые отсюда следуют. **Клип не бесплатен**: зигзаг теряет кадр там же, где
группы. **Прямоугольный клип почти бесплатен**: границы 21/22 и 22/23 дают заряд около
`столбцы + ряды` тайлов габарита — примерно **половину кольца**, а не весь периметр.
**Клип между группами ничего не сдвигает**: строка «клип вокруг каждой группы» повторяет
строку групп.

Симптом тот же, что в §33: `bump.failed` выставлен, `fine.wgsl` возвращается не рисуя,
`render_to_texture` отвечает `Ok`, в текстуре остаётся прошлый кадр.

### 34.3 Защита: карта тайлов и отсечение по глубине

Величина считается **по тайлам**, а не по путям, поэтому суммы по слоям недостаточно:
одна и та же группа над одним тайлом пятый уровень, над другим первый. `blazy-shell`
держит карту глубин размером с кадр в тайлах и заряжает:

* группа — весь свой габарит (габарит своего клипа, а без него — весь кадр: именно по
  `surface_clip` её пушит `imaging_vello`, `scene_sink.rs:305`);
* прямоугольный клип — дальний столбец и дальний ряд своего габарита, то есть ровно
  `столбцы + ряды − 1` тайлов;
* клип-путь — весь габарит, потому что контур может пройти где угодно внутри;
* всё вложенное — только внутри габаритов открытых клипов (`clip_zero`).

Спрос — `Σ по тайлам max(0, глубина − 4) × 256` слов против `1 << 20`. Модель
воспроизводит **все** строки таблицы §34.2, включая переход «клипы внутри четырёх групп»
между 12 и 20 на большом окне. Замер даёт счёт заряженных тайлов, но не их расположение;
дальний столбец и дальний ряд — выбор модели, а не установленный факт.

**Цена — ноль там, где важно.** Перед картой стоит счёт вложенности прямо по потоку
команд: глубже четырёх уровней тайл уйти не может, если сцена не уходит, а четыре живут в
регистрах. Настоящий кадр — восемь областей над графом из 5000 нод на HiDPI — это 383
команды, **ноль групп**, глубина **1**, 90 217 тайлов из 2 097 152 и ноль слов
(`a_real_frame_is_far_from_both_ceilings`). Проверка обходится в 0.000 мс; там, где карта
всё-таки строится, она стоит 0.017–0.066 мс на кадр.

Отказ — новый вариант `PresentError::SceneTooDeep { words, budget }`; окно ведёт себя как
с тайлами: предупреждение на переходе, кадр пропущен, окно живёт.

### 34.4 Замерено

Развёртка `bench-shell` по глубине на двух масштабах отказывает ровно там, где кадра нет:
глубина 6 при масштабе 1, глубины 5 и 6 при масштабе 2. Три критерия, каждый сломан на
живом коде:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---|
| каждая принятая вложенная сцена нарисована | 0 | < 1 кадра | 6 (бюджет 1<<40) |
| каждая отвергнутая действительно не рисуется | 0 | < 1 | 1 (бюджет 1<<19) |
| развёртка содержит сцену свыше бюджета | 0 | < 1 | 1 (бюджет 1<<40) |

Третий — не украшение по той же причине, что в §33.4: без него первые два проходят на
развёртке, которая до потолка не доходит.

Плюс восемь тестов без GPU (`tiles::blend_tests`), держащих измеренные границы: 5/6 и 4/5
для групп, 21/22 и 30/40 для прямоугольных клипов, 22/23 для клипа с отступом, 5/6 для
зигзага, и отдельно — что группа внутри маленького клипа заряжает только его тайлы.

### 34.5 Чего это не делает

* **Апстрим не вылечен.** Отчёт `rnd/upstream/vello-silent-tile-overflow.md` дополнен
  вторым режимом и исправлен там, где утверждал, что клипы не при чём; воспроизводитель
  рядом ходит по всем шести видам вложенности. Просьбы те же три: сообщать, оценивать,
  растить.
* **Проверено два буфера из шести.** `ptcl` остаётся непроверенной возможностью (§33.7),
  `segments`, `seg_counts` и `lines` не трогались.
* **Расположение заряженных тайлов — модель, а не факт** (§34.3). Счёт подтверждён тремя
  независимыми границами, место — нет.
* **Блит-путь не трогается**: у CPU-растеризатора такого буфера нет.
* **Константы привязаны к пину**, как `TILE_BUDGET` (§33.5): при смене пина `bench-shell`
  на машине с видеокартой обязателен.

### 34.6 Что это меняет в плане §16

Дыра, записанная §32.7 за пунктом 1 (`blazy-shell`), закрыта настолько, насколько её
можно закрыть у себя: обе достижимые границы vello теперь считаются до отправки кадра и
называются вслух.

Для пункта 11 (`blazy-widgets`) и для любого приложения поверх библиотеки появляется
число, которого раньше не было: **четыре уровня групп с прозрачностью бесплатны, пятый на
HiDPI-окне стоит кадра**. Это ограничение прозрачности, а не клипов, — то есть оно
касается оформления виджетов, а не раскладки областей. Guest mode (§14) получит ту же
границу вместе с чужим устройством.

## 35. Рычаги дальнего поля: сегменты, а не команды (замерено)

§32 показал, что растеризация не следует за числом команд, и §32.7 записал следствие:
рычаги, оставленные §31.6 «в запасе», перестают быть запасом. Задача —
`issues/far field levers.md`. Здесь: из чего кадр состоит, что каждый рычаг с него
снимает, и почему один из них оказался не рычагом, а найденной ошибкой.

### 35.1 Единица есть, и она бесплатна

`Scene::encoding().n_path_segments` считает сегменты без устройства, точно и
машинонезависимо, то есть годится в критерий (§20.9). Счётчик переехал из бенча хоста в
`blazy_shell::encoded` — канвасу он нужен тоже, а `imaging_vello` из примера не виден.

Чего стоит форма (замерено тестами `blazy_shell::encode`):

| Фигура | Сегментов |
|---|---:|
| прямоугольник (заливка) | 4 |
| скруглённый прямоугольник (заливка) | 8 |
| кубическая кривая (обводка) | 2 |
| прямая (обводка) | 2 |

Отсюда сразу два вывода. **Прямая стоит ровно столько же, сколько кубик** — «геометрия
проще» не рычаг, и §31.1 уже получал тот же ответ со стороны кодирования. И **ноды
перевешивают связи**: 5000 нод по 8 сегментов против 4920 связей по 2.

### 35.2 Что кадр стоит на самом деле

Замерено на графе из 5000 и 20 000 нод, вьюпорт 1100×750, зумы 0.02 (весь граф на
экране) и 0.10 (дальнее поле, но граф продолжается за областью записи). Каждая строка —
одно изменённое решение:

| Что | Сегментов | CPU, мс | GPU, мс |
|---|---:|---:|---:|
| **зум 0.02, 5000 нод** | | | |
| скруглённые ноды (как было) | 49 852 | 18.2 | 28.8 |
| прямые углы (как стало) | 29 852 | 16.8 | 19.4 |
| без связей | 20 012 | **3.7** | 11.9 |
| **зум 0.10, 5000 нод** | | | |
| запас 0.50 (как было) | 52 148 | 20.8 | 29.9 |
| запас 0.25 (как стало) | 36 918 | 17.5 | 29.4 |
| запас 0.10 | 25 938 | 15.1 | 21.1 |
| **зум 0.10, 20 000 нод** | | | |
| запас 0.50 | 47 502 | 15.3 | 27.3 |
| запас 0.25 | 27 580 | 12.1 | 19.5 |

**Главное число не про рычаги.** Убрать связи — 29 852 → 20 012 сегментов, минус треть, а
время падает с 16.8 до 3.7 мс, вчетверо с лишним. Считая по строкам: 20 012 сегментов
заливок стоят 3.7 мс (0.19 мкс на сегмент), 9 840 сегментов обводок — 13.1 мс (1.33 мкс).
**Обводка дороже заливки в семь раз на сегмент**, и это уточняет §32: платится за
сегменты, но сегменты не равны между собой, а кадр дальнего поля — это его *связи*.

**Рычаг первый: не скруглять то, чего не видно.** `RADIUS` — 6 канвасных единиц, на зуме
0.02 это 0.12 пикселя. Правило `FAR_MIN_RADIUS_PX = 0.5` в примере снимает четыре сегмента
из восьми с каждой ноды: 49 852 → 29 852 и 18.2 → 16.8 мс на CPU, 28.8 → 19.4 на GPU.
Ключёвано на собственной экранной геометрии, а не на уровне детализации, — по тому же
правилу, что и порог коротких связей (§31.4), и поэтому само выключается на зуме 0.10, где
скругление снова видно.

**Рычаг второй: запас области.** `FAR_OVERSCAN` был 0.5 «из соображений», то есть область
вчетверо больше вьюпорта по площади. Ценой оказалось от пятой части до четверти кадра, и
он теперь **0.25**. Что покупается обратно — перевыборы набора: 0.00 на кадр при 0.5,
0.02 при 0.25, 0.05 при 0.10. Дальше нельзя не потому, что дорого, а потому, что 0.05 —
это граница критерия `pan_does_not_reselect_links`, и пан начинает перевыбирать набор
достаточно часто, чтобы это было видно.

**Рычаг третий: порог коротких связей.** На зуме 0.02 соседние ноды в 4.4 пикселя друг от
друга, так что порог в 8 пикселей убирает **все** связи: 16.8 → 3.5 мс. Это единственный
рычаг, укладывающий кадр в 16.7 мс, и он же единственный, который стирает то, ради чего
обзорный зум существует: на обзоре рисунок графа и есть содержание. Замерено и оставлено
приложению как настройка, а не поднято в умолчание.

### 35.3 Константа, настроенная под одно значение (найдено в работе)

Сужение запаса с 0.5 до 0.25 уронило критерий `no_link_is_hidden_at_a_zoom_whose_nodes_are_
still_widgets`: 1015 связей спрятаны на зуме, где ноды снова виджеты. Виноват был не запас,
а `REGION_SLACK = 16.0` — «во сколько раз область может превышать вьюпорт, прежде чем её
перезапишут». Шестнадцать было выведено из того, что область при запасе 0.5 вчетверо
больше вьюпорта, то есть допускало зум внутрь вдвое. При запасе 0.25 область всего в 2.25
раза больше — и та же шестнадцать стала допускать зум в 2.7 раза, то есть **чем уже поле,
тем дольше живёт устаревший набор**. Задом наперёд.

Починка: слэк выводится из запаса, а не задаётся числом —
`region_slack(overscan) = (1 + 2·overscan)² · ZOOM_SLACK`, где `ZOOM_SLACK = 4` и означает
ровно то, что имелось в виду с самого начала: «зум внутрь вдвое область переживает, вчетверо
— нет». При 0.5 это те же 16, так что прежнее поведение сохранено буквально.

Урок в копилку §28.4 и §29.1: **константа, выведенная из другой константы, обязана быть
выражена через неё.** Иначе первый же поворот второй ручки тихо меняет смысл первой — и
здесь это поймал критерий, а не глаз.

### 35.4 Замерено

Два новых критерия, оба сломаны на живом коде:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---|
| дальнее поле — четыре сегмента на ноду и два на связь | 12 | < 64 сегментов сверх модели | 20 012 (`FAR_MIN_RADIUS_PX = 0`) |
| пан внутри записанной области переиспользует её | 0.02 | < 0.1 перезаписей/кадр | 1.00 (`FAR_OVERSCAN = 0`) |

Первый держит состав кадра: вернуть скругление на обзорном зуме — двадцать тысяч сегментов
сверх модели. Второй держит вторую сторону размена, и он же вместе с
`pan_does_not_reselect_links` не даёт сузить запас до значения, при котором пан начинает
перевыбирать наборы.

Сегменты добавлены в развёртку по зуму — в оба конца (§28.4), и асимметрия там видна
сразу: 0.040 «вниз» это 37 134 сегмента, «вверх» — 29 852, то есть набор, выбранный на
более глубоком зуме, ещё живёт. Строки дальнего поля архивируются в JSON-отчёт, чтобы
рычаги можно было передиффать, а не переспорить.

### 35.5 Влезает ли кадр в 60 Гц

Нет — и теперь это сказано числом. После обоих принятых рычагов обзорный кадр на 5000 нод
стоит 16.8 мс на CPU-пути и 19.4 на GPU при бюджете 16.7 мс; на 20 000 нод — 54.0 и 59.9.
Рычаги сняли от четверти до трети, но порядок остался.

Из этого следуют три вещи.

* **§16 пункт 8 (`blazy-compose`, текстура на область) срочности не потерял**, а получил
  цену: обзорный кадр большого графа в три с лишним раза за бюджетом, и это цена
  *перерисовки того, что не менялось*.
* **Дальше резать надо связи, а не ноды.** Ноды после правила скругления стоят 3.7 мс из
  16.8; всё остальное — обводки. Способ, не стирающий структуру графа, придётся искать в
  устройстве дальнего поля (§20.6): огрубление до сетки ячеек, объединение пучков связей,
  запечённая текстура.
* **GPU-путь на этом окне медленнее блита** (19.4 против 16.8 мс), что ровно то, что §27.4
  измерил про мегапиксель, и лишний довод к тому, что выбор пути — рантаймовый.

### 35.6 Чего это не делает

* **Устройство дальнего поля не переделано** (§20.6): огрубление до ячеек названо и
  посчитано как потолок, но не построено.
* **CPU-растеризатор по-прежнему без счётчика** (§32.6): времена блит-пути — часы, а не
  счётчик, поэтому критерии стоят на сегментах и на перезаписях.
* **Порог коротких связей не поднят в умолчание**: замерен и оставлен приложению.
* **Времена в этой секции — с машины разработчика** (Intel UHD, шесть кадров на строку) и
  в CI не гейтятся, как и все времена (§20.9).

## 36. Текстура на область: не перерисовывать то, что не менялось (замерено)

§35.5 назвал остаток кадра числом и указал сюда: после всех рычагов обзорный кадр не
влезает в 60 Гц, а платится он за перерисовку того, что не изменилось. Задача —
`issues/per-area texture.md`, пункт 8 плана §16 и уровень B из §7.3. Здесь: ловушка,
которую надо было обойти, механизм, который на восьми областях даёт кадр втрое дешевле, и
цена, которую он берёт.

### 36.1 Слой живёт один проход отрисовки

Первый вопрос задачи был «переживает ли граница слоя кадр, в котором виджет ничего не
перерисовывал», и ответ — **нет**. `paint.rs` ставит `state.paint_layer_mode =
PaintLayerMode::Inline` до того, как решит, рисовать ли виджет вообще, а чистый виджет не
рисуется; апстрим пишет это прямо в документации `set_paint_layer_mode`. Замерено на
экране из восьми областей: девять слоёв в плане на кадре, где областям велели
перерисоваться, и **один** на следующем — всё содержимое схлопывается обратно в слой
родителя. То есть механизм разваливался бы ровно в том случае, ради которого затевается:
простаивающая область перестаёт быть слоем.

Обходится это дёшево, и не так, как обходит дыра. `ExternalContent` держится
анимационным кадром (§26.1) — но анимационный кадр означает, что окно никогда не засыпает.
Здесь вместо этого **хост просит области перерисоваться на тех кадрах, которые и так
происходят**: `ShellDriver::layers` возвращает список виджетов-слоёв, цикл окна помечает
каждый `request_paint_only` и сообщает презентеру, чьи пиксели можно хранить. Цена — один
пустой `paint` на область на кадр: `AreaContent` не рисует ничего своего, а сцены его
регионов проход отрисовки доклеивает в любом случае.

### 36.2 Механизм: сравнить сцену, скопировать прямоугольник

`GpuFrames` держит текстуру на слой. На каждом кадре:

1. слой, чья `Scene` и трансформ совпали с прошлым кадром, **не рисуется** — его
   прямоугольник копируется из его текстуры;
2. остальные слои собираются в одну сцену и растеризуются как раньше;
3. копии идут **после** растеризации, потому что vello очищает цель;
4. каждый перерисованный слой копируется из кадра обратно в свою текстуру.

Ни одного шейдера и ни одной пересэмплировки: формат кадра и формат кэша совпадают,
копия попиксельная (`copy_texture_to_texture`), и вопрос §23 о резкости снимается не
замером, а устройством. Единственное, чего не хватало в существующем коде, — `COPY_DST` у
кадровой текстуры.

**Прямоугольник слоя приходится вычислять самим**, потому что план несёт сцены и не несёт
границ. Это обход сцены по габаритам — та же арифметика, что в §33.3. Первая версия
игнорировала клипы, «потому что шире — безопаснее», и это оказалось неверно ровно
наоборот: обводка на краю области раздувает габарит на полширины штриха, прямоугольник
перекрывает соседнюю область, и копия кладёт поверх её края чужие пиксели — 149 пикселей
неправильной картинки. С учётом клипов кадр совпал побайтово, а память кэша упала с 11.5
до 4.9 МиБ: клип — это и есть настоящий край области, и он уже целопиксельный, потому что
§21 округляет прямоугольники областей.

**Что каталог обязан пообещать.** Кэшируемый слой **владеет своим прямоугольником**:
никто другой в него не рисует. Для областей, замощающих окно, это верно; для всплывающего
окна поверх области — нет. Хост это проверить не может (в плане нет границ), поэтому он не
угадывает, а спрашивает: `GpuFrames::cache_layers` принимает список от приложения.

### 36.3 Замерено

Восемь областей над одним графом, все канвасы на обзорном зуме, окно 1400×900, Intel UHD.
Числа перемерены после уборки §37: одно устройство на таблицу, а не одно на строку —
инициализация драйвера внутри замера завышала кэшированные строки в полтора раза. Два
подряд идущих прогона расходятся на 5%.

| Что происходит | Кэш | Оставлено | Перерисовано | Обходов | Кадр GPU, мс |
|---|---|---:|---:|---:|---:|
| ничего не меняется | выкл | — | — | — | 44.2 |
| панится одна область | выкл | — | — | — | 42.9 |
| панятся все восемь | выкл | — | — | — | 45.4 |
| ничего не меняется | **вкл** | 8.00 | 0.00 | 0.00 | **11.8** |
| панится одна область | **вкл** | 7.00 | 1.00 | 1.00 | **13.7** |
| панятся все восемь | **вкл** | 0.00 | 8.00 | 8.00 | 44.5 |

**Вчетверо на простое, втрое с лишним на работе в одной области** — и разница в пределах
шума на кадре, где изменилось всё. Последняя строка и есть пол композиции: копии и решение
не видны, когда экономить нечего.

**Цена решения замерена, и порядок в ней важен.** Сравнить сцены — дёшево; вычислить
прямоугольник — обход всей сцены слоя. Первая версия считала прямоугольник до сравнения и
стоила 3.7–5.3 мс на кадр; перестановка (сначала сравнить, и только у изменившегося слоя
искать границы — у неизменившегося они уже есть) уронила это до 1.1 мс на кадре, где
ничего не менялось; из чего эта миллисекунда состоит — §37.1. Порядок держится счётчиком
`walks`, а не памятью о нём. Память: 4.9 МиБ текстур на восемь областей в окне 1400×900,
с потолком §37.2.

**Картинка та же, и это проверено побайтово.** Кадр, собранный из копий, совпадает с
кадром, нарисованным целиком, байт в байт (`a_kept_layer_is_the_same_picture`). Кадр, где
одна область перерисована рядом с семью скопированными, отличается **на один байт из пяти
миллионов** — один канал одного пикселя на шве между двумя областями, где в однопроходном
кадре смешиваются края обеих, а здесь копия кладётся поверх. Растеризатор при этом
детерминирован (тот же план дважды — те же байты), так что это свойство механизма, а не
шум GPU, и тест держит его порогом в один уровень.

Четыре критерия в `bench-areas`, и каждый сломан на живом коде:

| Критерий | Замерено | Граница | Сломано — даёт |
|---|---:|---:|---|
| на кадре без изменений не рисуется ни одна область | 0.00 | < 0.5 | 8.00 (кэш никогда не переиспользует) |
| пан в одной области из восьми рисует одну | 1.00 | < 2.0 | 8.00 (то же) |
| каждая область либо сохранена, либо нарисована | 0.00 | < 0.5 | — |
| в развёртке есть кадр, где рисуются все | 0.00 | < 1 | 1.00 (кэш переиспользует всё подряд) |

Второй способ поломки — «переиспользовать, не сравнивая сцену» — показал и то, чего
тесты не ловили: `a_kept_layer_is_the_same_picture` проходил, потому что проверял только
одну сторону переключателя. Отсюда `a_changed_layer_is_drawn_again` — та же дисциплина,
что в §28.4.

### 36.4 Чего это не делает

* **Блит-путь не кэширует ничего.** `Presenter::cache_layers` у него пустой: он
  растеризует в буфер на процессоре, и хранить ему нечего. Ниже мегапикселя он всё ещё
  быстрее (§27.4) — но там и экономить меньше.
* **Пан внутри области — это изменение сцены, а не трансформа слоя.** Проход отрисовки
  впекает трансформы детей в сцену слоя, а вид канваса живёт на `CanvasContent` внутри
  области. Поэтому переиспользование «той же текстуры со сдвигом» на уровне области
  невозможно в принципе, и вопрос о пересэмплировке (§23) не возникает: копия всегда
  попиксельная. Слой на самом канвасе дал бы сдвиг — и вместе с ним дробные смещения и
  ресэмплинг; не сделано и не измерено.
* **Слои объявляют только области.** Регион, канвас, всплывающее окно — нет; для
  перекрывающихся слоёв условие «владеет прямоугольником» неверно, и механизм для них
  надо проверять отдельно.
* **Кэш не спит**, но он ограничен: потолок и вытеснение по давности сделаны в §37.2.
  Текстуры живут, пока область зарегистрирована и пока помещаются в потолок.
* **Окно по-прежнему засыпает.** Список слоёв запрашивается только на кадрах, которые и
  так рисуются, поэтому объявление слоёв не заводит вечный цикл перерисовки.

### 36.5 Что это меняет в плане §16

**Пункт 8 закрыт в той форме, в какой его описывал §7.3 (уровень B), для GPU-пути.** «Тащим
ноду в нод-редакторе — таймлайн, аутлайнер, свойства не перерисовываются вообще» — это
теперь не план, а строка таблицы: семь областей из восьми стоят копии текстуры.

**Кандидат в контрибуцию §26.6 подтверждён замером.** Режим слоя как флаг прохода, а не
свойство виджета, — единственное, что заставляет хост просить перерисовку у виджетов,
которым рисовать нечего. Просьба наверх формулируется коротко: пусть `IsolatedScene`
переживает кадр, в котором виджет чист.

**Дальнее поле (§35.5) осталось дорогим ровно там, где было**: кадр, в котором работает
одна область, всё ещё стоит её растеризации. Кэш убрал соседей, а не саму сцену.

## 37. Ревью и уборка: что осталось после четырёх задач подряд (замерено)

§33–§36 сделаны одна за другой, и ревью кода нашло то, что накапливается при такой
скорости: документация в двух экземплярах, два обхода сцены с общей арифметикой, два
обхода плана, плоская публичная поверхность и девять конструкторов в примерах. План
уборки — `issues/refactor before ops.md`, пять фаз, каждая с гейтом «`cargo make ci` плюс
сверка счётчиков в отчётах». **Ни один счётчик не сдвинулся ни на одном шаге**; двигались
только критерии `Kind::Timing`, и всегда внутри границ.

Здесь — то, что потребовало замера, а не перестановки строк.

### 37.1 Из чего состоит решение кэша, и почему пред-фильтр не нужен

Кэш слоёв решает про каждый слой: сравнить его сцену с прошлой и, если она изменилась,
найти прямоугольник обходом (§36.3). Ревью предлагало дешёвый пред-фильтр перед полным
сравнением. Замер разложил решение на две половины (восемь областей, окно 1400×900):

| Что происходит | Сравнение, мс | Обход, мс |
|---|---:|---:|
| ничего не меняется | 0.81 | 0.46 |
| панится одна область | 0.74 | 0.92 |
| панятся все восемь | **0.015** | 2.95 |

**Пред-фильтр не нужен, и это видно из строки, где всё изменилось.** Сравнение
неравных сцен стоит 0.015 мс на девять слоёв — в пятьдесят раз меньше, чем сравнение
равных: `Vec::eq` останавливается на первом различии, то есть фильтр оптимизировал бы
случай, который уже почти бесплатен. А случай, который стоит денег, — это сравнение
**равных** сцен на простое, и никакой фильтр его ускорить не может: чтобы ответить «равны»,
надо посмотреть всё.

Единственный способ убрать эту миллисекунду — не сравнивать вовсе, то есть узнавать о
чистоте слоя от Masonry. Плана с такой информацией нет (§36.1), и это тот же запрос
наверх, что уже записан в §36.5. Цифра, которую он экономит, теперь известна: **0.8 мс на
кадр на восьми областях**, против 11.8 мс самого кадра.

Обход при этом остаётся дороже сравнения там, где он вообще случается (2.95 мс на восемь
изменившихся слоёв против 0.015 мс сравнения), — то есть перестановка §36.3 сделана в
правильную сторону, и теперь она закреплена счётчиком `walks`, а не памятью о ней.

### 37.2 Потолок памяти и вытеснение по давности

§36.4 честно писал: текстуры живут, пока область зарегистрирована, верхней границы нет.
Сделано: `LayerCache` держит потолок в байтах и вытесняет по давности использования
(`clock` тикает на каждое сохранение и каждое переиспользование), считая `evictions`.

**Умолчание выведено из устройства, а не выбрано.** Кэшируемые слои **замощают** окно —
это и есть предусловие §36.2, — поэтому все их текстуры вместе стоят примерно один кадр,
сколько бы областей ни было: 4.9 МиБ на восемь областей окна 1400×900, а сам кадр 4.8 МиБ.
Потолок по умолчанию — **два кадра**: второй нужен на ресайз, где старые текстуры живут,
пока их слои не сохранены заново.

Замерено на строке с потолком в четверть кадра (1230 КиБ):

| Потолок | Оставлено | Перерисовано | Вытеснено | Держит | Кадр GPU |
|---|---:|---:|---:|---:|---:|
| 9843 КиБ (умолчание) | 8.00 | 0.00 | 0.00 | 4858 КиБ | 11.8 мс |
| 1230 КиБ | 2.00 | 6.00 | 6.00 | 1214 КиБ | 33.0 мс |

То есть тесный потолок не ломает ничего — он просто возвращает цену перерисовки, ровно
пропорционально тому, сколько слоёв не поместилось. Два критерия, оба сломаны на живом
коде: «кэш не держит больше своего потолка» (0 КиБ сверх; без вытеснения — 3628) и
«в развёртке есть кадр, где кэш вытеснял» (иначе первый проходит, ни разу не наполнившись).

### 37.3 Что уборка изменила в коде

Коротко, потому что числа тут ничего не двигали:

* **Документация.** §16 стал живым статусом вместо пятнадцати абзацев «что это меняет в
  плане»; появилась карта §19; заголовки `tiles.rs` и `layers.rs` ужаты вдвое, а числа из
  них убраны туда, где они проверяются, — в тесты и сюда. `CLAUDE.md` перестал утверждать,
  что запас области — половина вьюпорта (§35.2 сделал его четвертью).
* **Один обход габаритов** (`bounds.rs`) вместо двух: предиктор бюджета и кэш слоёв считали
  габариты фигур, глифов и размытий по отдельности, и разошлись бы молча.
* **Один обход плана**: `Composition::build` принимает решение вызывающего по каждому слою,
  так что масштаб устройства и внешние дыры считаются в одном месте, а кэшированный путь
  перестал быть веткой на 95 строк.
* **Поверхность крейта**: `tiles`, `encode`, `layers` — модули; в корне только типы. Имена
  вроде `demand` и `segments` библиотека не может занимать в чужом корне (§15.1).
* **Примеры**: `CanvasSpec` и `ScreenSpec` вместо девяти конструкторов с булевыми
  аргументами.
* **Одно место, где слой держат живым**: метод `AreaScreen::keep_layers` убран, потому что
  это работа хоста (`ShellDriver::layers`), а библиотечный метод, существовавший ради того,
  чтобы харнесс мог изобразить хост, — это второй способ сказать одно и то же.

### 37.4 Чего уборка не делает

* **Времена по-прежнему не гейтятся** (§20.9), и правильно: две новые пары критериев —
  `needs_walk` для бюджета и `walks` для кэша — проверяют не «сколько миллисекунд», а
  «ходил ли код туда, куда не должен». Это то же утверждение в единице, которая не зависит
  от машины.
* **Разброс машины остаётся большим**: два прогона подряд на одном коде расходятся на
  5–27% в зависимости от нагрузки, поэтому все выводы о временах здесь сделаны на парах
  прогонов, а не на одном.
* **`raster_case` не разобран на структуру параметров**: пять его аргументов — это пять
  осей развёртки, и обёртка вокруг них ничего не объясняет.

## 38. Операторы, keymap и модальность: где садится слой (замерено)

Пункт 12 плана §16, задача — `issues/operators and keymap.md`. §11 описывает операторы,
keymap как данные и модальный стек, и в одном месте говорит неверное: что `blazy-ops`
сидит **выше** маршрутизации Masonry и перехватывает событие до спуска в дерево. Здесь:
что на пинне есть на самом деле (три места, и ни одно не делает всю работу), сколько стоит
каждое, во что это превратило устройство слоя, и две вещи, которые пришлось замерить, а не
выбрать — форма undo и место, куда рисует модальный оператор.

Собрано: крейт `blazy-ops` (реестр, keymap, модальный стек, журнал undo, счётчики), шесть
операторов в `examples/node-canvas` — выделение, рамка, перетаскивание, панорамирование,
undo и redo, — драйвер в `NodeEditor`, тот же слой внутри областей в `examples/area-screen`.
Гейт: 34 + 21 + 23 критерия, из них одиннадцать новых.

### 38.1 Три места, и ни одно не делает всю работу

Проверено на пинне `ce7b04d`, чтением `masonry_core/src/passes/event.rs` и опытами в
харнессе.

**Точка «до дерева» существует, и она не наша.** `run_on_pointer_event_pass` до того, как
вычислит адресата, проходит по корням слоёв и зовёт `Layer::capture_pointer_event` у
каждого — на **каждое** событие указателя, включая те, что вне прямоугольника слоя. Это в
точности перехват, которого хотел §11. Но остановить событие он не может: метод ничего не
возвращает, его `EventCtx` выбрасывается вместе с флагом `is_handled`, а `capture_pointer`
в нём отказывает — проход создаёт контекст с `allow_pointer_capture: false`. В самом
апстриме над этим методом висит TODO: «Return flag to suppress event from reaching
children». То есть просьба наверх формулируется в одну строку и уже названа теми, к кому
её адресуют (§17).

**Единственный рычаг, который держит событие вне дерева, — захват указателя**, и он
выдаётся только на нажатие: `run_event_pass` получает `allow_pointer_capture:
matches!(event, PointerEvent::Down(_))`. Отсюда следует то, что вся эта секция вертит:
модальный оператор, начатый **нажатием**, забирает захват, и дальше события идут прямо
драйверу; модальный оператор, начатый **клавишей** (блендеровские `G` и `B`), захвата
взять не может, и каждое его событие сперва доходит до дерева.

**Это видно в столбце**, а не в рассуждении — `tree-1st/g` считает события, дошедшие до
дерева раньше рантайма при живом операторе:

| жест | место | событий | modal/g | tree-1st/g | раскладок/g | пиков/g | зондов/g | мс/g |
|---|---|---|---|---|---|---|---|---|
| клик-выделение (ПКМ) | дерево | 3 | 0.0 | 0.0 | 0.00 | 2.0 | 0.0 | 0.137 |
| перетаскивание ноды (ЛКМ) | дерево | 22 | 21.0 | **0.0** | 20.00 | 2.0 | 0.0 | 2.389 |
| перетаскивание канваса | канвас | 22 | 0.0 | 0.0 | 20.00 | 2.0 | 0.0 | 2.323 |
| box select (ПКМ) | дерево | 23 | 21.0 | **0.0** | 0.00 | 2.0 | 0.0 | 1.577 |
| grab (клавиша `G`) | дерево | 22 | 21.0 | **21.0** | 20.00 | 22.0 | 0.0 | 2.649 |
| grab, отменённый | дерево | 22 | 21.0 | 20.0 | 21.00 | 21.0 | 0.0 | 2.454 |
| пан оператором (ЛКМ) | дерево | 22 | 21.0 | 0.0 | 3.00 | 2.0 | 0.0 | 5.701 |
| пан канваса (средняя) | канвас | 22 | 0.0 | 0.0 | 3.00 | 2.0 | 0.0 | 5.521 |
| grab (клавиша `G`) | хост | 22 | 21.0 | 0.0 | 20.00 | 21.0 | **41.2** | 2.182 |

5000 нод, окно 1100×750, шесть жестов на строку, перерисовка после каждого события.
Строки идут парами: то, что делает оператор, и то же самое, сделанное канвасом.

**У утечки есть цена, и она не в чистоте.** Столбец `пиков/g`: жест с захватом стоит два
пика (нажатие и первое наведение), жест без захвата — двадцать два, потому что каждое
утёкшее движение доходит до канваса и тот отвечает на «что под курсором» заново. Слой
операторов этот ответ уже имеет.

**И пара, ради которой таблица устроена парами: оператор стоит ровно того же, что и
собственный жест канваса.** Перетаскивание ноды левой кнопкой через оператор — 20 проходов
раскладки, 2 пика, 2.389 мс; то же перетаскивание кодом канваса — 20, 2, 2.323 мс.
Панорамирование оператором — 3.00, 2, 5.701; панорамирование канвасом — 3.00, 2, 5.521.
Счётчики совпадают, времена расходятся на шум. Разница появляется ровно там, где появляется
утечка.

**Дерево — не то же самое, что «после всех»**. Указатель идёт к самому глубокому виджету и
всплывает, поэтому драйвер-родитель получает событие последним — и это правильная сторона:
слайдер внутри ноды получает право первого отказа, и §20 claim 3 остаётся в силе без
единой строки согласования. Клавиши идут иначе: сфокусированному виджету, а если его нет —
`RenderRoot::set_focus_fallback`. Поэтому keymap слышит клавиши только после того, как
хост назвал виджет запасным адресатом; для этого в `ShellDriver` появился хук `started`.

**И одно ограничение, из-за которого место «до дерева» не может быть ответом целиком**:
`capture_pointer_event` зовётся у **корней слоёв**, а корень слоя в окне один. В
`node-canvas` редактор и есть корень, и счётчик `seen_first` растёт; в `area-screen`
редакторы вложены в области, и ни один из них этого места не имеет — тест
`an_editor_inside_an_area_has_no_pre_tree_seat` фиксирует это, потому что иначе оно
однажды «перестанет работать» без единого изменения в коде операторов.

### 38.2 Место в хосте: посчитано, а не отвергнуто

Место, о котором §11 думал, у нас всё-таки есть — но не в Masonry, а у себя: с §26 цикл
окна наш, и он сам зовёт `RenderRoot::handle_pointer_event`. Оттуда событие можно не
пропустить вовсе. Плата — контекст: хост не знает, что под курсором, и спросить может
только через `RenderRoot::edit_widget`, за которым следует полная батарея rewrite-проходов.

Строка «хост» в таблице выше — тот же самый `G`-grab, проведённый из этого места: рантайм
и мир живут снаружи дерева, на каждое событие делается зонд (что под курсором) и, если
оператор что-то сдвинул, второй зонд (перенести это в канвас) — **41.2 зонда на жест из 22
событий**. И при этом **2.182 мс против 2.649** у места внутри дерева. Хост не дороже,
потому что события, которые он забрал себе, не доходят до канваса: он платит 21 свой пик
вместо 22 чужих.

Отсюда вывод, который и стал устройством: **выбор места — не выбор, а раскладка**.
Состояние (реестр, keymap, модальный стек, история) живёт в обычном объекте
`OpRuntime<W>`, который ничего не знает о маршрутизации; событие ему приносит драйвер, и
`Seat` — это то, чем драйвер говорит, откуда оно пришло: `Host`, `Tree` (адресовано самому
драйверу — то, что даёт захват и фокус) или `Bubbled` (всплыло, дерево видело раньше).
Именно `Seat::Bubbled` при непустом стеке и есть `tree_first`.

### 38.3 Что из §11 переписано

**Оператор не трогает виджеты.** Ни один из пяти операторов примера не держит виджетного
контекста: они меняют модель и складывают в `EditorWorld::moved` номера нод, которым надо
догнать. Драйвер несёт это в свой канвас (`CanvasLayer::move_child_raw` из родительского
`RawCtx`) и в остальные виды графа через `mutate_later` — фан-аут §30, переехавший из
обработчика канваса к драйверу. Отсюда бесплатно берётся `exec`: те же операторы работают
в тесте без дерева вообще, и «клавиша и скрипт делают одно и то же» проверяется сравнением
состояния модели, а не картинки (`a_grab_and_a_scripted_move_agree`).

**Контекст собирается на наведении, а не на событии.** Вопрос §11 «кто отвечает, в каком
мы контексте» упирался в то, что драйвер с `EventCtx` не может хит-тестить ребёнка:
`CanvasLayer::hit_test` требует `WidgetMut`, а `CanvasContent::hit` — `&mut self`. Поэтому
отвечает канвас: он пикает на каждом движении и **теперь и на нажатии тоже**, и публикует
ответ в `CanvasStats::hovered`; драйвер читает его через `get_raw`. Пик не запускает
раскладку (§25.4), так что контекст стоит ровно того, что и раньше стоило наведение —
критерий `a_press_started_gesture_costs_no_extra_picks` держит это на двух пиках за жест.

**Keymap — данные, и `poll` — механизм, а не украшение.** Раскладка блендеровская: левая
кнопка тащит — ноду под курсором, а если её нет, то вид; правая выделяет — ноду под
курсором, а если её нет, то рамкой. Ни одной ветки `if` в этом нет: **каждая кнопка несёт
по две привязки, и различают их `poll` операторов**. Над нодой перетаскивание соглашается,
над пустотой отказывается и очередь доходит до панорамирования; то же на правой кнопке
между выделением и рамкой. Отказ считается (`refused`), и критерий `the_poll_is_exercised`
следит, чтобы в таблице он был. `G` и `B` оставлены клавишами — они блендеровские, и без
них из примера исчезла бы вторая разновидность модального старта, на которой стоит §38.1.

**Захват решает и то, чего keymap выразить не может.** Блендеровский keymap различает
`PRESS`, `CLICK` и `CLICK_DRAG`: клик по пустоте снимает выделение, протяжка по пустоте
двигает вид, и это две разные привязки. У нас так нельзя, и причина — та же §38.1: захват
выдаётся на нажатии и больше никогда, поэтому оператор, которому может понадобиться
удерживать указатель, обязан стартовать **на нажатии** — до того, как кто-либо может знать,
станет ли жест протяжкой. Значит, «чем этот жест оказался» решает тот, кто его держит:
`view.pan` со свойством `click_deselects` снимает выделение, если указатель так и не
сдвинулся дальше трёх пикселей, а `MoveOp` с той же стороны оставляет ноду выделенной и
ничего не пишет в историю, если её не двигали. Разделение остаётся в данных — какой
привязке что значит, говорят её свойства (`click_deselects`, `under_pointer`), — но
*момент* решения принадлежит оператору, и это не выбор, а следствие устройства апстрима.

**Вид — тоже оператор, и он показал границу правила «не трогать виджеты».** Вид
принадлежит виджету, а не модели, поэтому `view.pan` складывает смещение в
`EditorWorld::pan`, а вносит его драйвер (`CanvasLayer::pan_raw`) — тем же способом, каким
несёт сдвинутую ноду. Стоит это ровно того же, что собственный пан канваса (строки «пан»
в таблице совпадают по счётчикам).

**Канвасу понадобился шов.** Собственные жесты левой кнопки у `CanvasLayer` — умолчание, а
не механизм: канвас лежит *ниже* драйвера, и оставленный включённым он отвечал бы на
нажатие раньше, чем keymap о нём услышит. `with_builtin_gestures(false)` отдаёт левую
кнопку приложению и оставляет всё остальное — пан средней, зум колесом, пик на каждом
событии (строка «пан средней кнопкой» в таблице это и показывает).

**«Не стало хуже» — 20 раскладок против 20, 2 пика против 2.** Перетаскивание ноды через
оператор и собственное перетаскивание канваса — одна и та же кнопка, один и тот же старт,
одни и те же счётчики; времена расходятся на шум (2.389 против 2.323 мс на жест из 22
событий). Гейтом это не сделано намеренно: счётчик упирается в потолок «один проход на
событие» с обеих сторон, сломать его правкой драйвера не удалось, а критерий, который
нельзя сломать, — не критерий (§20.9). Разница появляется только у жеста без захвата —
двадцать лишних пиков, — и вот она гейтом накрыта.

### 38.4 Undo: журнал против снимка (замерено)

§30 положил истину в модель, значит undo живёт там же; вопрос был только в том, что такое
шаг. Замерено на графе в 20 000 нод, оба шага делает один и тот же оператор:

| форма | сдвинуто нод | шаг, байт | записать, мс | откатить, мс |
|---|---|---|---|---|
| журнал | 1 | 40 | 0.018 | 0.012 |
| снимок | 1 | 1 920 000 | 0.200 | 0.129 |
| журнал | 200 | 8 000 | 0.046 | 0.035 |
| снимок | 200 | 1 920 000 | 0.226 | 0.138 |

Снимок стоит **графа** на шаг, журнал — **тронутого**: на перетаскивании одной ноды это
48 000-кратная разница в памяти и одиннадцатикратная во времени, на двухстах — 240-кратная
и пятикратная. Цена журнала — по методу на оператор, который что-то меняет
(`Step::undo`/`redo`), и её платят один раз при написании оператора, а не в каждом кадре
жеста. Взят журнал; снимок оставлен в коде за `UndoMode`, потому что сравнение, которое
нельзя повторить, через год превращается в «кажется, мы это мерили».

Потолок у истории есть (`UndoStack::with_limit`, вытеснение старейшего), но умолчания нет
намеренно: сколько сессия может потратить на историю, зависит от того, что держат её шаги,
и библиотечное число здесь было бы догадкой в костюме политики — в отличие от потолка кэша
слоёв, который выведен из устройства (§37.2).

### 38.5 Куда рисует модальный оператор

Вопрос настоящий, потому что §36 сделал области слоями, а условие кэша — «слой владеет
своим прямоугольником», и проверить его хост не может (§36.4). Резинка box-select,
нарисованная поверх экрана, это условие нарушает; нарисованная внутри области — нет.

Сделано вторым способом: выделение и резинку рисует драйвер в `post_paint`, то есть внутри
своей области, в координатах канваса через `CanvasLayer::view()`. Замерено на восьми
областях над одним графом на обзорном зуме:

| жест | кэш | скопировано | перерисовано | обходов | мс кадра |
|---|---|---|---|---|---|
| выделение в одной области | нет | 0.00 | 0.00 | 0.00 | 37.39 |
| выделение в одной области | да | **7.00** | **1.00** | 1.00 | **9.58** |

Одна область из восьми, а не восемь: 9.58 мс против 37.39. Критерий
`a_selection_repaints_one_area` сломан на живом коде тем, что выделение начинает трогать
общую модель — и тогда его видят все восемь видов (8.00 перерисованных).

Отсюда же правило, которое стоит записать: **граф общий, выделение — нет**. В Blender
выделение принадлежит сцене; здесь оно принадлежит виду, и это выбрано, а не получилось
(`a_selection_stays_in_the_area_that_made_it`). Выделение в модели означало бы, что любой
клик перерисовывает каждую область, показывающую этот граф.

### 38.6 Чего это не делает

* **Перехват «до дерева» не работает как перехват.** Пока `capture_pointer_event` не умеет
  сказать «дальше не нести», модальный оператор, начатый клавишей, утекает в дерево —
  посчитано, а не спрятано. Просьба наверх сформулирована в §38.1.
* **Место в хосте построено только в бенче.** Драйвер там — сам бенчмарк; в `blazy-shell`
  из этого появился один хук (`ShellDriver::started`), а не слой.
* **Зум остался жестом канваса.** Колесо ни с чем в keymap не спорит, а `view.pan`
  показал, что оператор вида ничего не стоит сверх — так что это работа, а не вопрос.
* **`CLICK` и `CLICK_DRAG` как значения события в keymap не сделаны** и, пока захват
  выдаётся только на нажатии, сделаны быть не могут: решение отложено в оператор, а в
  данных остались свойства привязки. Если апстрим примет флаг из §38.1, это стоит
  пересмотреть — тогда keymap сможет различать их сам.
* **Меню, макросы, пользовательские переопределения keymap не сделаны**: keymap — данные
  (`Keymap::with`, `Props`, имена операторов строками), и этого достаточно, чтобы они
  стали возможны.
* **Скриптового языка нет**: `exec` — вызов из кода и из теста.
* **Свойства операторов — три типа** (`bool`, `i64`, `f64`). Первая же строка захочет
  перечисления, и тогда `Value` придётся расширять; строк в нём нет намеренно.
* **Оператор не может запустить сам себя**: реестр отдаёт коробку на время работы, и
  повторный вход паникует. Вложенные *разные* операторы стек держит.
* **Времена в таблицах — с машины разработчика** и не гейтятся (§20.9).

### 38.7 Что это меняет в плане §16

**Пункт 12 закрыт в части спайка.** Операторы, keymap как данные, модальность, undo/redo и
счётчики есть и стоят на гейте; `blazy-ops` реэкспортируется фасадом. Открытым в нём
остаётся то, что спайк намеренно не трогал: меню и пользовательские переопределения, зум
как оператор (пан уже оператор, зум остался жестом канваса — колесо ничем не спорит с
keymap) и второй драйвер — в хосте, а не в бенчмарке.

**У §17 появился четвёртый кандидат в контрибуцию, и самый дешёвый из всех**: флаг возврата
у `Layer::capture_pointer_event`. Апстрим сам записал его в TODO, а у нас есть число, чего
он стоит: 21 утёкшее событие и 20 лишних пиков на каждый жест, начатый клавишей.

**Пункт 11 (`blazy-widgets`) получил первого заказчика.** Выделение сейчас рисуется
обводкой поверх ноды, потому что ноде нечем сказать «я выделена»: наследуемых свойств нет
(§22.1), а `PropertyStack` — на виджет. Контрол, рассчитанный на плотный UI, должен уметь
состояние выделения так же, как умеет наведение.
